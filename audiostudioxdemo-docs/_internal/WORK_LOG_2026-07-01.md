## 1. 诊断(证据链)

- 上一个容器 `lastState.terminated.reason=OOMKilled`,`exitCode=137`;崩前日志一路 `/health 200`+`transcriptions 200`,**末尾无应用报错即中断** → 被内核 SIGKILL(cgroup RAM 超限),非 vLLM 自崩、非 CUDA 显存 OOM(那会有报错、不会 137)。
- 容器 `memory limit=18Gi`(chart 默认),GPU `gpumem=12288` 正常。
- 节点总 RAM **~94GiB、无内存压力** → 18Gi 单容器上限是唯一瓶颈。
- 该 pod 昨天 14:30 起、稳定运行 ~23h 未再 OOM(2 次重启都在白天密集测试时)→ **OOM 与负载相关**(并发长音频解码缓冲 + vLLM 多模态/prefix 缓存峰值),非空跑稳定泄漏。

## 2. 修复细节

- **RAM 上限 24Gi**:`audiolabxv3/templates/engine.yaml` `$memLimit` 默认 24Gi;**并且** `audiolabxv3/OlaresManifest.yaml` 的 `AUDIO_MEMORY_LIMIT` clone 字段 `default: "24Gi"`。
  - **关键教训**:OlaresManifest 里 clone-form env 的 `default` 会在 clone 时注入 `olaresEnv`,模板里 `$oe.X | default "Y"` 看到的是 manifest 的默认,不是模板的 Y。本地 `helm template`(不设 olaresEnv)只会走到 Y,**掩盖了差异**。改值要两处一起改。已写进 skill 的 GOTCHA 段。
- **MM 缓存封顶**:vLLM `--mm-processor-cache-gb ${VLLM_MM_CACHE_GB:-1}`(默认 4→1;可用 env `VLLM_MM_CACHE_GB` 覆盖)。旧 flag `--disable-mm-preprocessor-cache` 在 vLLM ≥0.13 已删,必须用新 flag。
- **Demo 并发**:`audiostudioxdemo-app/web/src/App.tsx` `sttConcBounds()` 里 qwen 分支 `{def:4,max:8}`→`{def:2,max:6}`。用户仍可拖高。
