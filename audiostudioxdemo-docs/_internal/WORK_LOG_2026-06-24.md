## 0. 这个应用是什么

老板指示做的**原型级示例应用**:上传一个音频/视频 → 经 **LLM Gateway** 调用 M1 全部音频能力
(STT / 翻译 / VAD / 说话人分离 / 降噪增强 / 声纹),用来对外展示「M1 已可通过 Gateway 提供服务」。

核心诉求(已实现):
- 独立 Olares App,浏览器里运行,通过 Gateway 的 internal 接口 + 可填 KEY。
- 可配置 Gateway URL / API Key,从 console 接口动态拉取各 mode 的可用模型做选择项。
- 上传音频/视频(视频需服务端 ffmpeg 抽音频)。
- 能力开关:勾选才调用;执行透明面板自证「只调了勾选项」。
- **按勾选能力组成工作流编排**(不是各跑各的),产出统一融合结果;各能力单独输出仍作为中间产物/证据保留。
- 导出 TXT / SRT / JSON。

## 2. 工作流编排(App.tsx run())

依赖顺序(按勾选自动降级):

1. **Enhance(前处理)** — 产出增强音频;开关 `enhancePre`「作为后续输入(歌曲建议关)」控制是否让后续步骤用增强音频。原始始终保留做前后对比。
2. **VAD / Diarize(分段)** — 在工作音频上切「谁在何时说」时间轴(优先 Diarize 带说话人,否则 VAD)。
3. **STT** —
   - **默认:整段一次调用**(verbose_json → json 兜底)。whisper 类一次拿「文字+时间戳」;Qwen3 无时间戳只出整段文字。
   - **可选 `sttFine`「逐段转写(精细·调用多)」**:按分段切片逐段转写(**串行**,遇熔断中止),可得逐行说话人文字(Qwen3 也适用),代价是调用数=段数。
4. **Translate** — 默认整段一次;`sttFine` 时逐行翻译(串行,遇熔断中止)。
5. **Embed** — 有 Diarize 时**按说话人取最长片段**算声纹(串行,遇熔断中止)→ 相似度矩阵验证区分;否则整段一个向量。

结果区:
- **⑤ 工作流融合结果** — 统一说话人 + 时间轴 + 原文/译文时间线 + 声纹相似度矩阵。
- **⑥ 各能力单独输出(中间产物/证据)** — 保留每能力原样结果。

可靠性(本轮重点):
- `callRetry` 只对真瞬时错误(502/504/网络 0)指数退避重试;`isCircuitOpen`(响应体含 `circuit`)时**立即放弃**,逐段/逐行/声纹循环**遇熔断立即 break**。
- 默认模式总调用数 ≈ 6 + 说话人数(不再是逐段扇出)。

## 4. !! 当前阻塞:Gateway 熔断(circuit breaker)!!

现象:STT(Qwen3-ASR /v1/audio/transcriptions)持续返回 **503**,响应体:
```json
{"error":{"message":"upstream provider circuit break...","type":"upstream_error","code":"upstream_circuit_open"}}
```

根因分析:
- 旧设计「逐段切片 + 并发 + 重试」把一条音频拆 25~33 段,叠加重试 → 一次运行 **289 请求 / 173MB / 42 分钟**,把 Qwen3 provider 的熔断器打开。
- 熔断打开后,后续所有请求**立即 503**(不到引擎)。VAD/Diarize/Enhance(其它 provider)仍 200。
- 已反风暴改造(见上),但**晚上验证仍 503** —— 说明熔断器**还没冷却闭合**,或 **Qwen3 引擎本身已被打挂/异常**(单次请求也会再次触发熔断)。

注:更早一次**整段** Qwen3 请求曾返回 400(verbose_json 不支持)→ 证明引擎当时是活的、能响应。所以最可能是「熔断未复位」或「引擎被风暴拖垮」。

# 续:2026-06-25 下午(落地完成 + 第二道内存关)

## 重要修正:GPU 配额下 vLLM 有「两道」内存关,不止一道

上午只解决了第一道。重新部署后第二道才暴露:

- **关于「原地 upgrade 走不通」**:`nvidia.com/gpu` 由 Olares gpu-inject 准入 webhook 在「安装时」注入(chart 只写 `nvidia.com/gpumem` + `gpu-inject` 注解,llamacppllmbasev3 同款标准写法)。`market upgrade` 走 patch 不触发注入 → 报 `resources.limits: Limit must be set for non overcommitable resources`。**结论:GPU 应用改 chart 只能走「先删后传 chart + uninstall + 重 clone」,不能原地 upgrade。**
- **clone id 由 `--title` 哈希决定**:同 title 重 clone 必回同一 id `audiolabxv3ad5667` → 同 NS → 同 URL `53b75222` → **网关 provider 无需重建/改地址**(印证用户判断)。
- **同版本 chart 必须先 `market delete` 再 `upload`**:只 upload 不 delete,实测 clone 出来的 deployment 仍是旧渲染(env 缺 `VLLM_GPU_UTIL`、cmd 缺 `--max-model-len`)。

### 第一道:分配 OOM(util 写死 0.8)
util 是占「物理整卡 24G」的比例,0.8≈19G ≫ 12G 配额 → 首次推理触碰物理页被 OOM 杀。已改为按配额动态算 `VLLM_GPU_UTIL`(12288/24454×0.85=**0.43**)。

### 第二道:KV 容量校验失败(max_model_len 65536)
util 降到 0.43 后,启动日志真实数据:权重 3.9G、CUDA graph 0.14G、**Available KV cache 4.93G**;而 Qwen3-ASR 默认 `max_model_len=65536` 单请求需 **7.0G KV** → vLLM 启动即 `ValueError: ... larger than the available KV cache memory (4.93 GiB) ... estimated maximum model length is 46192`,**CrashLoopBackOff 8 次**(不是分配 OOM,是启动期容量断言)。
修复:engine.yaml qwen3-asr cmd 加 `--max-model-len ${VLLM_MAX_LEN:-32768}`,注入 env `VLLM_MAX_LEN`(默认 32768,可用 `MODEL_MAX_LEN` 覆盖)。ASR 音频分块,32768 远够;32768 KV ≈3.5G < 4.93G。

## 本轮修的问题(按发生顺序)

1. **Enhance 1h5m 报 500(CUDA OOM)**
   - 错误:`enhance failed: CUDA out of memory. Tried to allocate 15.02 GiB ... 3.19 MiB free ... this process has 20.04 GiB in use`。
   - 根因:speechbrain 增强把**整条波形**塞 GPU,1h 一次要 ~15G;且那张卡是共享的、当时几乎被别的租户占满(只剩 3MB)。
   - 修:**分块 enhance**(`App.tsx` Stage0)。`ENH_WHOLE_MAX=900`(≤15min 仍整段,15min 整段已验证 OK)、`ENH_CHUNK=900`、`ENH_CONC=1`(串行降峰值显存)。逐块降噪 → 解码 → `concatToWav`(`audio.ts` 新增,接缝处 5ms 淡入淡出消爆音)拼回整段。**失败块用原始切片填回**,保证整轨长度/时间轴不变。

2. **Embed 间歇 500(`Calculated padded input size (6) < kernel size (7)`)**
   - 根因:ECAPA 卷积核=7,VAD/Diar 的零点几秒极短段帧数不够。
   - 修:`App.tsx` 新增 `embedSlice()`,embed 前把窗口**对称扩展到 ≥1.2s**(贴边回夹,裁到音频内)。两处 embed 切片(diar 声纹缝合 / 逐说话人)都改用它。

3. **413 Payload Too Large(VAD 整段 + DIAR 20min 分块)** ← 今晚主坑
   - 根因:enhance 输出是**未压缩 WAV**(1h ≈ 115MB),作为 workingAudio 传给 VAD(整段)直接超 Olares 边缘(envoy)请求体上限;DIAR 的 20min 分块用 `sliceWav` 切出来也是 ~38MB WAV,同样 413。
   - 修(三件):
     - `server.js` 新增 **`POST /api/transcode`**(`toMp3_16kMono`:ffmpeg → 16k 单声道 **64k MP3**,临时文件进出)。
     - `api.ts` 新增 `transcodeToMp3` + `edgeSafe`:`audioMultipart` 发送前,**>8MB 且非压缩格式**自动转 MP3 再发(STT 的 30s 小片 ~1MB 原样直发,不增开销)。
     - `App.tsx` enhance 输出(整段/分块两路)产出后**一次性压成 MP3** 再当 workingAudio,并 `decoded=null` 让下游重新解码。
   - 源音频若是超大 WAV:由 `edgeSafe` 兜底(MP3 源不重复压)。

4. **空段污染**:STT 后 `fused` **丢弃 `text` 为空的片段**(silence/noise 产生的空 1s 段),融合结果/时间轴更干净。

5. **STT 超长段试验(先加后撤)**:发现 101s/215s 大片段来自 diar/VAD 的连续长发言;`coalesceSegments` 只合并不拆分;vLLM whisper 对 >30s 输入内部按 30s 自动切。曾加 `splitLong` 把 >30s 等分,**用户当时觉得 200s+ 也稳定 → 已撤回**。**但见下方今晚最终发现,这个判断要翻案。**

## 结果:1h5m 全流程**首次完整跑通**(server 日志全 200)

- Enhance:5 块全 200(每块 ~5-6s),拼接+压成 31MB MP3 → 413 消失。
- VAD:200,31s。
- **Diarization:4 个 20min 分块全部 200** → 128s / 289s / 137s / 42s(合计 ~10 分钟,串行)。
- Embeddings:5 个 200(diar 声纹缝合)。
- STT transcriptions:逐段 200(每段 ~20-44s)。
- ⚠ 用户看到的「进入队列 9.2 分钟 / 已停止 / 尚未完成」**不是失败**:是 Chrome 同域名 ~6 并发连接上限,串行长 diar 分块占满连接 → 后续请求被浏览器排队,面板画成灰条像挂了,轮到就跑完。

## ‼ 今晚最终关键发现(明天第一优先级)

**STT 段 >30s 时 whisper 仍会幻觉死循环**(转录出现「姆·姆·姆·姆…」整段重复的奇葩输出),即使 vLLM 有内部分块也救不了。
→ **结论翻案:长段必须在客户端切到 ≤30s**(撤回的 `splitLong` 要重新引入)。
