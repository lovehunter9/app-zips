# 方案一 / 方案二 / 方案三 / 方案五 客户端设计

> 本文是四条"客户端类"候选方案的设计层文档。**目的**：为每条路径给出"用户故事 → 模块拆解 → 关键 API/契约 → 与 LarePass 的衔接点 → 工作量估算"，物料量级足以支撑最终选型判断与立项决定。
>
> **不做的事**：不写完整代码、不画 UI 高保真、不锁死技术栈细节（如最终用 Quasar 还是 Tauri 这种二选题留到立项时拍）。

---

## 一、四条路径的全景对照

| 路径 | 形态 | 平台 | 上下游依赖 | 工作量量级 |
|---|---|---|---|---|
| **方案一 用户自选系统 IME** | 推荐清单 + 配置指南 + 方案五 桌面端衔接 | Android / iOS / 桌面 | 选品 + 文档 | 0.5‑1 人月 |
| **方案二 Olares 自家完整 IME APK** | Android IME（含 RecognitionService）| Android | 模型本地化 + 方案四 远端兜底 + LarePass 触达 | 5‑8 人月 |
| **方案三 RecognitionService-only APK** | Android RecognitionService（不带 IME UI）| Android | 同 方案二 子集 | 3‑5 人月 |
| **方案五 LarePass-aware 桌面客户端** | macOS / Windows / Linux 桌面 dictation app | 桌面 | LarePass Service Provider SDK + 方案四 sharedEntrance | 6‑10 人月（含三平台） |

> 方案四是后端（见 `06_R4_集群侧设计.md`）。本文只讨论"用户能直接看到 / 装上"的客户端。

## 二、方案一 ── 用户自选系统 IME（零工程）

### 2.1 用户故事

> "我已经在用 Gboard / FUTO Keyboard / WhisperIME / 讯飞输入法 / Apple 自带输入法。请告诉我怎么配置才能用上 Olares 集群里的 ASR，不用换输入法。"

### 2.2 关键洞察

- **Android：用户其实可以保留 Gboard 等首选输入法，只需多装一个 RecognitionService APK**——参考 方案三 路径；方案一 路径下，Olares 不主动做 APK，但**给出"哪些 IME 支持自定义 RecognitionService"的推荐清单**。
- **iOS**：第三方键盘无麦权限是 Apple 政策硬约束；iOS 用户用 Apple 系统 dictation 是唯一选择。
- **桌面**：方案一 路径在桌面端等价于"用户已经装了 Type4Me / VoiceInk / Handy / CapsWriter Client 等第三方桌面端"，Olares 只需引导用户把 OpenAI baseURL 配到 方案四 endpoint。

### 2.3 产出物

| 产出 | 形式 | 维护周期 |
|---|---|---|
| **《Olares 语音输入 IME 兼容性指南》** | docx + Olares 应用商店内嵌文档页 | 每季度复审 |
| Android 兼容性表 | Gboard + Samsung Keyboard + FUTO + HeliBoard + WhisperIME 等 RecognitionService 切换指南 | 季度 |
| iOS 兼容性表 | "Apple 系统语音 + 桌面 方案五 覆盖" 二件套指南 | 半年 |
| 桌面端"配 OpenAI baseURL"指南 | Type4Me / VoiceInk / Handy / CapsWriter / Whispr / hyprwhspr 各自截图 | 季度 |

### 2.4 LarePass 衔接点

- LarePass 在用户首次登录后弹"语音输入推荐"页，引导到本指南；
- 桌面 LarePass 客户端可"一键复制" 方案四 sharedEntrance URL 到剪贴板（**这条建议同时进 方案五 设计**）。

### 2.5 工作量

| 工作 | 时长 |
|---|---|
| 各平台兼容性测试 + 截图 | 1.5 周 |
| 文档撰写（中英双语）| 1 周 |
| LarePass 弹窗 PR | 0.5 周 |
| **合计** | **0.5‑1 人月** |

## 三、方案二 ── Olares 自家完整 IME APK（重型）

### 3.1 用户故事

> "我装了 Olares + LarePass。我希望 Android 手机上有一个 Olares 官方语音输入法，按住麦克风就能识别中文，识别走我家集群 GPU，离线时本地兜底。不再依赖 Google / 讯飞 / 百度。"

### 3.2 总体形态

- 一个 Android APK，同时实现：
  - `InputMethodService` （系统输入法 IME UI，键盘弹出后可切到语音模式）
  - `RecognitionService`（让其他 IME 如 Gboard 在按麦克风时调到本 APK）
  - 后台 Foreground Service（持续录音 + 模型推理）
  - LarePass-aware 配置面板（与 LarePass 共享登录态、自动发现 方案四 endpoint）

### 3.3 技术栈选型

| 层 | 选型 | 备注 |
|---|---|---|
| 语言 | **Kotlin**（Java 必要时） | Android IME 事实标准；FUTO/HeliBoard/WhisperIME 都是 Kotlin |
| UI | Jetpack Compose | 现代 Android UI |
| 本地 ASR 引擎 | **sherpa-onnx**（Android prebuilt 库）| 跨架构 + 支持 SenseVoice/Paraformer/Whisper-tiny |
| 本地 VAD | sherpa-onnx 内置 silero VAD | 已有 |
| 模型 | SenseVoice-Small（中文）+ Whisper-tiny（多语种）双下载 | ~280 MB 总体 |
| 远端 ASR | speaches-ext OpenAI 兼容 endpoint | 通过 方案四 |
| 网络 | OkHttp + Retrofit | 标准 Android 栈 |
| LarePass 衔接 | LarePass Android SDK（如存在）/ AAR 引用 / Intent 跨 APP 通讯 | 待确认 LarePass 是否有 Android SDK |
| 持久化 | Room（SQLite）| 历史记录 + 配置 |
| Build | Gradle + AGP 8.x | 标准 |

### 3.5 引擎策略

| 场景 | 默认引擎 | 切换条件 |
|---|---|---|
| 离线 / 无 方案四 配置 | LocalSenseVoiceEngine（中文）+ LocalWhisperTinyEngine（其他语种） | 无网或集群不可达 |
| 在线 + 已连 LarePass + 集群有 GPU | RemoteSpeachesEngine | 默认在线高准模式 |
| 用户手动锁本地 | LocalSenseVoiceEngine | 隐私模式开关 |

### 3.6 LarePass 衔接细节

> 这是 方案二 最大的工程不确定项；与 方案五 共享一组未解决问题。

| 问题 | 当前认知 | 决定方式 |
|---|---|---|
| LarePass Android SDK 是否存在 | 未确认 | 看 LarePass 仓库（已知 `apps/packages/app` 是 Quasar+Capacitor，理论上有 Android 入口）|
| 跨 APP 通讯方式 | 三选：Intent + Bundle / Content Provider / Bound Service | 优先 Bound Service（持久连接、可推送 endpoint 变更）|
| 用户身份共享 | LarePass 已有 OIDC 风格 token，可通过 SDK 颁发短期凭据给本 IME | 与 LarePass team 对齐 |
| sharedEntrance 拿什么形式 | 推荐 `{ host, port, basePath, token, expiresAt }` JSON | 与 方案五 共用同一 SDK 协议 |

**Fallback**：如果 LarePass 没有 Android SDK，**方案二 的"LarePass 连接"页面可降级为手动填 URL + token**（用户从 LarePass 桌面端复制过来）。

### 3.7 关键 API（自家定义）

```kotlin
interface AsrEngine {
    suspend fun startStreaming(audio: Flow<ByteArray>): Flow<TranscriptChunk>
    suspend fun transcribeFile(audio: ByteArray, sampleRateHz: Int): TranscriptResult
    fun supports(feature: AsrFeature): Boolean   // streaming / multilang / vad
}

data class TranscriptChunk(
    val text: String,
    val isFinal: Boolean,
    val confidence: Float?,
    val timestampMs: Long
)

interface LarePassConnector {
    suspend fun discoverServiceProvider(name: String): ServiceProvider?
    fun observe(): Flow<LarePassConnectionState>
}

data class ServiceProvider(
    val name: String,            // "speaches-ext"
    val baseUrl: String,         // "https://speaches-ext.<user>.<topDomain>/v1"
    val authToken: String,
    val expiresAt: Long,
    val tags: List<String>       // ["openai-compatible-asr", ...]
)
```

## 四、方案三 ── RecognitionService-only APK（轻型）

### 4.1 用户故事

> "我用 Gboard / Samsung Keyboard / FUTO 用得很好，不想换。我希望按 Gboard 的麦克风键时，语音识别走我家 Olares 集群，不要走 Google Cloud。"

### 4.2 与 方案二 的差异

- **去掉 InputMethodService**：不实现键盘 UI，不抢占用户的默认输入法；
- **保留 RecognitionService**：把识别服务挂到 Android 系统，让任何支持 `SpeechRecognizer` API 的 IME / app 都能调到；
- **配置面板**：一个简单的 Activity（不是 IME 设置），让用户连 LarePass / 选模型 / 看历史。

### 4.3 用户体验对比

| 行为 | 方案二 | 方案三 |
|---|---|---|
| 用户安装步骤 | 8 步（含切默认 IME） | **6 步**（无需切 IME，仅启用 RecognitionService）|
| 默认输入法 | 切到 Olares IME | 保持原有（Gboard 等）|
| 语音入口 | Olares IME 的麦克风键 | Gboard 等的麦克风键 |
| 用户感知 | "换了一个输入法" | "原有输入法的麦克风变厉害了" |

> 方案三 用户感知更轻、抵抗力更小、潜在用户面更大。**这是优先级仅次于 方案五 的客户端路径**。

### 4.4 模块拆解（方案二 的子集）

```
olares-recognition-android/
├── app/src/main/java/com/olares/recognition/
│   ├── service/
│   │   └── OlaresRecognitionService.kt   # 唯一系统 service
│   ├── engine/   ← 与 方案二 共享
│   ├── larepass/ ← 与 方案二 共享
│   ├── settings/
│   │   └── ConfigActivity.kt              # 简化的设置入口（不是 IME 设置）
│   └── data/    ← 与 方案二 共享
└── AndroidManifest.xml
```

### 4.5 与 方案二 的代码复用策略

- **engine/、larepass/、data/ 共享 ~70%**：抽成 Gradle module（`:core-engine`、`:core-larepass`、`:core-data`），方案二 与 方案三 各自的 `:app` 引用即可。
- **方案三 先出，方案二 后做**：方案三 工作量小、用户面大；先验证 方案四 endpoint 的实际表现，再决定要不要做完整 IME。

### 4.6 工作量估算

| 模块 | 时长 |
|---|---|
| `:core-engine` (sherpa-onnx + OkHttp) | 2 周 |
| `:core-larepass` (前提：SDK 存在) | 2 周 |
| `:core-data` (Room + Config) | 1 周 |
| RecognitionService 实现 | 1 周 |
| ConfigActivity（Compose）| 1 周 |
| F-Droid 包装 + 测试 | 2 周 |
| 端到端兼容测试（Gboard / Samsung / Pixel / 小米 / FUTO）| 2 周 |
| 国际化 + bug 修复 buffer | 1 周 |
| **合计** | **约 12 周 ≈ 3 人月**（共享假设成立） |
| LarePass SDK 自研 buffer | 视 方案二 是否同步做而摊销 |
| **乐观‑悲观区间** | **3‑5 人月** |

> 方案二 / 方案三 同时开工的话，因 `:core-*` 共享，**合并工作量约 6‑10 人月**，而非 5+3 = 8 人月。

## 五、方案五 ── LarePass-aware 桌面客户端（旗舰）

### 5.1 用户故事

> "我在 macOS / Windows / Linux 上长时间敲键盘，希望按一个全局热键就能录音 + 识别 + 注入到当前焦点输入框；识别走我家 Olares 集群（隐私 + 高准 + 多语种），离线时本地兜底；不依赖 OpenAI / Anthropic 公有云的 API key（除非我主动配置）。"

### 5.2 形态选择

| 候选形态 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|
| **A. 全自研 Tauri Rust 跨平台 app**（参考 Handy）| 三平台一致；体积小（~10 MB 单二进制）；现代化 | 自研工作量大；要做 macOS Accessibility / Windows IInputManager / Linux ydotool 三套注入 | ★★★★☆ |
| **B. Fork 已有 OSS（Handy / Type4Me / hyprwhspr）增加 LarePass 集成** | 复用大量基线；快速出版本 | 要维护三个 fork（一平台一个）；上游升级 rebase 麻烦 | ★★★☆☆ |
| **C. Quasar/Capacitor 桌面（沿用 LarePass 自身技术栈）** | 与 LarePass 团队技术对齐；可直接进 LarePass 主包 | 全局热键 + 文本注入在 Electron/Quasar 里要绕弯（Tauri 已经验证 Rust 直接 OK）| ★★☆☆☆ |
| **D. 多客户端推荐 + 集成 SDK / CLI 中间件**（不自做客户端，做一个"adapter daemon"） | 工作量极小；用户用自己喜欢的 ASR 客户端 | 不能控制 UX；不少 ASR 客户端不支持自定义 baseURL（如 Whisperboard） | ★★★★☆（与 方案一 重叠）|

**推荐组合**：
- **短期（短期阶段）= D + 方案一 指南**：写一份"如何让 Handy / Type4Me / VoiceInk / CapsWriter Client 用 方案四 endpoint"的指南；
- **中期（中期阶段）= A 全自研 Tauri**：基于 Handy 的代码做 hard fork（许可证 MIT 允许），加 LarePass Service Provider 发现 + Olares 主题；
- **长期（长期阶段）= 维护三平台 + iOS 文件转录辅助**。

> 下方 §5.3‑5.9 以"中期 = A 全自研 Tauri"为主线展开。

### 5.3 技术栈选型

| 层 | 选型 | 备注 |
|---|---|---|
| Shell | **Tauri 2.x** | Rust 后端 + WebView UI；跨 macOS/Win/Linux |
| 后端 | **Rust** | 复用 Handy/Voquill/Murmur 生态 |
| UI | **React + TypeScript + Tailwind** | Handy 已是这套；用户偏好 |
| 全局热键 | `rdev` 或 `tauri-plugin-global-shortcut` | 跨平台 |
| 音频捕获 | `cpal` | 跨平台 |
| 文本注入 | 自家 `enigo` wrapper（macOS Accessibility + Win SendInput + Linux ydotool/wtype） | 视平台 |
| 本地 ASR | `whisper-rs` + `transcribe-rs` + `vad-rs` | 同 Handy |
| 远端 ASR | `reqwest` 调 方案四 sharedEntrance（OpenAI SDK 风格） | Handy 已有云模式可扩展 |
| LarePass 衔接 | **LarePass 桌面客户端 IPC**（Unix socket / Named Pipe / HTTP loopback） | 待确认 LarePass 是否暴露此接口 |
| 配置存储 | `tauri-plugin-store` (~/.config/olares-voice) | 标准 |
| Auto-update | `tauri-plugin-updater` + Sparkle (macOS) | 标准 |

### 5.5 引擎切换策略

```
[用户按热键]
    ↓
[Hotkey Manager]
    ↓
[Audio Capture (cpal) 启动]
    ↓
[VAD 检测语音段，松开热键停止]
    ↓
[Transcriber 抽象]
    ├── if LarePass connected && endpoint reachable
    │      → RemoteSpeachesEngine (方案四 sharedEntrance)
    ├── elif user explicitly chose "local only"
    │      → LocalSenseVoiceEngine / LocalWhisperEngine
    ├── elif user has BYOK (OpenAI / Anthropic / Groq)
    │      → BYOKCloudEngine
    └── else fallback to Local (with warning toast)
    ↓
[Optional LLM postprocess]
    ├── if user enabled "auto polish"
    │   ├── if LarePass connected → ollamav2 sharedEntrance
    │   └── elif BYOK → OpenAI / Anthropic
    └── else skip
    ↓
[TextInjector]
    ├── macOS: AX/AXValue if focused app supports it, else Pasteboard + Cmd+V
    ├── Windows: SendInput Unicode
    └── Linux: ydotool (Wayland) / xdotool (X11)
```

### 5.6 LarePass 衔接细节

| 子问题 | 设计 |
|---|---|
| LarePass 是否已在用户机器上运行 | 启动时 lookup IPC socket（`~/Library/Containers/com.olares.larepass/Data/Library/Caches/sp.sock` 或 Win NamedPipe `\\.\pipe\larepass`），找不到则提示用户先装 LarePass |
| Service Provider 查询 | IPC 调 `larepass.discoverServiceProvider("speaches-ext")` → 返回 `{baseUrl, token, expiresAt, tags}` |
| Token 刷新 | LarePass 颁发短期 token（30 min），自家维护刷新；过期后自动重新 IPC 拿 |
| 多用户切换 | LarePass 当前登录用户切换时，触发 callback → 客户端清掉 endpoint 缓存重拉 |
| 离线 fallback | LarePass 不可达时，UI 红条提示，但允许继续用本地 / BYOK |

> 这一节是 方案五 最大的工程不确定项。**强烈建议立项前与 LarePass team 对齐"是否已有 / 计划做 Service Provider SDK"**。备选：客户端不依赖 LarePass，让用户手动复制 URL + token；体验差但可行。

### 5.7 关键 UX 决定

| 决定 | 取舍 |
|---|---|
| **默认引擎是哪个** | 推荐 RemoteSpeaches（方案四）；理由：方案四 准确率高 + 隐私好（仍在用户家） |
| **录音模式** | 推荐"按住录音"（VoiceInk/Type4Me 主流）；可选"双击切换" |
| **注入方式** | macOS 优先 AX → fallback 剪贴板（VoiceInk 实测剪贴板更稳）；Windows SendInput；Linux ydotool |
| **LLM 后处理默认** | **默认关闭**；用户主动开 |
| **历史记录是否上传** | **绝不**；本地 SQLite，用户可一键删除 |
| **首启引导** | 三步：① LarePass 连接（自动 / 手动）② 选默认引擎（远端 / 本地）③ 设全局热键 |

## 八、跨路径的共享技术与决定

### 8.1 LarePass Service Provider SDK / IPC 是 方案二/方案三/方案五 共享的基础设施

- 三条路径都依赖它；
- **建议立项第一周即与 LarePass team 对齐其形态**；
- 如果 LarePass 已有 SDK / IPC，三条路径全部受益；
- 如果没有，需 LarePass team 投入 0.5‑1 人月做 SDK，或客户端自己 ad-hoc 解析 LarePass 本地配置（不优雅，但能跑）。

### 8.2 引擎契约（AsrEngine）应在 方案二 / 方案三 / 方案五 之间统一

- Kotlin 版本（Android）和 Rust 版本（桌面）的接口形状保持镜像；
- 这样 方案四 endpoint 升级时（如加 streaming），三平台一起改。

### 8.3 模型源策略与 方案四 保持一致

- 中文走 ModelScope，Whisper 走 hf-mirror.com；
- 方案五 客户端首启时如果选"本地"，自动从同样的源拉模型；
- 客户端内置模型选择 UI = 方案四 OlaresManifest 公开的 alias 列表（如 `whisper-1` / `sensevoice` / `paraformer`），保证用户在客户端选了什么，远端就有什么。

### 8.4 隐私默认值统一

- 历史记录 = 本地 SQLite，绝不上传；
- 音频 = 不落盘，转写完销毁；
- LLM 后处理 = 默认关闭；
- 数据出网（仅 LarePass VPN + 集群本地）= 默认；任何公网 BYOK 都需要用户显式配置。

## 九、章节小结

1. **方案一 = 文档 + 指南**：0.5‑1 人月即可上线，0 工程；与 方案五（轻量版）配合可覆盖大多数桌面用户。
2. **方案五（轻量版） = adapter daemon + 客户端指南**：1 人月即可上线；是"短期最经济、最快验证 方案四 价值"的路径。
3. **方案五（完整版） = 中期旗舰**：4.5‑6.5 人月（三平台），基于 Handy fork + LarePass 集成 + 引擎抽象；推荐 中期阶段 启动。
4. **方案三 = Android 短期最优**：3‑5 人月，无需用户换 IME，搭配 Gboard 等主流键盘即可使用；优先于 方案二。
5. **方案二 = Android 长期完整**：5‑8 人月，做完整 IME；建议看 方案三 反响后决定是否启动。
6. **LarePass Service Provider SDK 是关键基础设施**：直接影响 方案二/方案三/方案五 工作量的 ±30%；**立项前必须与 LarePass team 对齐**。
7. **iOS 路径**：仅 方案一（Apple 系统）+ 方案五 桌面端覆盖；不要尝试 方案二/方案三 在 iOS，**这是已查证的硬约束**。
