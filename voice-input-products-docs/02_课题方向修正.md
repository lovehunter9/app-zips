## 一、用户的关键澄清

原话（保留以供审计）：

> LarePass 是 Olares 的移动端，它存在输入法（可能直接集成了所安装在的系统的），现在要考虑的课题之一就是在 LarePass 里集成 typeless 这类应用的可能性与复杂度。**我们不关心 LarePass 具体的实现，也不会把这个集成直接做在 LarePass 里**，让你分析源代码是为了有更清晰的视图来做这个设计。

可拆出 4 条事实约束：

| 编号 | 约束 |
|---|---|
| C‑1 | LarePass 的"主战场"是**移动端**；其"输入法"概念**可能不是自带 IME**，而是间接利用所在系统的输入法 / Autofill |
| C‑2 | 课题之一是"在 LarePass 里集成 typeless 这类应用"——**用户视角**的"集成"（即 LarePass 用户能用上语音输入），不是工程视角的"代码塞进 LarePass 仓库" |
| C‑3 | **不动 LarePass 代码**：不 fork、不向上游 PR、不修改 LarePass 源代码 |
| C‑4 | LarePass 源码考察的目的是**避免设计踩空**（拿清晰视图）的**背景知识**，不是开工依据 |

## 三、新的集成路径分类（方案一 ~ 方案五）

> 命名以 R 开头（Reframed），与原 P 系列清晰区分。下文 §4 给出 R↔P 完整映射表。

### 方案一 「零工程·系统输入法兼容」路径

**思路**：什么都不做。告诉 LarePass 用户："在你的手机上装一个支持语音的输入法（Gboard / SwiftKey / 讯飞 / 搜狗 / 百度 / WhisperIME / Kaiboard / VoxPen / Sayboard / FUTO Keyboard），它们的麦克风按钮在 LarePass 的任何输入框里都能用。"

| 维度 | 评估 |
|---|---|
| 用户感知 | 一般（要装额外 App，体验取决于第三方 IME） |
| 工程量 | **零** |
| 涉及谁 | 用户自己 + 第三方 IME 作者 |
| 与 LarePass 耦合 | **零**（C‑3 完美满足） |
| 隐私 | 取决于用户选择的 IME（Gboard / 讯飞默认走云；WhisperIME / FUTO Keyboard 默认走端侧） |
| 适合作为：基线对照 |

**作为基线**：本路径的存在意味着即便我们什么都不做，用户仍有完全可用的方案。任何后续 方案二 ~ 方案五 都必须证明"比 方案一 多带来什么"。

### 方案二 「独立 Olares 语音输入法 APP」路径

**思路**：发布一个独立的 Android（可选 iOS）应用，本身是一个完整的 IME（Input Method Editor），自带本地 Whisper / Sherpa‑ONNX / FunASR 推理；可选配置为"指向用户家 Olares 集群里的 ASR 后端服务（即下文 方案四）"以获得更高精度或更多模型选择。

样本集中**直接可作为参考样板**的项目：

| 项目 | 形态 | 引擎 | 可借鉴度 |
|---|---|---|---|
| `woheller69/whisperIME`（重点分析项目） | Android IME，纯开源，F‑Droid | whisper.cpp | ★★★★★ — 完整 IME + RecognitionService 双形态 |
| `kaisoapbox/kaiboard` | Android IME | whisper.cpp（assets/models/） | ★★★★ |
| `soanseng/voxpen-android` | Android IME，Kotlin + Jetpack Compose | BYOK Whisper + LLM | ★★★★ |
| `ElishaAz/Sayboard` | Android IME，GPL‑3，555★ | Vosk | ★★★（引擎不同） |
| `DevEmperor/Dictate` | VoxPen 的父项目 | — | ★★ |
| `futo-org/voice-input` + FUTO Keyboard | 独立服务 + 自带 IME | whisper.cpp + ACFT 微调 | ★★★★★（最成熟参考） |

| 维度 | 评估 |
|---|---|
| 用户感知 | 强（"Olares 官方语音输入法"品牌效应） |
| 工程量 | **中‑高**（Android IME 框架 + 模型分发 + 上架 Play / F‑Droid + 可选 ASR endpoint 配置 UI） |
| 涉及谁 | Olares 团队（或独立开发者） |
| 与 LarePass 耦合 | **可选**（IME 默认走本地，可选切到 Olares ASR） |
| 关键工程点 | InputMethodService、模型分发体积、Wayland/iOS 受限（iOS 自定义键盘无法注入麦克风权限以外的本地推理，需特别评估） |

### 方案三 「独立 RecognitionService APK」路径

**思路**：不做 IME，只发一个独立 APK，实现 Android 的 `android.speech.RecognitionService` 协议；用户在系统设置里把"语音输入"换成我们；之后用户原有的 Gboard / HeliBoard / FlorisBoard / AnySoftKeyboard / Unexpected Keyboard 在点击麦克风按钮时会自动委托给我们。我们再决定是本地推理还是调远端 Olares ASR。

**直接样板**：

| 项目 | 说明 |
|---|---|
| `futo-org/voice-input`（**主要参考**） | FUTO Voice Input，独立 RecognitionService APK，被 HeliBoard / FlorisBoard / AnySoftKeyboard / Unexpected Keyboard / AOSP Keyboard 通用 |
| `woheller69/whisperIME` 也兼任 RecognitionService | 同一 APK 既是 IME 也是 RecognitionService |
| `woheller69/whisper_android`（vilassn fork） | HeliBoard 社区推荐的 RecognitionService 实现 |

| 维度 | 评估 |
|---|---|
| 用户感知 | 中（用户不需要换 IME，只要切换"系统语音输入"，体感无缝） |
| 工程量 | **中**（比 方案二 小一半 — 不用做完整 IME，专注 RecognitionService 协议） |
| 涉及谁 | Olares 团队（或独立开发者） |
| 与 LarePass 耦合 | **可选**（默认走本地，可选切到 Olares ASR） |
| 局限 | 部分 IME（如 Gboard）固定只用自家语音输入，不开放委托给第三方 RecognitionService — 这部分用户拿不到 |

### 方案四 「Olares 集群侧 ASR 后端」路径（= 原 P‑A）

**思路**：把 Whisper / FunASR / sherpa‑onnx / Speaches / WhisperLiveKit / faster‑whisper‑server / whisperX‑FastAPI 等任一服务以 Olares Market 应用形式打包，通过 `sharedEntrances` 暴露 OpenAI 兼容 REST + WebSocket 流式接口；任何"支持自定义 endpoint"的端到端语音输入产品（含 方案一 / 方案二 / 方案三 用户选的 IME）都能把 baseURL 改成 Olares 共享地址。

**直接样板**（来自 服务端选项）：

| 项目 | 接口 | 一键部署度 |
|---|---|---|
| `speaches-ai/speaches` | OpenAI 兼容 REST + 流式 | ★★★★★ Docker 一键 |
| `QuentinFuxa/WhisperLiveKit` | WS `/asr` + REST `/v1/audio/transcriptions` | ★★★★★ pip 装即用 |
| `Nyralei/whisperx-api-server` | OpenAI 兼容 + Kafka/S3 分布式可选 | ★★★★ |
| `pavelzbornik/whisperX-FastAPI` | REST 模块化 | ★★★★ |
| `ahmetoner/whisper-asr-webservice` | REST | ★★★★ |
| `collabora/WhisperLive` | WebSocket 实时 | ★★★ |
| 自己用 `funasr` / `sherpa-onnx` 套 FastAPI | 自定义 | ★★ |

| 维度 | 评估 |
|---|---|
| 用户感知 | 间接（不直接用 方案四，而是通过 方案二/方案三 用） |
| 工程量 | **低‑中**（已有 OpenAI 兼容服务端 → 套 Helm + `OlaresManifest.yaml`；GPU/模型分发是主要变数） |
| 涉及谁 | Olares 团队 |
| 与 LarePass 耦合 | **零**（C‑3 完美满足） |
| 作为：方案二 / 方案三 / 方案五 的**必要基础设施** | 方案四 是这一切的"地基"。即便选了 方案一，用户也可以单独跑 方案四 给自己的桌面客户端用 |

### 方案五 「第三方端到端产品 LarePass‑aware」路径（≈ 原 P‑C）

**思路**：让 重点 / 横向对比项目 中支持自定义 ASR endpoint 的端到端产品（如 Type4Me / Handy / VoiceInk / FluidVoice / OpenWhispr / TypeWhisper / Talkie / hyprwhspr / Voquill 等）在配置里识别"用户已登录的 LarePass 身份 + Tailscale 在线"，自动填充 Olares 集群内 ASR 共享地址 — 这一步对用户透明。需要这些产品的作者添加对应支持，但**不需要 LarePass 改任何代码**。

| 维度 | 评估 |
|---|---|
| 用户感知 | 强（用户体验"一键就接上自家 Olares ASR"） |
| 工程量 | **低**（每个产品只需加一个 Olares config 入口，~一两百行代码） |
| 涉及谁 | 各第三方产品作者（社区路线）或 Olares 团队提交 PR |
| 与 LarePass 耦合 | **零代码耦合**，但有协议耦合（约定通过 Headscale/Tailscale 的 hostname 找到 ASR 服务） |
| 局限 | 只覆盖**桌面端**；移动端用户不直接受益（移动端用户仍要走 方案一/方案二/方案三） |

## 八、本次修正后剩余的不确定项

1. **LarePass 移动端是否真的引入了某种 IME 概念**（用户表述里的"可能直接集成了所安装在的系统的"），还是只有 Autofill 服务。按 C‑4，本课题不再深究——但如果后续 方案二 / 方案三 设计需要避免"与 LarePass 的某个潜在 IME 路径冲突"，则需要回头确认。**当前列为"不深究，但保留再开口子"。**
2. **方案五 与 LarePass 的"识别 LarePass 在线"约定协议**：是用 Tailscale hostname 约定？还是 LarePass 暴露一个 `lares://discover` URL Scheme？或借 Olares 的 OIDC？这个**需要 Olares / LarePass 团队定义一个公共约定**，否则 方案五 各个第三方产品就要各自硬编码 — 这条会留到 §8.4 设计层评估中明确。
3. **iOS 端的 方案二 / 方案三 完全不存在**：iOS 自定义键盘不允许做"系统 RecognitionService"（这是 Android 独有协议），且自定义键盘对网络访问有严格限制。iOS 路径只能依赖 方案一（用户在系统设置里启用 Dictation，由 Apple SpeechAnalyzer / Whisper Memos 等处理）或 方案五（桌面客户端 LarePass‑aware）。
4. **方案三 在国内 Android ROM（MIUI / HarmonyOS / ColorOS 等）的兼容性**：部分国内 ROM 对第三方 RecognitionService 有限制甚至屏蔽，这个会影响 方案三 实际可达的用户面，需在 §8.3 中以 `[推测]` 或 "需实测" 标注。
5. **方案一 与 方案三 在 LarePass 自身 Autofill 上的冲突**：如果 LarePass 已经注册了系统 Autofill Service（用于密码 / OTP 填充），与"用户切换系统语音输入到 方案三"会不会触发输入焦点冲突？属于实测题，留待 §8.5 组合策略章节确认。
