## 二、Step 2 ── LarePass 源码考察

### 2.1 突破性发现

用户给的旧仓库 `github.com/beclab/TermiPass` 仍然存在但已不再维护（最后 v1.2.17，2024‑06‑17）。LarePass 的真实当前源码已迁入 `beclab/Olares` 主仓的 `apps/` 子目录。这是今天最关键的事实更正——以"我先看一下旧仓的项目"为出发点的任何分析都会落空。

具体证据链：
1. `beclab/Olares/apps/README.md` 第一段："*This directory contains the code for system applications, primarily for LarePass.*"
2. `beclab/Olares/apps/lerna.json` 表明这是 Lerna 单仓库（`packages/*`）。
3. `beclab/Olares/apps/package.json` 显示 6 个子包，npm scope 是 **`@didvault`**（LarePass 项目内部代号 = DIDvault）。
4. `apps/packages/app/package.json` 给出客户端真实技术栈：**Quasar 2 + Vue 3 + Capacitor 7 + Electron 39 + TypeScript 4**，一份代码 build 出 **14 个不同 entry**（Vault / Wise / Files / Share / Wizard / Login / Desktop / Dashboard / Control Hub / Profile Editor / Profile Preview / Market / Settings / Studio）。

### 2.2 调查方法
沙箱不允许直接 `git clone`，改用 GitHub Contents API + raw.githubusercontent.com 直接拉关键文件：
- `apps/README.md`
- `apps/package.json`、`apps/lerna.json`、`apps/tsconfig.json`
- `apps/packages/app/package.json`（200+ 依赖全清单）
- `apps/packages/app/README.md`
- `apps/packages/server/package.json`
- `apps/packages/app/src/` 顶层目录列表（38 个条目）

这种方式比 `git clone` 更省事，缺点是不能 grep 全代码——但对于"识别技术栈 + 顶层结构 + 空白领域"的目的够用。

### 2.3 三个最有价值的认知

1. **LarePass 是 14 entry 巨型 monorepo**。"加一个语音输入功能"必须先回答"加在 14 个 entry 的哪一个 / 还是做成共享组件让多个 entry 复用 / 还是新开第 15 个 entry"。

2. **客户端目前**完全没有任何语音相关代码**。`src/` 下没有 `audio/` / `microphone/` / `voice/` / `whisper/` / `asr/` / `speech/` 任何目录；`package.json` 里也没有 `voice-recorder` / `microphone` / `speech-recognition` / `media-recorder` 这类 Capacitor 插件。这意味着这是个干净的空白领域，没有历史包袱，但也意味着没有任何上游"半成品"可借力。

3. **"移植 Olares" 与 "集成 LarePass" 工程边界是干净可分的**：
   - 前者只在 Olares Helm + `OlaresManifest` 一侧落地，与 LarePass 客户端正交。
   - 后者要在 Vue 3 + Capacitor 原生插件（Swift + Kotlin）+ Electron 主进程三个层面同时铺路，工程量自然更大。

### 2.4 踩到的坑
1. **GitHub Web 直接 fetch 仓库子路径返回 404**（无论是 `https://github.com/beclab/Olares/tree/main/apps`、`/apps/larepass`、`/apps/packages/app` 都 404）。WebSearch 能搜到，但 WebFetch 不行。这是 GitHub 对非浏览器 UA 的反爬措施。最终走 GitHub Contents API（`api.github.com/repos/.../contents/...`）成功。
2. **预设了一个错误的路径 `apps/larepass/`**。先入为主以为"主要给 LarePass 的代码 = `apps/larepass`"——实际上 `apps/` 下没有这个目录，所有 LarePass 客户端代码都在 `apps/packages/app/` 里，分 14 个 build entry。教训：永远先列目录再做断言。
3. **同名干扰**：`LaraPass`（Laravel/PHP 密码管理器）、`alibori/larapass`（Laravel + NativePHP）跟 beclab 的 LarePass 完全无关。要靠"维护组织 + 技术栈 + 命名空间"三重验证排除。

### 4.3 关键发现

1. **2025‑2026 桌面语音输入主流派系是 Swift 原生 + Tauri Rust 两条主线**——共占 ≥60%，Electron 已被边缘化（样本里只有 OpenWhispr / Buzz 两个）。
2. **R‑4 Olares 集群 ASR 后端最佳样板就是 CapsWriter Server 端**——它的 C/S 严格分离 + multiprocessing 子进程隔离 + sherpa-onnx 多引擎接入 + RAG 热词系统，几乎可以原样作为 Olares Market app 部署蓝本。
3. **R‑5 LarePass‑aware 路径的天然候选**有 5 个 Tier 1 项目（Type4Me / Handy / hyprwhspr / CapsWriter / Voquill）+ 3‑5 个 Tier 2 项目（Talkie / Dictto / Epicenter 等）已经支持自定义 endpoint，每家 PR 工作量 ≤ 200 行。
4. **R‑2 / R‑3 移动端的唯一开源样板是 WhisperIME**——它已经同时实现了 `InputMethodService` 和 `RecognitionService`；分发只能走 F‑Droid（Google Play 2026/2027 强制实名将让此类项目退出）。
5. **iOS 路径在系统级注入层面客观不存在**——Whisperboard、Aiko 都不是真正的"语音输入法"，是"录音转录工具"。命题 B 在 iOS 上事实上只有 R‑5 桌面端覆盖一条路。
6. **Tauri Bundler / Rust crate `transcribe-rs` 是跨平台桌面语音输入的新标准**——它本身在做"屏蔽 Whisper 推理后端差异（whisper-cpp / onnx / metal / vulkan / directml）"这件事，Handy 已经把它用熟。
7. **Cohere Transcribe 模型在客户端的 CoreML 集成**只有 FluidVoice 一家做了（通过 FluidAudio 的 `B/cohere-coreml-asr` 分支）——值得后续 §4 大模型对比时单独留一行。

### 5.3 关键操作性结论

1. **R‑4 Olares 集群默认 = `speaches`（Whisper-large-v3-turbo）+ 新增 `olares-funasr`（SenseVoice-Small）双部署 + 复用 `ollamav2` 做 LLM 后处理**——三组件 ≤ 6 GB 模型 + ≤ 8 GB VRAM 覆盖 80% 场景。
2. **R‑2 / R‑3 Android 默认引擎 = sherpa-onnx + SenseVoice-Small**（~228 MB ONNX，Apache-2，ModelScope 国内拉），不要绑 Whisper TFLite（体积大且国内难拉）。
3. **R‑5 LarePass-aware 桌面端模型默认 = 用户家 Olares 集群里的 R‑4 服务**；离线兜底 = 火山豆包（中文）/ Groq Whisper-turbo（英文）；这两家都在国内 / 国外有最低成本路径。
4. **iOS 路径补充**：Apple macOS 26+ 引入的 SpeechAnalyzer 是 R‑5 桌面 Mac 用户的"无成本基线"，第三方 ASR 必须证明"比系统快/准/隐私更好"才有黏性。
5. **Cohere / Voxtral / Parakeet** 三个模型在许可证、国内可得性、Olares 集群部署体积上各有限制，**都不适合作为 R‑4 的默认**，但可作为"高级用户可选"档。
6. **国内可获得性的事实标准**：模型走 ModelScope 镜像（SenseVoice / Paraformer / Qwen3-ASR / 国产模型）+ 推理代码走 GitHub（必要时 ghproxy）+ 云后端走火山豆包 / 阿里云 NLS。

### 5.4 关键不确定项

- `speaches` 现有 Olares 应用是否已暴露 sharedEntrances（影响 R‑4 第一版到底是"零工程"还是"小工程"）
- CapsWriter Server 端容器化的实测踩坑（特别 `multiprocessing.Process` 在 K8s pod 内）

### 7.3 重大事实更新（反向修正 §04）

**§04 §九原结论**：R‑4 第一版需要 speaches + 新建 olares-funasr + ollamav2 三件套。

**§05 落实后的更新**：speaches Olares 应用**已经把完整 OpenAI 兼容 API 通过 sharedEntrance 暴露给集群内其他 app**，且 CHAT_COMPLETION_BASE_URL 默认就指向 ollamav2 sharedEntrance；预装 faster-whisper-small + Kokoro-82M TTS。

→ **R‑4 第一版几乎"零工程"** —— R‑5 客户端只需把 OpenAI baseURL 指到 speaches sharedEntrance 即可。第二阶段才需要"中文扩展"（fork speaches 加 sherpa-onnx，或新建 olares-funasr）。

### 7.4 其他关键发现

1. **macOS / Windows 桌面平均 4 步装完**，Linux 5‑6 步是当前痛点（Wayland 注入 + systemd/udev）。
2. **Android IME 安装下限硬性 8 步**（系统强制"启用 + 切默认"两步独立）。
3. **iOS 第三方键盘无麦权限**——R‑2 / R‑3 在 iOS 完全不可行，只能 R‑1（Apple 系统）+ R‑5（桌面端覆盖）。这是 §02 应补进的硬约束 C‑5。
