# 市场全景与样本概览

> **本文定位**：列出报告所覆盖的产品样本、引擎清单与生态背景。具体的"集成方案、技术对比、选型推荐、风险"等结论请直接读 `README.md` 与编号 03–09 的章节文档。本文不下结论，只做"样本盘点"。

> **报告主题**：横向对比当前可获得的 AI 语音输入类产品（开源为主、商业闭源对照），覆盖 macOS / Windows / Linux / Android / iOS / 跨平台 6 个维度，并独立评估与 **LarePass**（Olares 官方跨平台客户端）以及 **Olares**（K8s‑based 个人云 OS）两个生态体的集成可行性。

---

## 一、目标与边界

### 1.1 报告目标
- 横向对比当前可见的 AI 语音输入产品（开源为主、商业闭源为对照），覆盖 macOS / Windows / Linux / Android / iOS / 跨平台 6 个维度。
- 系统梳理底层引擎（whisper.cpp、WhisperKit、faster‑whisper、sherpa‑onnx、Parakeet、SenseVoice 等）的能力差异。
- 独立评估两件不同的集成命题：
  - **命题 A**：把语音输入服务"**移植到 Olares**"——以 Olares Market 应用形式部署后端服务。
  - **命题 B**：与 "**LarePass** 客户端"集成——在官方跨平台客户端里增加语音输入能力或与之协同。

### 1.2 本报告**不做**的事
- 不输出可执行的设计稿（不写 Helm chart、不写 `OlaresManifest.yaml`、不写代码骨架）。本系列**只到设计层面**的可行性评估。
- 不做用户端可用性 / 易用性主观打分。
- 不评估商业模式 / 定价 / 法律合规。
- 不绑定任何单一产品作为"锚点"，所有样本平等对待。

## 三、LarePass / Olares 关系澄清

这一节是后续两条集成路径（命题 A / B）的前置事实。

### 3.1 名词对齐

| 名称 | 角色 | 状态 |
|---|---|---|
| **Olares** | 自托管个人云 OS（K8s + Helm），原名 Terminus | 主仓 `beclab/Olares`（4.5k★，Go 为主），AGPL‑3 |
| **LarePass** | Olares 官方跨平台**客户端**（身份钱包 / VPN / 文件同步 / 密码 / 知识收藏） | 原名 TermiPass。当前源码位于 `beclab/Olares/apps/` 子目录（Lerna 单仓库，npm scope `@didvault`） |
| **TermiPass 旧仓** | `github.com/beclab/TermiPass` | **遗留**，最后版本 v1.2.17（2024‑06‑17） |
| **`beclab/apps`** | Olares Market 的官方应用集合（Helm chart + `OlaresManifest.yaml`） | 51★，Python；**与 LarePass 客户端无关**，是上架 Olares 应用商店的 PR 仓库 |

> 单独有一份 `01_LarePass源码考察.md` 把 `beclab/Olares/apps/` 的真实目录结构、技术栈和构建产物一一落地。

### 3.2 Olares 应用与外部通信的三种入口（基于 `OlaresManifest` v0.11）

1. **常规应用入口 `entrances:`**：HTTP 端口对外，由 Olares 路由分配 `xxx.olaresid.olares.com`，浏览器 / LarePass 桌面或移动端可访问。`authLevel ∈ {private, public, internal}`。
2. **共享入口 `sharedEntrances:`（v0.11 新增）**：后端服务以集群内地址 `{route-ID}.shared.olares.com` 暴露，供**其它应用**而非用户调用。典型场景：Ollama / ComfyUI 作为 headless backend，LobeChat / OpenWebUI / Continue.dev 等客户端把 baseURL 指过来。
3. **Service Provider 机制（v0.10 新增）**：应用在 manifest `provider:` 声明开放给集群内其它应用的 REST 接口集合，调用方在 `permission.provider:` 申请权限，Olares 自动生成 K8s Service + envoy sidecar 做访问控制。这是 Olares 应用之间 RPC 的官方协议。

### 3.3 集成方案的最终定型

> 本节给出"最终采用的五条候选方案"。其推导过程（含一条已废弃的"修改 LarePass 源码"方案）见 `02_课题方向修正.md`；对外读者无需关心推导。

| 候选方案 | 含义 |
|---|---|
| **方案一：系统输入法兼容** | 不动用户现有输入法，输出推荐清单 + 配置指南，让 LarePass 用户在已装的输入法里直接用语音 |
| **方案二：自研完整移动输入法** | 发布 Olares 官方 Android（可选 iOS）APK，自带完整 IME UI + 本地引擎 + 可选远端 ASR |
| **方案三：自研移动语音识别后台服务** | 发布 Android `RecognitionService` APK，不带键盘 UI；用户保留原有 IME，麦克风键调到本服务 |
| **方案四：集群侧统一语音后端** | Olares Market 应用，统一暴露 OpenAI 兼容 STT/TTS/LLM endpoint，供所有上层客户端复用 |
| **方案五：第三方桌面端 LarePass 感知集成** | 让 Type4Me / Handy / VoiceInk / CapsWriter 等已有桌面客户端在用户登录 LarePass 时自动发现集群语音后端 |

- **三级置信度**：`[高]` 有官方文档 / 源码 / 直接抓包证据；`[中]` 多方独立第三方证据 + 一致逻辑推断；`[推测]` 仅有间接线索。
- "安装复杂度"判断优先使用 README 的官方步骤数 + 公开 Issue 中的失败报告，不做主观估算。
- "集成可行性"判断只能基于 (a) Olares 官方文档（manifest 规范、Provider、sharedEntrances）+ (b) LarePass 源码实际目录结构与 `package.json`；任何超出这两类证据的结论必须明确标 `[推测]`。
- 商业闭源产品（Typeless 闭源、Wispr Flow、SuperWhisper、Monologue 等）仅作行业对照，技术细节标 `[推测]` 或注明"基于第三方评测推断"。

## 六、已知盲点

1. **Capacitor 原生插件细节**：LarePass 移动端是否已自研某个语音相关 Capacitor 插件，待与 LarePass team 确认。

5. **Typeless 闭源版的真实模型选型**只能基于第三方评测推断，本报告将明确标 `[推测]`，不会硬下结论。
