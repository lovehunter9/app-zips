# 安装与运行复杂度 / 生态横向对比

> 本文回答的核心问题：**"如果一个普通用户想用上 §02 §三五条 候选方案中任意一条，他需要做几步？踩哪几个坑？模型从哪儿拉？依赖装在哪儿？"** 通过桌面 / 移动 / 服务端三栏对比 重点 / 横向对比项目 项目的真实安装流程，把"技术上可行"翻译成"用户上能跑"。

---

## 一、方法与评分维度

### 1.1 维度（6 维）

| # | 维度 | 量化方式 |
|---|---|---|
| I1 | **从下载到能录第一句话的步骤数** | 计 GUI 点击 + 命令行 + 配置项；目标 ≤ 5 步 = ★★★★★ |
| I2 | **模型下载体积** | MB / GB；含首次拉的所有 ASR + VAD + LLM |
| I3 | **首启耗时**（含模型加载） | 秒；带 / 不带 GPU 两档 |
| I4 | **硬件门槛** | CPU only / 任意 GPU / 仅 Apple Silicon / 仅 NVIDIA CUDA |
| I5 | **依赖冲突风险** | 0=单二进制；1=容器；2=系统 pip/cargo/npm；3=多依赖手编译（如 espeak-ng+cuda+pyaudio） |
| I6 | **权限授予步骤数** | 麦克风 + 辅助功能 + 全盘 + 输入监听 + 系统 IME 启用 + 离屏权限的数量 |

### 1.2 约定

- 所有评分按 **2025‑11 至 2026‑05 公开 release** 为准；任何"未发布的某 PR"不计。
- 步骤数严格按"普通用户、有网络"假设；不含极端情况（无 Xcode + macOS Sequoia 之前的 SDK 等）。
- 模型体积按"项目默认推荐档"计；可选下载更大模型的另计。
- 凡 §04 §十待核实清单中已查证项，本文用 `[高]` 标；查证来源放进 §九。

**macOS 桌面端关键观察**：

1. **5 步以内 = 行业平均**——99% 项目都是 `下载 → 拖应用 → 启动 → 授权 3 项 → 用`，无需命令行。
2. **Apple Silicon 是事实强制**——FluidAudio / WhisperKit / MLX 都不跑 Intel；重点分析项目 项目中只有 Handy 和 Type4Me（云模式）正经支持 Intel mac。
3. **3 项权限**几乎所有 dictation 类应用都要齐：麦克风（Audio Capture）+ 辅助功能（Accessibility，监听全局热键）+ 输入监听（Input Monitoring，CGEvent 注入）。这是 macOS 13+ 的硬性要求，不可绕过。`[高]`
4. **TestFlight 路径是 iOS 唯一选择**——但 iOS 真应用不超过 1 个（Whisperboard），其余都是文件转录。

**Linux 桌面端关键观察**：

1. **Linux 是用户体验最差的一档**——平均步骤数 5‑6 步，常涉及 systemd / udev / WM 配置；普通用户难以独立完成。
2. **Wayland 注入是事实门槛**——所有 Wayland 路径都要装 `ydotool` 守护进程并配置组权限；X11 用户走 `xdotool` 较顺。
3. **AUR 包是 Arch / Hyprland 用户最干净的路径**（hyprwhspr 给出标杆）；Debian/Ubuntu 用户多数靠 deb/AppImage，体验差异较大。
4. **Murmur（Tauri Rust 单二进制 + 多平台一致）是 Linux 用户最容易上手的英文方案**——但中文场景仍要回到 CapsWriter（需 Wine 跑 Windows 版）或自部署 CapsWriter Server 端。

**Android 关键观察**：

1. **8 步是 Android IME 安装的硬下限**——再优化也降不到 5 步以下，因为 Android 强制要求"启用 + 切换"两步独立。`[高]`
2. **F-Droid 是首选分发渠道**——Google Play 在 2026/2027 起对个人开发者要求"实名 + 持续维护"，多数开源 IME 项目会先迁 F-Droid。`[中]`
3. **国内分发渠道（华为 / 小米 / OPPO / vivo / 应用宝）**对开源 IME 极不友好——绝大多数项目不在国内应用商店上架；用户需自行下载 APK + 启用未知来源安装。这是 方案二 / 方案三 在国内分发时的最大门槛。
4. **HarmonyOS 4.x 兼容性**：含 GMS 替代层（HMS Core）的非纯血鸿蒙可装大部分基于 TFLite/ONNX 的 IME；纯血鸿蒙（HarmonyOS NEXT）不兼容 Android APK，需重新开发。`[中]`

### 4.2 关于 `speaches` Olares 应用现状（§04 §十 #6 查证已落实）

> 通过查看 `app-zips/speaches/OlaresManifest.yaml` 和 `speachesserver/templates/speaches.yaml` 完全核实。`[高]`

- **sharedEntrance**：`sharedentrances-speaches`（K8s Service port 80 → targetPort 8000），`authLevel: internal`，`invisible: true` — **集群内其他 app 可以直接通过这个 host 调完整 OpenAI 兼容 API**。
- **entrance**：三个公开入口：
  - UI（Gradio Playground，port 8080）
  - Terminal（CLI 管理模型，port 8081）
  - API（与 sharedEntrance 等价，port 8082，invisible）
- **GPU 支持**：CUDA 12.4.1 镜像 + `applications.app.bytetrade.io/gpu-inject: "true"` 注解；CPU fallback `:0.8.2-cpu`；通过 `SPEACHES_GPU` 环境变量切换。
- **预装模型**：
  - STT：`Systran/faster-whisper-small`（默认，可换 large-v3）
  - TTS：`speaches-ai/Kokoro-82M-v1.0-ONNX`
- **Chat 链路**：环境变量 `CHAT_COMPLETION_BASE_URL` 默认指向 `http://d54536a50.shared.{topDomain}/v1` —— 即 **ollamav2 的 sharedEntrance**。换言之 speaches 自带"audio chat"功能默认会走集群里的 Ollama。
- **多用户**：`clusterScoped: true`（admin 装一份，其他 user 通过 `dependencies.application: speaches` 引用）—— Olares 多租户共享模式。
- **存储**：`hostPath` 挂在 `userspace.userData/Huggingface/speaches`，模型持久化。
- **资源配额**：GPU 模式 2.5–9 Gi RAM + 4–16 Gi GPU；CPU 模式 2.5–9 Gi RAM。

**对 方案四 设计的直接影响**：

> 方案四 第一版基本上**不需要开发**——直接复用现有 `speaches` 即可作为"OpenAI 兼容的 STT/TTS 后端"，方案五 桌面客户端只需把 baseURL 配到 `https://<sharedEntrance>/v1` 即可。这把 方案四 的工程量从"中型"压到"几乎为零"。

**但仍需补的事**（中文 / 多语种场景）：

1. speaches 的 faster-whisper 后端**只能跑 Whisper 家族**，中文场景仍需扩展到 SenseVoice / Paraformer / FunASR。两种做法：
   - **方案 A（推荐）**：fork speaches 加上 sherpa-onnx 后端 → 同一容器支持 Whisper + SenseVoice，仍走 /v1/audio/transcriptions OpenAI 兼容 path。技术成本中等，但对用户最干净。
   - **方案 B**：新建独立 `olares-funasr` 应用（基于 CapsWriter Server fork 或 sherpa-onnx 自家 FastAPI），暴露独立 sharedEntrance；缺点是 方案五 客户端要支持"双 endpoint"配置。
2. speaches 默认模型是 `faster-whisper-small`，对中文 ASR 准确率不够；建议为中文场景**默认改为 `Systran/faster-whisper-large-v3`**（通过 `SPEACHES_WHISPER_MODEL` 环境变量即可，无需改代码），代价是 ~2 GB → ~3 GB 模型 + 6 GB VRAM。

### 4.3 关于 CapsWriter Server 容器化（§04 §十 #7 查证已落实）

> 公网已存在至少 3 个成熟的容器化 fork，均围绕 CapsWriter Server 端。`[高]`

| Fork | 镜像 | 体积 | 维护情况 |
|---|---|---|---|
| `DF-wu/CapsWriter-Offline-Container` | `ghcr.io/df-wu/capswriter-offline-server:latest` | ~4 GB | **生产级 fork**；GPU/CPU 自适应；默认 `qwen_asr` + 备选 `fun_asr_nano`；自动 bootstrap 模型 |
| `xieyuschen/CapsWriter-Offline` | `xieyuschen/capswriter:v1.0.0` | ~4.6 GB | 整包含模型；开箱即用；2025‑12 发布 |
| `sipcink/capswriter-offline-server` | `sipcink/capswriter-offline-server:1.0` | ~3 GB | docker-compose 教程版 |

- **K8s 内 multiprocessing.Process 行为**：CapsWriter 服务端使用 `util/server/service.py` 在独立子进程跑 AI 模型（防止 GIL 阻塞 WebSocket 心跳）—— 这是合法的 K8s pod 内模型，PID namespace 隔离不会有冲突。`[高]`
- **K8s 部署路径**：用 Kompose 把 docker-compose.yml 转 K8s Manifest 后稍作调整即可；建议加一个 `PersistentVolumeClaim` 持久化 `models/` 目录，避免每次启动重下 ~700 MB Paraformer。
- **WebSocket 协议**：CapsWriter 默认 6016 端口，**自家 protobuf 协议**，不是 OpenAI 兼容——方案五 客户端要么走 CapsWriter 官方 client.exe（不现实），要么需自行实现协议适配（适中工作量，参考 `util/client/ws_client.py`）。

**对 方案四 设计的影响**：

> CapsWriter Server 的容器化已被验证，可以走 方案四 的"中文场景默认 ASR 后端"路径，但要解决两件事：(a) 写 Helm chart（参照 speaches 那一份即可）；(b) 方案五 客户端要么集成 CapsWriter WS 协议，要么在服务端加个 OpenAI 兼容适配层。后者推荐——只要在 K8s 同 pod 里挂个 Python FastAPI sidecar，把 OpenAI POST 转 protobuf 即可。

## 六、候选方案用户体验地图

> 把 §02 五条 候选方案翻译成"用户从零到能用"的最少步骤数与权限清单。

### 6.1 各 候选方案步骤数

| 候选方案 | 用户安装步骤数 | 权限项数 | 模型下载体积 | 网络要求 | 关键限制 |
|---|---|---|---|---|---|

| **方案二 Olares 自家完整 IME APK** | 8 步（同 Android IME 标准）+ 跳过 Google Play | 3 项 | ~280 MB（SenseVoice + 标点 + VAD）| 首启需要拉 ModelScope | 不上 Google Play；F-Droid + Olares 自家分发 |
| **方案三 RecognitionService-only APK** | 6 步（无需"切换默认输入法"）| 2 项（麦 + RecognitionService 启用） | 同 方案二 | 同上 | 必须搭配支持 RecognitionService 的 IME（Gboard / Samsung Keyboard 默认支持） |

| **方案五 第三方 LarePass-aware 桌面客户端** | 4 步（装客户端）+ 1 步（填 Olares baseURL 或扫码）| 3 项（同桌面 dictation） | 0（远端推理）| 客户端到集群可达 | 需 LarePass 安装在同一设备并已登录（用于发现 sharedEntrance） |

### 6.2 端到端"装 → 用"路径推荐

#### 路径 A：**纯国内 Android 用户**（推荐组合 方案一 或 方案二 + 方案五）

1. 手机：装 Olares 官方 IME APK（方案二，从 LarePass 二维码 / 应用商店分发）
2. 系统设置 → 启用 → 切默认
3. 平时打字按麦克风键，本地 SenseVoice 跑（无网亦可）
4. （可选）家里装了 Olares，IME 配置中填 `https://<speaches sharedEntrance>` → 切到远端"高准模式"

#### 路径 B：**macOS 用户**（推荐组合 方案五）

1. 装 LarePass macOS 客户端（确认登录）
2. 装 Type4Me 或 VoiceInk 或 Handy（按个人偏好）
3. 在客户端设置里把 "OpenAI BaseURL" 填成 `https://<speaches sharedEntrance>/v1`，API key 留空或填 "olares-token"
4. 平时按热键说话，ASR 走家里 GPU；离线时 fallback 到 SenseVoice/Whisper 本地

#### 路径 C：**Windows / Linux 用户**（推荐组合 方案五 + 本地 fallback）

1. 装 Handy 或 Murmur 或 CapsWriter Client
2. 配置 ASR 后端 = Olares speaches endpoint
3. 本地装 whisper-small 作离线兜底

#### 路径 D：**iOS 用户**（推荐组合 方案一 + 方案五 桌面端覆盖）

1. iOS 端：直接用 Apple SpeechAnalyzer（系统输入法）
2. 桌面端：按路径 B 配置 方案五
3. iOS 不能装第三方语音 IME，这是无解项

## 七、安装风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Apple Silicon 强制 | Type4Me / VoiceInk / FluidVoice 等只支持 ARM mac | 方案五 默认配 Handy（多平台 Tauri）+ Type4Me（云模式） |
| Google Play 个人开发者实名（2026/2027 起） | 方案二 / 方案三 APK 不能上 Google Play | 走 F-Droid + LarePass 二维码 + Olares 自家镜像分发 |
| Apple Notarization | macOS 端项目不签可能被 Gatekeeper 拦 | 推荐 方案五 客户端走官方 Homebrew Cask + Apple Developer ID |
| iOS 第三方键盘无麦权限 | 方案二 / 方案三 在 iOS 不可行 | 仅 方案一（Apple 系统）+ 方案五（桌面端覆盖）；接受 |
| CC-BY-4.0 模型（Parakeet）Attribution | 方案四 / 方案五 商用要保留版权说明 | 在 OlaresManifest + 方案五 客户端"关于"页加 attribution |
| Cohere 模型本地商用许可 | 不能裸装在 Olares Market | 仅作"高级用户客户端可选"，不进 方案四 默认 |

| 模型版本不一致导致客户端报错 | speaches 改默认模型后 方案五 客户端可能预期某 endpoint 不存在 | 方案五 客户端启动时调 `/v1/models` 探测可用模型清单，UI 给用户选 |
| Olares sharedEntrance 名字硬编码 | 方案五 客户端写死 `sharedentrances-speaches` 在用户改了 admin / app name 时会失效 | 通过 LarePass Service Provider 机制取，不要硬编 |

## 八、章节结论

1. **方案四 第一版几乎零工程**：speaches 现有 Olares 应用已经把 OpenAI 兼容 STT/TTS 完整暴露在集群内 sharedEntrance（端口 80 → 8000），还自带 ollamav2 LLM 联动。方案五 桌面客户端把 baseURL 指过来即可。`[高]`
2. **方案四 第二阶段重点 = 中文扩展**：fork speaches 加 sherpa-onnx 后端跑 SenseVoice 是首选（保持 OpenAI 兼容），或者新建 `olares-funasr` 走 CapsWriter Server 容器化路径。`[高]`
3. **桌面端用户体验已成熟**：macOS / Windows 平均 4 步装完；Linux 5‑6 步是当前痛点，主要拖累在 Wayland 注入和 systemd/udev 配置。
4. **Android IME 安装下限 = 8 步**：这是系统硬性要求，无法压缩；分发渠道 = F-Droid + LarePass 二维码 + Olares 应用商店；Google Play 不能依赖。
5. **iOS 只能 方案一（Apple 系统）+ 方案五（桌面端覆盖）**：iOS 第三方键盘无麦权限，这是无解硬约束（应补进 §02 ）。
6. **模型源策略**：阿里系走 ModelScope（直连国内、无需登录、已被 sherpa-onnx 等大量项目使用）；OpenAI / NVIDIA / Mistral 系走 HF + hf-mirror.com；方案四 集群侧用 hostPath PVC 一次下载所有用户共享（speaches 已用此模式）。`[高]`
7. **CapsWriter Server 容器化已成熟**：3 个公网 fork 可直拉；K8s 部署只差 Helm chart；其内部 `multiprocessing.Process` 在 K8s pod 内行为正常无特殊踩坑。`[高]`

## 十一、一句话结论
