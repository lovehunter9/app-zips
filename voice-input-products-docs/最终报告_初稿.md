# Olares 语音输入产品综合调研 · 最终报告（初稿）

> **重要：本报告已锚定到统一语音 AI 平台愿景。** 完整产品形态、架构、落地路线请优先看 [`../voice-ai-platform-docs/README.md`](../voice-ai-platform-docs/README.md)。本报告聚焦"语音输入法"这一用例集在统一平台下的角色，以及该用例独有的市场全景、技术架构、客户端形态细节。

---

## 一、产品愿景下的本课题角色

**统一平台一句话**：做一个新 Olares 应用（暂名 `voice-ai-hub`），提供一套统一 API（OpenAI 兼容 + 扩展），让用户跑转录 / 实时听写 / 会议 / 翻译 / TTS / 播客等 26 个用例；底层模型全部可配置（本地"独立模型应用" + 远程 BYOK）。

**"语音输入法"在该平台下不是独立产品，而是 3 个 API 用例的实现路径**：

| 用例 | API 端点 | 实时性 | 主要消费方 |
|---|---|---|---|
| **A-3 流式 STT** | `/v1/audio/realtime`（WebSocket）| < 300 ms | 任意流式客户端（桌面 / 移动 / 浏览器扩展）|
| **A-4 实时语音录入（dictate）** | `/v1/dictate/stream`（WebSocket，含标点 / 数字 / 大小写恢复）| < 500 ms | 桌面 IME 客户端 / Android RecognitionService / iOS（系统层）|
| **C-1 会议记录（实时段）** | `/v1/meeting/sessions` + `/stream` | 实时增量 | 会议机器人 / 浏览器扩展 / 桌面 App |

**之前推荐的"自研 IME APK / 完整移动输入法 / 桌面客户端"现在的定位**：

- ✅ 这些**仍然是有意义的项目**——它们是核心应用的**客户端外壳**
- ⏬ 但都**降级为统一平台的第三阶段（长期）路线**——不在第一/第二阶段做
- 🔄 之前的"集群侧 R-4 设计"内容**全部并入**统一平台的"接入本地 STT 模型应用 + 接入远程流式 STT BYOK"任务

## 二、本课题独有的事实清单

> 这部分内容是统一平台规划中**不重复**的、属于"语音输入法用例"独有的事实。

### 2.1 平台覆盖与硬约束

| 平台 | 客户端形态 | 关键约束 |
|---|---|---|
| **macOS** | Tauri 2 + Rust + 全局热键 + Accessibility API 注入 | Apple Silicon 优先用 WhisperKit；ANE 加速 |
| **Windows** | Tauri 2 + Rust + `SendInput` 注入 | INT8 量化跑 small 模型 |
| **Linux** | Tauri 2 + Rust + `xdotool` / `wtype` / `ydotool` 注入 | X11 / Wayland 两路径 |
| **Android** | Kotlin + `InputMethodService` 或 **`RecognitionService`** | 国产 ROM 后台限制是最大坑 |
| **iOS** | 走系统 Dictation；自定义键盘**无麦克风权限不可绕过** | Apple 政策硬约束 |

### 2.2 五条客户端方案（原报告核心，现降级为"长期客户端外壳"备选）

| 方案 | 一句话 | 用户面 | 工作量 | 统一平台下的位置 |
|---|---|---|---|---|
| **方案一：系统输入法兼容** | 整理"哪个第三方 IME 在 LarePass 输入框里能用"的设置教程 | ~95% 全平台 | 零 | 兜底永远存在，但不阻塞 |
| **方案二：自研完整移动输入法** | 发布"Olares 输入法 APK"，自带键盘 UI + 引擎 | ~35% 安卓中文 | 6–8 人月 | **不做**（投入翻倍而净增益有限）|
| **方案三：Android `RecognitionService` 后台服务** | 不带键盘 UI；用户保留原 IME，麦克风键调到本服务 | ~70% 安卓 | 3–5 人月 | **第三阶段 3.2** |
| **方案四：集群侧统一语音后端** | 集群里跑 OpenAI 兼容 STT/TTS endpoint | 间接服务所有人 | 短期零（已成品） | **已被统一平台核心应用 + 本地 STT 模型应用替代** |
| **方案五：桌面端 LarePass 感知集成** | fork `Handy` 做 Olares 感知；轻量版 adapter daemon → 完整自研 Tauri | ~60% 桌面 | 1–7 人月 | **第三阶段 3.1**（推荐 fork `Handy`）|

### 2.4 国产 Android ROM 兼容性（实测前的预判）

| ROM | 第三方 RecognitionService 限制 | 应对 |
|---|---|---|
| **MIUI / HyperOS** | 系统级语音绑定搜狗；用户切换路径深 | 详细文档化设置步骤 |
| **HarmonyOS（非纯血）** | 应用商店里 WhisperIME / FUTO 缺席；侧载安装提示多 | 侧载教程 + 应用商店申请通道 |
| **ColorOS / FunTouch** | 后台杀进程激进 | 加白名单引导 |

| **OxygenOS / 原生 Android** | 兼容性最好 | 默认推荐 |

立项时实测 5 家是必做事项。

### 2.5 iOS 政策约束（硬性，自 iOS 8 起未变；通过 iOS 18 仍然有效）

> 来源：Apple《App Extension Programming Guide: Custom Keyboard》—— "Custom keyboards, like all app extensions in iOS 8.0, have no access to the device microphone, so dictation input is not possible."

- 第三方键盘（custom keyboard extension）**没有麦克风权限**（`AVAudioRecorder` 失败 / `SFSpeechRecognizer` 不可用 / 无 Siri 集成）
- 系统 Dictation 仅在系统输入法上能调，第三方键盘**点不到麦克风按钮**
- **但存在三条 workaround 路径**（Wave / Spokenly / Wispr Flow / Willow 等都用其中一种）：
  - **host-app 模式**：键盘麦克风按钮通过 SwiftUI Link 启动主 App；主 App 录音 + 转录；结果写 App Group 共享容器；键盘读取后用 `textDocumentProxy.insertText()` 插入。**用户感知有 1-2 秒 app switch 延迟**
  - **Share Extension** 模式：在 share 菜单里转录；适合"长录音转笔记"，不适合短输入
  - **App Intents / Siri Shortcuts** 模式：用户配置好后说"嘿 Siri，用 XX 听写" 触发；适合 power user
- → **iOS 端推荐策略**：
  - 兜底：用户走系统 Dictation（方案一）
  - 进阶：自家 App + 自定义键盘扩展 + host-app 模式（参考 Wave / Wispr Flow 的实现）—— 这是**长期可选客户端外壳的合理路径**
  - 桌面端覆盖 Mac（方案五）

### 2.6 关键模型选型摘要

> 模型层与统一平台共用；只列**本用例独有的偏好**。

| 子用例 | 偏好 |
|---|---|
| **英文极致 + 实时** | 远程 Deepgram Nova-3（sub-300 ms）|
| **本地 + 实时** | 本地 `voice-stt-live`（fork `WhisperLiveKit`，待新建）|
| **中文 + 实时** | 远程 火山豆包 / 阿里云 NLS 流式 |
| **离线优先 + 隐私** | 桌面客户端内嵌 whisper.cpp / WhisperKit（不走集群）|

完整模型清单与 provider 列表见 [`../voice-ai-platform-docs/01_独立模型应用清单与配置层.md`](../voice-ai-platform-docs/01_独立模型应用清单与配置层.md)。

```
[第一阶段 1.5–2.5 月 / 2–3.5 人月]
```

## 六、关键事实（已查证）

- **`speaches` 已上 Olares Market**（v1.0.12），暴露 OpenAI 兼容 STT/TTS endpoint，内置 `faster-whisper-small`（英文）+ `Kokoro-82M` TTS；统一平台第一阶段实际上无需新建任何模型应用即可跑"按一下说话"的最小用例。
- **LarePass 客户端没有任何语音输入相关代码**（Quasar + Vue 3 + Capacitor 7 + Electron 39 单仓库 14 entry）；策略是**不动它**，外部应用通过统一平台核心应用接入。
- **国内可用性**：ModelScope 不登录可直接下 SenseVoice / Paraformer；HuggingFace 走 hf-mirror.com 兜底；Whisper / Parakeet / Voxtral 均能在国内一致拉到。
- **Android 推荐路径是方案三 + RecognitionService**，最佳样板是 FUTO 的 `voice-input` APK。
- **桌面端 fork 基线**：`Handy`（**22.2k★**、MIT、Tauri 2 + Rust + whisper-rs + **transcribe-rs（Parakeet V3）**+ Silero VAD，工程最干净；v0.8.3 / 2026-04-28）。

## 七、与 Olares Team 应对齐的事项

1. **LarePass Service Provider SDK 时间表** —— 第三阶段桌面/移动客户端"自动发现集群核心应用"的硬依赖
2. **`whisperwebuiv2` 现役维护节奏** —— 不直接影响本课题；统一平台已锁定"短期借力 + 长期解耦，本平台不在其上扩展任何新功能"，最终是否长期保留由 Olares Team 决定
3. **Olares Market 上架对带 Attribution 模型的态度**（Parakeet TDT v3 CC-BY-4.0）—— 决定是否纳入本地 STT
4. **Olares Mobile / LarePass 移动端的 IME / Autofill 现状** —— 影响 Android 方案三的实测路径
5. **集群侧 GPU 资源池现状** —— 影响本地 STT 模型应用的资源需求设定

完整 10 项沟通点见 `09_风险与开放问题.md` §十。

## 八、一行结论

> **"语音输入法"不再是一个独立产品，而是统一语音 AI 平台的 3 个 API 用例**（流式 STT / 实时听写 / 会议实时段）。其客户端形态（桌面 fork Handy / Android RecognitionService）作为统一平台第三阶段的客户端外壳交付；iOS 走系统 Dictation 兜底；完整自研 IME 不做。**第一 + 第二阶段（5.5–9.5 人月、4–6.5 个月）就能让用户在浏览器里完成本课题的核心场景**；客户端外壳是长期路线。
