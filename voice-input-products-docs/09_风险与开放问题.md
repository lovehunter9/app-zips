## 二、法律与许可证风险（5 条）

### Parakeet 系列 CC‑BY‑4.0 Attribution 要求

- **影响 H / 概率 M**
- 描述：NVIDIA Parakeet 全家族（TDT v2/v3、Flash 120M）权重 CC‑BY‑4.0，要求**保留 NVIDIA 作为原作者的署名**。Olares Market 应用 + 方案五 客户端 UI + LarePass 装包页面均需显式标注。
- 缓解：在 OlaresManifest `license` 字段 + 方案五 客户端"关于"页 + Olares Market 介绍页统一展示 attribution；做一份《模型版权与署名规范》写入 Olares 上架审核流程。
- 监测：上架前自查清单；用户投诉率 < 1%。

### Cohere Transcribe 本地部署许可不友好

- **影响 H / 概率 L**（仅在尝试做 Cohere 本地服务端时触发）
- 描述：FluidVoice 用的是 Cohere CoreML 客户端版（被 Cohere 默许的"客户端使用"），如果 Olares 想把 Cohere 模型部署到 方案四 集群侧供多用户共享，**需先咨询 Cohere 商业 SaaS 协议**。
- 缓解：长期阶段默认**不部署 Cohere 到 方案四**；如未来要做，先走法务咨询。
- 监测：选型阶段是否有人提议"加 Cohere"——一旦提议立即上报法务。

### FluidVoice 许可证从 BSL → AGPL 的反复风险

- **影响 M / 概率 M**
- 描述：FluidVoice 历史上经历过 BSL → AGPL → 改回 BSL 的反复，**fork 它做 Olares 桌面客户端有潜在风险**。
- 缓解：不 fork FluidVoice；方案五（完整版）推荐 **fork Handy（稳定 MIT）**。
- 监测：跟踪 FluidVoice GitHub License 变更。

### AGPL 传染性（Voquill 等）

- **影响 M / 概率 L**
- 描述：Voquill 是 AGPLv3，若 方案五 客户端 fork Voquill，整个 方案五 产品要 AGPL；这对 Olares 商业化（如 Pro 付费版）有限制。
- 缓解：方案五 fork **MIT/Apache‑2 项目优先**（Handy / Type4Me / Whisperboard 都 OK）。
- 监测：fork 前过一遍 License Compatibility。

### 模型权重二次分发的法律真空

- **影响 M / 概率 L**
- 描述：Olares 在 hostPath PVC 内"代用户下载"模型，**严格来说算二次分发**。多数开源模型（Whisper MIT、SenseVoice Apache‑2）无此问题；但若用 Mistral Voxtral / NVIDIA Parakeet 等带 attribution / 商业条款的，部分国家/地区可能算 "redistribution"。
- 缓解：默认让用户**自己拉**（initContainer 直接调 HuggingFace / ModelScope，不预包入 Olares 镜像）；speaches 已是这套做法，沿用。
- 监测：选型时核对每个模型许可证 "redistribution clause"。

## 三、模型生态风险（5 条）

### 上游 Whisper 大版本变化

- **影响 M / 概率 H**
- 描述：OpenAI 每 6‑12 个月发新 Whisper（v3→v3-turbo→未来 v4）；GGML / CoreML / CTranslate2 适配滞后 1‑2 个月；方案四 升级窗有空档期。
- 缓解：speaches `SPEACHES_WHISPER_MODEL` 可动态切换，OlaresManifest 升级时同步发新默认；保留旧版本至少 2 个 minor。
- 监测：HuggingFace `openai/whisper-*` releases 订阅；speaches 上游 commits。

### SenseVoice / Paraformer 路线被阿里抛弃

- **影响 H / 概率 L**
- 描述：阿里 FunAudioLLM 团队组织变动可能导致维护停滞；类似 ESPnet 当年的情况。
- 缓解：sherpa-onnx 已经 vendor 了模型 + 推理代码，即使阿里上游不更新，Olares 仍可用；同时观察 Qwen3-ASR 是否会替换。
- 监测：FunAudioLLM GitHub 活跃度 + ModelScope 维护状态。

### Cohere / OpenAI / Anthropic 提价或限流

- **影响 M / 概率 M**
- 描述：方案五 BYOK 用户依赖云 API，价格变动 / 国家限流可能让用户跑路。
- 缓解：方案五 默认推荐 方案四 本地集群优先；BYOK 仅作可选。
- 监测：定期复审云 API 定价 / 区域可用性。

### MLX / WhisperKit / FluidAudio 上游 fork 分裂

- **影响 L / 概率 M**
- 描述：Apple Silicon 生态有 3 个并行栈（Apple SpeechAnalyzer / WhisperKit / MLX），fork 风险高。
- 缓解：方案五 桌面客户端用 Tauri Rust（whisper-rs）作为本地引擎主路径，避开 Apple 生态分裂；mac 用户优先连 方案四 而非本地。
- 监测：Apple SpeechAnalyzer 在 macOS 26+ 的实际推广速度。

### Voxtral / Granite / GLM-ASR 等新模型实际质量不达预期

- **影响 L / 概率 M**
- 描述：纸面参数好不代表真实可用；这些 2025 年新模型尚无大规模生产验证。
- 缓解：长期阶段 才考虑；上之前先做 PoC（如 ASR 准确率对比 SenseVoice/Whisper-large-v3）。
- 监测：Hugging Face downloads + 开源社区 benchmark。

## 四、平台政策风险（6 条）

### Google Play 个人开发者 2026/2027 实名 + 持续维护要求

- **影响 H / 概率 H**
- 描述：Google 已宣布 2026/2027 起对个人开发者要求实名验证 + 持续应用维护；开源 IME 类应用很难满足。
- 缓解：方案二 / 方案三 APK **不上 Google Play**；走 F-Droid + LarePass 二维码 + Olares 自家市场。
- 监测：Google Play 政策公告（每季度）。

### Apple iOS 第三方键盘无麦权限

- **影响 H / 概率 H**（已确认）
- 描述：Apple 政策硬约束；方案二/方案三 在 iOS 完全不可行。
- 缓解：iOS 用户仅 方案一（Apple 系统）+ 方案五（桌面端覆盖）；接受。
- 监测：每年 WWDC 关注 iOS 政策有无松动（极小概率）。

### Apple Notarization 流程

- **影响 M / 概率 H**
- 描述：方案五 macOS 客户端需 Apple Developer ID + Notarization；不签会被 Gatekeeper 拦。
- 缓解：中期阶段 启动时同步申请 Olares 自家 Developer ID（如已有则复用）；走 Homebrew Cask 作 fallback 分发。
- 监测：Apple Developer 政策变化。

### HarmonyOS NEXT（纯血鸿蒙）不兼容 Android

- **影响 M / 概率 M**
- 描述：2026‑05 时 HarmonyOS NEXT 渗透率仍低（< 5% 华为手机），但 2027‑2028 可能反超；纯血鸿蒙不跑 Android APK。
- 缓解：方案二/方案三 暂不考虑 HarmonyOS NEXT 适配；等 HarmonyOS Voice IME 生态成型再评估。
- 监测：HarmonyOS NEXT 装机率 + 是否有"通用 IME API"。

### F-Droid 上架 reproducible build 要求

- **影响 L / 概率 M**
- 描述：F-Droid 要求所有依赖可从开源源拉取、构建过程可复现；Tauri Rust 应用 + Android Kotlin 应用做 reproducible build 需特别配置。
- 缓解：参考 WhisperIME / FUTO Keyboard 的 F-Droid 上架经验；预留 1 周做 reproducible build 调试。
- 监测：F-Droid build server 状态。

### 国内 Android 应用商店（华为/小米/OPPO/vivo）对开源 IME 不友好

- **影响 M / 概率 H**
- 描述：上架审核要求企业资质、隐私评估、麦克风权限说明；多数开源 IME 难通过。
- 缓解：不依赖国内应用商店；走 LarePass 二维码 + Olares 自家市场 + F-Droid（虽然 F-Droid 在国内访问受限，但可镜像）。
- 监测：国内应用商店政策变化。

## 五、工程复杂度风险（6 条）

### LarePass Service Provider SDK 不存在或形态不合

- **影响 H / 概率 H** ★ **当前最大不确定项**
- 描述：方案二/方案三/方案五 三条路径都依赖此 SDK 自动发现 方案四 sharedEntrance；如果 LarePass 没有 / 不愿做，客户端要么硬编码（脆弱）要么解析 LarePass 本地配置文件（不优雅）。
- 缓解：立项第一周与 LarePass team 对齐；如果 LarePass team 无资源，**建议先做"adapter daemon"（方案五（轻量版））暴露 HTTP loopback** —— 这把 SDK 问题降级为 "客户端 → loopback URL 的简单 HTTP 调用"。
- 监测：立项后 2 周内必须有 LarePass team 的明确答复。

### Olares K8s Helm chart 调试复杂

- **影响 M / 概率 M**
- 描述：Olares 自定义了 charts 模板（GPU 注入 / sharedEntrance / clusterScoped），新人需要 2‑3 周学习。
- 缓解：照抄 `speaches/` 这套 chart，大改避免；招进时 onboarding 加 K8s + Olares 双重培训。
- 监测：Chart Lint + 部署成功率。

### sherpa-onnx + speaches 集成的"执行器抽象"不一定干净

- **影响 M / 概率 M**
- 描述：speaches 的 `executors/` 目录设计是否能让 sherpa-onnx 自然挂上 —— 没真正读过代码不能下结论。
- 缓解：立项第一周做 PoC，~200 行 Python 验证；如果发现 speaches 抽象不友好，转 中期阶段 方案 B（独立 olares-funasr）。
- 监测：PoC 跑通时间。

### Tauri 2.x 在 Linux Wayland 下文本注入不稳定

- **影响 L / 概率 M**
- 描述：方案五（完整版） 桌面 Linux 版要在 Wayland 下用 ydotool / wtype；现有项目（hyprwhspr）需要用户手动配 input group，体验差。
- 缓解：Linux 版优先 X11；Wayland 提供"半自动配 ydotool"脚本。
- 监测：Linux 用户反馈 + Tauri 跨平台 issue。

### speaches 上游升级与 fork 维护负担

- **影响 M / 概率 M**
- 描述：方案四 中期阶段 fork speaches 加 sherpa-onnx 后，speaches 每升级一版（如 0.9.x）需要 rebase。
- 缓解：fork 时把 sherpa-onnx 加在独立目录 `executors/sherpa_onnx/`，patch 文件最少化；建立月度 rebase 节奏。
- 监测：speaches 上游 commit 频率。

### CapsWriter Server K8s 部署的隐性踩坑

- **影响 L / 概率 M**
- 描述：虽然 `multiprocessing.Process` 在 K8s pod 内行为正常，但 CapsWriter v2.3 引入 RAG/LLM 后状态机更复杂；可能有未爆雷。
- 缓解：中期阶段 方案 A 不依赖 CapsWriter Server；只有走方案 B 才有此风险。长期阶段 如选方案 B，需 1‑2 周做完整集群测试。
- 监测：CapsWriter Server 在 K8s pod 内的崩溃率。

## 六、用户体验风险（4 条）

### speaches 默认 faster-whisper-small 中文体验差

- **影响 M / 概率 H**（已知）
- 描述：短期阶段 直接复用 speaches，但 small 模型中文准确率约 70‑80%；用户体验"speaches 不能用"。
- 缓解：文档里强调"中文用户先改 `SPEACHES_WHISPER_MODEL=Systran/faster-whisper-large-v3`"；中期阶段 上线后 speaches-ext 默认 SenseVoice/Paraformer。
- 监测：用户投诉率 + speaches Olares Market 评分。

### 方案五（完整版）客户端首启引导冗长

- **影响 L / 概率 M**
- 描述：连 LarePass + 选引擎 + 设热键 + 下模型，新手容易劝退。
- 缓解：默认配置一键完成（LarePass 已运行 → 自动连 → 选 RemoteSpeaches → 设默认 Ctrl+Shift+; → 不下任何本地模型）；高级用户进 Settings 自调。
- 监测：用户首启完成率 ≥ 80%。

### 模型首启下载耗时（5‑30 分钟）

- **影响 M / 概率 H**
- 描述：speaches initContainer 首次拉 large-v3（~3 GB）+ SenseVoice（~228 MB）+ Kokoro（~80 MB）在国内带宽下可能 10‑30 分钟；用户感知"装完不能用"。
- 缓解：speaches UI 显示进度条；首启前先把模型 push 到 Olares 应用打包内或 CDN 镜像（**与 Olares Market 团队对齐**）；ModelScope 直连可显著缩短中文模型下载时间。
- 监测：用户从"安装完成"到"第一次成功调用"的中位时间 ≤ 5 分钟。

### 方案三 RecognitionService 与 Gboard 配合时的语种 / 标点行为不一致

- **影响 L / 概率 M**
- 描述：Gboard 接收 RecognitionService 结果后会做二次处理（自动标点 / 大小写），可能与 方案四 后端的处理结果有偏差。
- 缓解：实测覆盖 Gboard / Samsung Keyboard / FUTO / HeliBoard 主流，文档列已知差异。
- 监测：用户反馈"识别出来标点不对" issue 数。

## 七、国内特殊风险（5 条）

### HuggingFace 国内不可达

- **影响 H / 概率 H**（已知）
- 描述：speaches 默认从 HF 拉模型，国内用户首启失败。
- 缓解：speaches-ext 默认 `HF_ENDPOINT=https://hf-mirror.com`；用户文档说明此环境变量可改。
- 监测：speaches 首启成功率（国内 IP 段）。

### ModelScope CDN 速率与稳定性

- **影响 M / 概率 L**
- 描述：ModelScope 总体稳定，但偶尔有限速；SenseVoice 模型 228 MB 通常 1‑5 分钟下完。
- 缓解：Olares Market 服务器可加 ModelScope 镜像（如允许）；hostPath PVC 复用避免重复下载。
- 监测：用户首启耗时统计。

### 国内云 API（火山/阿里）的稳定性

- **影响 L / 概率 M**
- 描述：方案五 客户端如果用国内云 API 作 fallback，遇到云厂商限流 / 改协议风险。
- 缓解：方案五 默认 方案四 本地优先；BYOK 给用户选。
- 监测：客户端 BYOK 失败率。

### Olares 在国内的合规

- **影响 H / 概率 L**
- 描述：Olares 自身在国内的运营合规（ICP 备案 / 算法备案）会传染到所有应用，包括 ASR；ASR 类应用 2024 起有"生成式 AI 备案"要求。
- 缓解：与 Olares 法务对齐；如属重大问题，可能影响整体上线时机。
- 监测：CAC 算法备案政策。

### F-Droid 在国内访问受限

- **影响 M / 概率 M**
- 描述：F-Droid 主站 + 应用安装通常需要 VPN；国内用户难以直接装。
- 缓解：Olares 自家镜像一份 F-Droid 仓（已知 Olares 有 CDN）；或走 LarePass 二维码直接下 APK（绕过 F-Droid）。
- 监测：国内用户 APK 下载渠道占比。

## 八、商业 / 战略风险（4 条）

### speaches 与 whisperwebuiv2 / 其他 Olares 同方向应用重叠

> **⚠️ 此风险已被统一平台决策覆盖**：现已锁定"短期借力 + 长期解耦，本平台不在 whisperwebuiv2 上扩展任何新功能；自家 ASR 应用矩阵（`voice-stt-pro` / `voice-stt-zh` / `voice-stt-live`）独立规划"。最新版本见 [`../voice-ai-platform-docs/04_风险与开放问题.md`](../voice-ai-platform-docs/04_风险与开放问题.md) §三 Risk 14。

- **影响 M / 概率 H**（历史评估）
- 描述：工作区已有 `whisperwebuiv2` 1.0.4‑1.0.19 多版本，与 speaches 都是 ASR；是否合并 / 替代 / 平行存在没明确。
- 缓解：客户端设计末节 已列；立项前与 whisperwebuiv2 团队对齐。
- 监测：内部产品规划会议结论。

### Olares Mobile 产品节奏未明

- **影响 M / 概率 M**
- 描述：方案二/方案三 APK 分发是否依赖 Olares Mobile（独立产品线）？如果 Olares Mobile 优先做"系统级 IME 集成"，方案二/方案三 可能重复造轮。
- 缓解：与 Olares Mobile team 对齐；如果有 Olares Mobile 优先做 方案二，本课题侧只做 方案三。
- 监测：内部 roadmap 同步。

### "语音输入"是否进 Olares 主路线

- **影响 M / 概率 L**
- 描述：如果 Olares 主路线只想做 "personal cloud OS"，语音输入可能被定性为"应用商店中的某类应用"而不是核心能力，资源投入受限。
- 缓解：本课题先按"侧翼能力"立项，资源不强求；方案四 短期阶段 已经"零工程"，先把现状文档化；后续看用户反馈再扩。
- 监测：业务方拍板态度。

### 商业化路径不清

- **影响 L / 概率 M**
- 描述：自研客户端 / Olares Market 应用是否有付费档？是否有 Olares Pro 加值能力？不清晰会影响投入意愿。
- 缓解：本课题不绑商业化；按"开源 + Olares 生态促进"路线推进；商业化路径留给业务方。
- 监测：—

## 九、实测缺口（3 条，对应 客户端设计末节 L‑*）

> 这些不是"风险"严格意义，而是"如果不补就有未知大小风险"。

### speaches + sherpa-onnx PoC 未跑

### ModelScope 在普通家庭带宽下的实际拉取速率

- 描述：未实测；估算 1‑5 分钟下完 SenseVoice，但实际可能更慢。
- 缓解：立项前找 5 个国内不同运营商网络实测一次。

## 十三、章节小结

1. **最大风险 = LarePass Service Provider SDK 不到位**：影响 方案二/方案三/方案五 三条客户端路径。立项第一周必须与 LarePass team 对齐。
2. **强烈推荐风险缓解动作 = 立项第一周做 PoC**（：speaches+sherpa-onnx；：ModelScope 实测）：可化解 70% 的工程不确定性。
3. **Apple iOS 无解约束已确认**，接受为产品边界。
4. **国内分发不依赖 Google Play 已是事实，走 F-Droid + LarePass 二维码 + Olares 市场三轨**。
5. **speaches 与 whisperwebuiv2 重叠是商业层最需要先解决的事**：建议立项前的产品规划会议必须先决策。
6. **Cohere / Voxtral / Parakeet 三个模型法律性各有约束**，长期阶段 才考虑且需逐一审。
7. **可接受的"模糊地带"**：Olares Mobile / 商业化路径 / 合规细则——这些不需 短期阶段 拍板，但 中期阶段/3 之前需明确。
