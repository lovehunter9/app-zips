## 三、按维度展开

### 3.1 D1 进程模型 / Shell 框架

把 重点分析项目 按 Shell 框架归类得到 **五大派系**：

| 派系 | 项目 | 代表特征 | 适合场景 |
|---|---|---|---|
| **A. Tauri 2 (Rust + TS/React)** | Voquill Voquill、Handy Handy | Rust 后端 + Web 前端，**单二进制 + Web 渲染**；产物约 10–30 MB（不含模型）；可一份代码 Bundler 出 macOS/Win/Linux | 想要"小体积、跨桌面、Rust 安全性"且团队前端实力强 |
| **B. macOS Swift 原生** | Type4Me Type4Me（SPM）、VoiceInk VoiceInk、FluidVoice FluidVoice、Whisperboard Whisperboard（Tuist） | 直接 SwiftUI + AppKit；与 macOS/iOS 系统服务（Accessibility / Keychain / NSPasteboard / NSSpeech / Core ML）原生互操作；Sparkle/AppUpdater 自更新；体验质感最好 | 只做 Apple 平台，追求"质感 + 系统集成 + 性能"的旗舰形态 |
| **C. Python 桌面** | CapsWriter CapsWriter（Tkinter+pyinstaller）、hyprwhspr hyprwhspr（GTK4/PyGObject + systemd） | 起步快、模型生态最全（sherpa-onnx / faster-whisper / pywhispercpp / onnx-asr / FunASR）；分发靠 PyInstaller 单 exe 或 Linux 包管理器 | 中文社区（CapsWriter 圈）+ Linux 重度用户；体积大但功能最全 |
| **D. Android IME** | WhisperIME WhisperIME | `InputMethodService` + `RecognitionService` 同 APK 双形态；F‑Droid 上架；TFLite 推理 | Android 用户的唯一通用形态（详 方案二 / 方案三） |
| **E. Hybrid / Mobile-first** | Voquill Voquill（Flutter mobile + Tauri desktop） | 同时铺设桌面 + 移动 + Web；shared `packages/types` 在 TS 与各端共享 | 想做"全家桶"产品形态 |

> 我们的样本里**没有一家**走纯 Electron 路线，连"半 Electron 半 Swift"的也没有。横向对比项目 里只有 `OpenWhispr`、`Buzz` 部分形态用了 Electron——这是 2025‑2026 这波 AI 语音输入工具的明显技术风向：**Tauri 已经把 Electron 在这个细分品类挤出去**，因为 Whisper/Parakeet 这类本地推理对内存与启动时间敏感，Electron 的 Chromium 加载根本拼不过 Tauri 的 webview 复用。`[中]`

### 3.2 D2 音频采集

| 项目 | 采集库 | 采样率 / 格式 | 缓冲策略 |
|---|---|---|---|
| Type4Me | AVAudioEngine | 16 kHz mono PCM16-LE | 200 ms chunks (6400 B)；首 6400 samples 丢弃以避开起始音效 `[高]` |
| Voquill | `cpal` (推断) | 16 kHz `[推测]` | — |
| Handy | `cpal` 0.16 + `rubato` 0.16 重采样 + `hound` WAV writer | 16 kHz | 通过 `vad-rs` Silero v4 后处理 `[高]` |
| VoiceInk | AVAudioEngine | 16 kHz `[推测]` | — |
| FluidVoice | AVAudioEngine | 16 kHz `[推测]` | — |
| CapsWriter | `sounddevice` callback → `asyncio.Queue` | 16 kHz | Client 直接流式上传到 Server；Server 按时间切片（60 s 段 + 4 s 重叠）`[高]` |
| hyprwhspr | `sounddevice` + `pulsectl`（音频路由） + `pyudev`（设备热插拔） | 16 kHz `[中]` | 录音时支持系统音量 ducking |
| WhisperIME | Android `AudioRecord` | 16 kHz mono | 30 s 上限（Whisper 单次推理窗口）`[高]` |
| Whisperboard | AudioKit + AVAudioEngine | iOS 系统默认 `[中]` | 长录音 + ShareExtension 接收外部音频 |

**横向总结**：
- **桌面 Apple 系**清一色 AVAudioEngine；**Rust 系**清一色 `cpal`；**Python 系**清一色 `sounddevice`；**Android** 用 `AudioRecord`。这是事实上的"语种 → 采集库"硬绑定。
- 几乎所有项目都把音频归一化到 **16 kHz mono PCM**（Whisper / SenseVoice / Parakeet 等模型的通用输入格式）；说明"采集层"在所有竞品里高度同构、不存在差异化竞争。
- Handy 在 `cpal` 之上手写 `rubato` 重采样，原因是 `cpal` 不能保证麦克风给出 16 kHz——需要自己降采样。其他项目（Python / Swift）依赖系统/库帮忙。
- Type4Me 的"丢弃首 6400 samples"是细节中的工程经验：录音起始音效（"ding"）会让 ASR 首字误识别。这种经验只有真做过的人才会写在 `CLAUDE.md` 里。`[高]`

### 3.3 D3 文本注入

| 项目 | 注入手段 | 局限 |
|---|---|---|
| Type4Me | **剪贴板 + Cmd+V**（保存/恢复原剪贴板）`[高]` | macOS 通用，但有 1 帧的剪贴板污染窗口 |
| Voquill | Rust `enigo` 等 `[推测]`；桌面 Tauri 通过 Rust 调系统输入 | — |
| Handy | `enigo` 0.6.1 模拟键盘 + Tauri clipboard plugin `[高]` | enigo 在 Wayland 上需要 ydotool 兼容层 |
| VoiceInk | Accessibility API + NSPasteboard `[中]` | 需 Accessibility 权限 |
| FluidVoice | macOS Accessibility + NSPasteboard `[中]` | 需 Accessibility 权限 |
| CapsWriter | Python `keyboard` / `pynput` 模拟键入 + 剪贴板 + Toast UI 二选 `[中]` | 中文 IME 状态下键入可能错位（已知社区 issue）`[中]` |
| hyprwhspr | `ydotool` user service（systemd 起）+ `pyperclip` | 需开 ydotool；Wayland 唯一干净方案 |
| WhisperIME | Android `InputMethodService.currentInputConnection.commitText()` | IME 原生路径，无需权限 |
| Whisperboard | UIPasteboard / Share Sheet | iOS 受沙箱限制，**无法系统级注入**——只能用户手动粘贴或导出转录文件 |

**横向总结**：
- 注入手段是"平台天花板"：
  - **macOS**：Accessibility（VoiceInk/FluidVoice 选）vs 剪贴板模拟粘贴（Type4Me/Handy 选）—— Accessibility 体验更好但触发系统警告；剪贴板更兼容但有污染。
  - **Linux Wayland**：必须 ydotool / wtype 之一，没有第三条路（hyprwhspr 选 ydotool）。
  - **iOS**：**根本没有系统级注入**——这是 方案一/方案二/方案三 在 iOS 上不成立的根本原因，Whisperboard 也只能"录完手动粘贴"，不是真正的"语音输入法"。`[高]`
  - **Android IME**：`InputConnection` 是最干净的协议——这也是 方案二 选 IME 形态的根本理由。
- **重点分析项目 没有任何项目能真正在 iOS 上做"系统级语音输入"**——`Aiko`、Whisperboard 都只是"录音 → 转录 → 复制"，不是 typing。这进一步证实 §02 §八 的判断："命题 B 在 iOS 上事实上只有 方案五 桌面端覆盖。"

### 3.5 D5 VAD（语音活动检测）

| 项目 | VAD | 集成方式 |
|---|---|---|
| Type4Me | sherpa-onnx 内置 VAD（fsmn-vad / Silero）`[中]` | SenseVoice 引擎自带管线 |
| Voquill | `vad-rs` 或引擎内置 `[推测]` | — |
| Handy | **Silero VAD v4**（`vad-rs` Rust 绑定，模型 `silero_vad_v4.onnx`，部署期 curl 下载）`[高]` | 录音 → cpal → rubato 重采样 → Silero VAD 静音剪除 → Whisper |
| VoiceInk | 引擎内置或自研 `[推测]` | — |
| FluidVoice | 引擎内置 `[推测]` | — |
| CapsWriter | **禁用 VAD**（作者主动选）`[高]` | 按时间切片（60 s 段 + 4 s 重叠），完整上下文保留，避免 VAD 切错位 |
| hyprwhspr | whisper.cpp / Parakeet 引擎内置 `[推测]` | — |
| WhisperIME | **Android-VAD**（gkonovalov）`[高]` | 自动模式下做静音切断 |

- VAD 选型几乎被 **Silero VAD** 一统天下（Handy、Voquill、Type4Me/sherpa 中、hyprwhspr 间接）；中文圈历史用 fsmn-vad，但 sherpa-onnx 已经把两者打包。

- Android 用 `gkonovalov/android-vad`（社区维护，MIT，封装 WebRTC VAD），不是 Silero——因为 TFLite 集成成本高且模型大。`[高]`

### 3.6 D6 推理引擎集成方式

把项目按"推理形态"分四档：

| 形态 | 项目 | 特点 |
|---|---|---|
| **F1 端侧 in-proc**（同进程内 FFI） | Handy（`transcribe-rs` Rust binding），VoiceInk（whisper.cpp xcframework），FluidVoice（SwiftWhisper + FluidAudio），WhisperIME（TFLite），Whisperboard（WhisperKit） | 启动快、延迟低、没有 IPC 开销；模型必须随 App 分发或首启下载 |
| **F2 端侧外挂子进程**（自管 Python） | Type4Me 的 Qwen3-ASR（Python WebSocket on MLX） + SenseVoice（同样 Python WebSocket） | Swift 主进程 + `SenseVoiceServerManager` 起 Python 子进程，端口动态分配，PID 保存以便重启 |
| **F3 本地 HTTP/WS 服务**（C/S 同机或局域网） | CapsWriter（Client/Server 严格分离，WebSocket binary，base64 chunks，Server 端再用 `multiprocessing.Process` 隔离推理），hyprwhspr 可选 REST/WS 后端 | 可让推理跑在另一台 GPU 机器；CapsWriter 还允许多 Client 共用一个 Server |
| **F4 纯远端 API** | Type4Me 8 家云、Handy 也支持 BYOK云、hyprwhspr 多家云、Voquill BYOK 云 | OpenAI / Deepgram / AssemblyAI / ElevenLabs / Volcano / Soniox / Bailian / Baidu / Cohere / Groq / Gemini... |

**核心观察**：
- **F1 是事实标准**——80% 的桌面项目走 in-proc FFI（Swift xcframework / Rust crate / Java JNI），原因是延迟和分发简单。
- **F2 是非常罕见的"妥协形态"**——只有当某个模型只有 Python 实现（如 Qwen3-ASR 的 MLX 实现）时才会选择。Type4Me 的 `SenseVoiceServerManager` 是该形态的最佳工程参考。`[高]`
- **F3 是中文圈传统形态**——CapsWriter 把 C/S 分离做到极致（连 Server 内部都用 `multiprocessing.Process` 隔离推理，避免 GIL 阻塞 WebSocket 心跳），是工程上最干净的设计。这种形态天然适合"Olares 集群部署 Server，桌面/移动端只跑 Client"——也就是我们 方案四 + 方案二/方案三/方案五 联合架构的精确蓝本。`[高]`
- **F4 是最简单的形态，也是商业化必走的形态**——所有项目几乎都支持 BYOK 云模式作为"无 GPU 用户的兜底"。

> 这一节对 方案四 设计的启发：**Olares 集群侧 ASR 后端的最佳参考样本就是 CapsWriter 的 Server 端**（已经把 sherpa-onnx + Paraformer/SenseVoice/FunASR/Qwen-ASR 四引擎统一接入了），下一份 §6 命题 A 报告应当详查它的 protocol、容量隔离、多 Worker 调度。

### 3.7 D7 客户端 / 服务端分离度

把"C/S 分离度"做成 0–3 分量表：

| 分数 | 含义 | 项目 |
|---|---|---|
| **0** 单进程 | 录音 + ASR + 注入全在一个进程 | Handy Handy、VoiceInk VoiceInk、FluidVoice FluidVoice、WhisperIME WhisperIME、Whisperboard Whisperboard |
| **1** 同机子进程 | 主进程 + 自管 Python/native 子进程，进程间 WebSocket | Type4Me Type4Me |
| **2** 同机 C/S（默认本地，可异机） | 真正的 Client + Server，WebSocket 协议；默认 localhost，可改 host | CapsWriter CapsWriter、hyprwhspr hyprwhspr（可选）、Voquill Voquill（部分功能走 Firebase Functions） |
| **3** 远端 ASR + 本地 Glue | 纯客户端 + 远端服务，无本地推理 | (所有项目的 BYOK 云模式) |

**含义**：
- 分数越高，**对应"方案五 LarePass‑aware 第三方桌面客户端"路径的可行性越高**——只要桌面客户端已经支持"自定义 endpoint"，把 baseURL 指到 Olares 共享地址就是 ≤100 行 PR。
- 重点分析项目 中**已经原生支持远端 endpoint 配置**的：Type4Me / Handy（在 settings.rs 31 KB 中有 LLM/Provider 配置）/ hyprwhspr（CLI `hyprwhspr config` 显式支持 REST/WS endpoint）/ CapsWriter（C/S 本来就需要配置 server host）/ Voquill（Provider 抽象层在 enterprise/admin）。**Direction 方案五 落地的最佳候选**就这 5 个。
- WhisperIME / Whisperboard / VoiceInk / FluidVoice 是单进程封闭推理，要让它们走远端要先做架构改造，难度大。

### 3.8 D8 构建与分发

| 项目 | 构建 | 分发 |
|---|---|---|
| Type4Me | `swift build -c release`；自家 `scripts/deploy.sh`；自签证书"Type4Me Local"持久化 macOS 权限 | DMG 直链（GitHub Releases）+ **`updates.json`** 自更新源 |

**横向总结**：
- **桌面 macOS 项目**的事实标准是：Xcode/SPM build → Sparkle/AppUpdater 自更新 → Homebrew Cask 分发（4/5 选）。
- **跨平台 Tauri 项目**事实标准是：Tauri Bundler → GitHub Releases + tauri-plugin-updater；签名各平台一套（macOS 自签 / Windows trusted-signing-cli / Linux 不签）。
- **Linux 项目**走 AUR + systemd user service 是 Arch 社区的强偏好（hyprwhspr）；Debian/Fedora 系靠自家 installer。
- **Android 开源 IME** 唯一可行的分发路径是 **F-Droid**——Google Play 2026/2027 将要求个人开发者实名提交，WhisperIME 已经声明届时退出 Play。这对 方案二/方案三 设计有直接影响：**Olares 自家若做 IME，要么走 F-Droid + 自家 APK 直链，要么按 Google Play 实名合规走 Play 渠道**。`[高]`
- **iOS 项目**只能走 TestFlight + App Store——这意味着 方案二/方案三 在 iOS 上的分发本身就是死路（App Store 审查不允许第三方 IME 注入 dictation/Whisper 服务）。`[中]`

## 四、重点分析项目 单项要点

### Typeless Typeless（macOS，闭源）

公开材料能确认：macOS 菜单栏 App、商业订阅、远端云 ASR + LLM 后处理（GPT-4 风格）；**端侧无模型推理**。其余推断属 `[推测]`。本报告不会基于 Typeless 推断架构事实，只用其作为"商业闭源对照点"。

### Type4Me Type4Me（957★，MIT，macOS Swift）

**最大特点**：双轨架构 + 三档变体编译。

- **双轨架构**：Swift 主进程做 UI/录音/全局热键/凭证存储；Python 子进程跑 Qwen3-ASR（MLX）和 SenseVoice。Swift 用 `SenseVoiceServerManager` 拉起/守护 Python 子进程，WebSocket 通信，动态端口，PID 持久化以优雅关闭。
- **三档变体**：`pure`（云 only）/ `local`（端侧 SenseVoice + Qwen3-ASR）/ `official`（订阅，2026‑04 已 archive）。通过 `Package.swift` 在 manifest 评估期检测 `Frameworks/sherpa-onnx.xcframework/Info.plist` 和 `Type4Me/CloudSubscription/marker` 文件存在与否，动态决定 `HAS_SHERPA_ONNX` / `HAS_CLOUD_SUBSCRIPTION` 编译标志和源文件排除。
- **凭证存储**：混合模式——secure 字段进 macOS Keychain（`com.type4me.grouped` / `com.type4me.scalar`），non-secure 字段进 `~/Library/Application Support/Type4Me/credentials.json`（0600 权限）；首启自动迁移。GUI App 无法读 shell env vars，这是个常见踩坑点。
- **ASR Provider 架构**：`ASRProvider` enum + `ASRProviderConfig` 协议 + `ASRProviderRegistry` 注册表；15 个 provider 槽位中已实现 9 个，6 个仅 config 占位。每个 provider 配置自家 `credentialFields` 用于动态 UI 渲染。**这是所有 重点分析项目 中 Provider 抽象做得最干净的一家**，可作为 §6/§7 设计参考。`[高]`

### Voquill Voquill（938★，AGPL-3，跨 5 端）

**最大特点**：Turborepo monorepo 把 5 端塞进一个仓库。

- 顶层：`apps/desktop`（Tauri）+ `apps/web`（Next.js 静态导出）+ `mobile/`（Flutter）+ `enterprise/gateway` + `enterprise/admin`。
- 架构原则（来自 `AGENTS.md`）："**Rust is the API, TypeScript is the Brain**"——所有业务逻辑在 TS，Rust 只提供 API 能力。状态用 Zustand + Immer。数据流：用户/原生事件 → actions → repos → Tauri commands → SQLite/Whisper/APIs。
- **packages/** 下有 9 个共享包：`agent`、`desktop-native-apis`、`desktop-utils`、`firemix`、`flutter_video_looper`、`functions`、`pricing`、`rust_gtk_pill`、`rust_macos_pill`、`rust_transcription`、`rust_windows_pill`、`types`、`voice-ai` 等。`rust_*_pill` 是各平台原生 overlay UI 组件；`rust_transcription` 是 ASR 核心 Rust crate；`voice-ai` 是 TS 端 AI 业务逻辑。
- **req.txt 文件**显示了一些 Python 辅助脚本依赖（pydantic, httpx, groq SDK），但主线 ASR 在 Rust 端。
- 后端 Firebase Functions（在 `apps/firebase/functions/`，被 pnpm-workspace 收纳），承担 billing/demos。
- Voquill 是 重点分析项目 中**唯一对"跨平台 + 移动端"做了完整工程实践**的样本——值得 §6/§7 的 方案二/方案三 设计直接借鉴它的 "Tauri 桌面 + Flutter 移动" 形态。`[高]`

### Handy（**22.2k★**，MIT，Tauri 2 跨桌面；同时支持 Whisper 和 Parakeet V3）

**最大特点**：Rust 生态最干净的 Tauri 2 样板。

- `Cargo.toml` 包含 tauri 2.10.2、cpal 0.16、vad-rs（cjpais fork）、rdev（rustdesk fork）、`transcribe-rs` 0.3.8（whisper-cpp + onnx，平台条件编译启用 Metal / Vulkan / DirectML）、rubato 0.16、enigo 0.6、hound、rusqlite + rusqlite_migration、tauri-specta（用于 TS 类型自动生成）、handy-keys 0.2.4、ferrous-opencc（简繁转换）。
- 单进程架构：Manager Pattern（Audio/Model/Transcription/History 四个 manager）+ Command-Event Architecture（前端 → invoke → Rust state → 持久化 tauri-plugin-store）。
- 模型管理：首启从 `blob.handy.computer/silero_vad_v4.onnx` 拉 VAD；whisper 模型 small/medium/turbo/large 四档；用户可自选。
- **`patch.crates-io` 改了 tauri-runtime / tauri-runtime-wry / tauri-utils 三个 crate**，指向自家 `cjpais/tauri.git` fork（`handy-2.10.2` 分支）——说明 Tauri 上游对 Handy 的某些需求支持得不够好，作者自维护补丁。这是个**潜在风险**：跟主线脱节后升级困难。`[高]`
- 全局热键：rdev + tauri-plugin-global-shortcut + 自家 handy-keys 0.2.4 crate；push-to-talk 与 toggle 两种模式。
- CLI 参数：`--toggle-transcription`、`--cancel`、`--start-hidden`、`--no-tray`、`--debug` — 通过 `tauri_plugin_single_instance` 把第二个实例当 RPC 客户端使用。这是 Tauri 单实例桌面应用的标准模式。
- **i18n 强制**：ESLint 禁止 JSX 出现硬编码字符串，所有文案走 i18next（en/de/es/fr/ja/ru/zh/...）。这是开源跨地区运营的成熟做法。
- 推理引擎在 `transcribe-rs` 这个独立 crate 里——它本身就是 Tauri 圈"想做语音输入"的项目最经常选用的抽象层。`[高]`

### VoiceInk VoiceInk（4k★，GPL-3，macOS Swift）

**最大特点**：纯原生 + Power Mode（应用感知）+ 不接受 PR 的"作者控制权"路线。

- Xcode `.xcodeproj` 工程；依赖 whisper.cpp + FluidAudio（Parakeet）+ Sparkle + KeyboardShortcuts + LaunchAtLogin + MediaRemoteAdapter + Zip + SelectedTextKit + Swift Atomics。这是 Apple 原生圈"事实标准依赖集"。
- README 明示 "This project is **not accepting pull requests** at this time" —— 作者 Pax 选择"开源但闭门开发"的路线。这对生态影响很关键：**VoiceInk 是参考样板，不是协作样板**。`[高]`
- **Power Mode**：检测当前活跃 App / URL，自动套用预配置的 prompt / 模型——这是 重点分析项目 中最差异化的功能之一，是商业产品才舍得做的细节。
- 商业模式：源码开放但 binary 收费（tryvoiceink.com）；Homebrew Cask 也是。这是"双轨开源"的典型形态。

### FluidVoice FluidVoice（GPL-3，macOS）

**最大特点**：6 引擎并列 + **Cohere Transcribe 在客户端的稀有 CoreML 集成**。

- `Package.swift` 依赖 6 个 SwiftPM 包：AppUpdater（mxcl，自更新）/ **FluidAudio**（自家 fork `B/cohere-coreml-asr` 分支，承载 Parakeet + Cohere CoreML）/ PromiseKit / DynamicNotchKit（Mac Notch overlay 渲染）/ SwiftWhisper（whisper.cpp Swift 绑定）/ PostHog（telemetry，可关）。
- 6 模型并列：**Parakeet Flash（120M，~250 MB，最低延迟，英文 only）** / Parakeet TDT v3（25 语种，~500 MB）/ Parakeet TDT v2（英文 only，最快） / Cohere Transcribe（14 语种，~1.4 GB） / Apple Speech（零下载，系统原生） / Whisper Tiny→Large（99 语种，~75 MB ~ 2.9 GB，含 Intel Mac 支持）。
- 用 `DynamicNotchKit` 在 MacBook Notch 区域渲染 overlay 是 2025 macOS 设计风潮之一——比 SwiftUI 自建 panel 更原生。
- **License 历史变更**：2026-02-23 前 Apache-2.0，之后 GPLv3——这是 fork 时的合法性边界，需要注意。`[高]`

### CapsWriter CapsWriter‑Offline（中文圈，Python，C/S）

**最大特点**：业界最干净的 C/S 分离 + RAG 热词 + LLM Agent。

- "**快、准、稳、离线**" 四字方针；C/S 架构：Server 主进程跑 WebSocket，**`multiprocessing.Process` 子进程跑推理**（避免 GIL 阻塞心跳）；Client 轻量启动，做全局热键 + 录音 + UI（Tkinter Toast）+ LLM Agent。
- **核心源码全保留在发行版**（`core/` 目录），用户可改——这是中文桌面开源工具的"传统美德"。
- ASR 引擎四档可切（ParaformerEngine / SenseVoiceEngine / FunASREngine 的 GGUF 版本 / QwenASREngine 的 GGUF 版本），通过 `EngineCapabilities` 标志位（`ASR` / `PUNC` / `TIMESTAMPS` / `STREAMING` / `HOTWORDS`）声明能力；`ModelLoader` 智能补丁（缺 PUNC 就外挂 Punct-CT-Transformer，缺 TIMESTAMPS 就外挂 QwenForceAligner）。**这是 重点分析项目 最完善的引擎能力检测设计**。`[高]`
- **音素 RAG 热词**：`hot.txt` 统一中英文热词，两阶段检索（FastRAG 倒排索引 + Numba JIT 粗筛 → AccuRAG 模糊音权重精确匹配），双阈值（0.85 用于替换，0.6 用于 LLM 上下文参考）。`hot-rule.txt` 正则替换。**这是中文圈对"专有名词识别"的成熟方案，西方圈普遍不及**。`[高]`
- LLM Agent 系统：模块化 `LLM/*.py`，每个文件一个角色（default / 翻译 / 高级翻译 / 大助理 / 小助理 / ...）；`watchdog` 文件监视器 3 秒防抖热重载；角色触发靠识别结果前缀（"翻译"、"助理"）；Context 组装支持热词 + 选中文字（模拟 Ctrl+C 抓鼠标选中）+ 历史。
- UDP 广播 / 远程控制 / 历史归档（按日期 Markdown）—— 中文工具典型的"功能极大化"风格。
- 用户偏好显式声明"中文优先"——这是中文开源圈的礼貌。
- **方案四 设计的最佳直接借鉴对象**：CapsWriter Server 端本身就可以**几乎不改地**部署到 Olares 集群里（接 sharedEntrances + 改默认端口），让 重点分析项目 / 横向对比项目 中所有"支持自定义 server host"的 Client 直接接进来。`[高]`

### hyprwhspr hyprwhspr（1k★，MIT，Linux Wayland）

**最大特点**：Linux/Wayland 标杆 + AUR 一键安装 + Waybar 集成 + 多引擎可挂。

- Python + `pywhispercpp` 1.4.1 + `sounddevice` + `evdev` + `pyperclip` + GTK4 可视化 + dbus-python + pulsectl + pyudev + `elevenlabs` Python SDK + `rich`（CLI 格式化）。
- 后端可切：whisper.cpp（默认本地）/ Cohere / Parakeet (`onnx-asr`) / 自定义 REST / 自定义 Realtime WebSocket / Gemini / ElevenLabs—— 6 种后端在同一份 CLI 配置里切换。
- 分发：AUR (`yay -S hyprwhspr` 或 `hyprwhspr-git`)；非 Arch 走 `install-deps.sh`；systemd user service + ydotool user service。
- **重点是它把 Wayland 上做"全局语音输入"这件事**变得像 Windows 上的 Dragon 一样傻瓜——前面这件事其实超过 5 年没有令人满意的开源方案，hyprwhspr 是当下最完整的答案。`[高]`

### WhisperIME WhisperIME（559★，MIT，Android）

**最大特点**：Android 端唯一**纯开源 + IME + RecognitionService 双形态**。

- Gradle 工程，单 APK 同时实现 `InputMethodService`（IME 形态）和 `RecognitionService`（被 HeliBoard 等其他 IME 调用）—— **这就是 方案二 + 方案三 同时落地的样板**。
- 引擎：**TFLite Whisper**（不是 whisper.cpp），两档可选——英文 only 小模型（速度）vs 多语种大模型（覆盖）。模型 ~435 MB 首启从 Hugging Face `DocWolle/whisper_tflite_models` 下载，**全离线运行**。
- VAD：`gkonovalov/android-vad`（社区，MIT）。
- 中文简繁转换：`Opencc4j`（Apache-2.0）。
- 30 s 录音上限——Whisper 单次推理窗口的硬约束。
- **关键 README 警告**：Google 2026/2027 强制个人开发者向 Google 提交个人身份；作者明确表示不会接受，**届时 Play 商店版本会停服**。这意味着如果 Olares 要做 IME，要么自己实名上 Play，要么走 F-Droid + 直链 APK。`[高]`
- **方案三 RecognitionService 的设置 trick**：如果用户在系统设置看不到 WhisperIME 作为可选 voice input（只有 Google/Samsung 硬编码），需要 `adb shell settings put secure voice_recognition_service org.woheller69.whisper/com.whispertflite.WhisperRecognitionService`——这是 方案三 在国内 ROM 兼容性评估时要重点测的踩坑点。`[高]`

### Whisperboard Whisperboard（1k★，GPL-3，iOS SwiftUI + TCA）

**最大特点**：iOS 端唯一活跃开源 + Tuist + TCA 全家桶。

- **Tuist** 生成 `.xcworkspace`（不是手写 `.xcodeproj`）；`Project.swift` 定义 3 个 staticFramework（WhisperBoardKit / AudioProcessing / Common）+ App + ShareExtension + 三组测试 target。
- 大量外部依赖：AsyncAlgorithms / AudioKit / **ComposableArchitecture** (TCA) / DependenciesAdditions / DSWaveformImage / DynamicColor / FluidGradient / Inject / KeychainAccess / Lottie / NavigationTransitions / OrderedCollections / Popovers / PulseLogHandler / PulseUI / SwiftUIIntrospect / VariableBlurView / **WhisperKit** / Pow / SnapshotTesting（测试）/ Rollbar（仅 App Store 版）。
- iCloud Document scope，audio + processing 后台模式，BGTaskScheduler 注册。
- ShareExtension 接收外部音频文件做转录（不是流式语音输入！）。
- **关键限制**：iOS 不允许自定义 IME 注入第三方语音识别——所以 Whisperboard 不是真"语音输入法"，而是"录音 → 转录 → 复制/分享"的工具。这是 iOS 平台事实约束，不是 Whisperboard 自身的设计缺陷。`[高]`

- Shell 派系比例（含 重点分析项目，34 项）：Swift 原生约 **13** 项（38%）/ Tauri Rust 约 **8** 项（24%）/ Python 桌面约 **7** 项（21%）/ Electron 约 **2** 项（6%）/ Android IME 约 **1** 项/iOS+ 约 **2** 项/其他 约 **1** 项。**Swift + Tauri 加起来超过 60%**，是 2025‑2026 这波 AI 语音输入工具的事实主流。
- C/S 分离度 0 占绝大多数（24/34）；C/S=2/3（可挂远端）的约 8 个项目就是 **方案五 LarePass-aware 路径的天然候选**。

## 七、剩余不确定项 / 留待 §4 §5 解决

1. **`FluidAudio` 内部细节**（Parakeet CoreML 实现）—— 关系到 方案二 / 方案四 是否能在 Olares 集群里复用相同模型，留待 §4（大模型架构对比）解决。
2. **`transcribe-rs` 0.3.x 的 whisper-vulkan / whisper-metal feature** 是否能在 Olares ARM64 容器内启用 GPU —— §5 安装复杂度评估解决。
3. **CapsWriter Server 的 GPU/容器化部署是否平滑** —— 它现在主要面向 Windows + CUDA local，要迁移到 K8s Helm chart 形态需评估 `multiprocessing` 在容器里的行为 —— §6 命题 A 解决。
4. **WhisperKit 在 iOS 上的 Core ML 模型缓存策略与 方案五 中桌面 Mac 用户的 WhisperKit 缓存能否共享** —— 跨 §4 / §6 解决。
5. **Voquill 的 Flutter mobile 实际是否上架 Google Play / App Store** —— 关系到 方案二 在 iOS 上是否真的有可行的"Capacitor/Flutter 套壳"参考样板（vs 我已论断的"iOS 不可能"），留待 §5。
6. **Type4Me Python 子进程在 macOS 11/12/13 旧版的兼容性** —— 仅 Apple Silicon + macOS 14+ 的限制是否能放宽，留待 §5。

## 八、一句话结论

> 桌面端语音输入的 2025‑2026 主流是 **Swift 原生派**（Apple 系）和 **Tauri Rust 派**（跨桌面）两条主线，Electron 已被挤出；中文圈以 **CapsWriter C/S 架构**为旗舰，是 方案四 Olares 集群侧 ASR 后端的最干净直接借鉴。移动端事实上只有 **Android IME 派**这一条路（WhisperIME 是 方案二 + 方案三 双形态唯一参考），**iOS 路径在系统级注入层面客观不存在**，只能依赖 方案五 桌面端覆盖。
