# 方案四 Olares 集群侧设计

> 本文是方案四（Olares 集群侧 ASR / TTS / LLM 后端）的设计层文档。**目的**：把已查证的事实（speaches 已成品 + CapsWriter Server 容器化成熟 + ModelScope 可直连 + sharedEntrance 机制完整）翻译成**三阶段可落地路线 + 应用骨架 + 关键接口契约**，供方案五客户端、Olares Team、第三方桌面端开发参考。
>
> **不做的事**：不写代码、不画完整 Helm chart、不做架构层面的"再设计"——这些放到真正立项后做。本文只做"如果决定立项，第一周要先想清楚什么"。

---

## 一、设计目标与约束

### 1.1 目标

| 目标 | 量化 |
|---|---|
| 给桌面客户端、Android IME、第三方 LarePass-aware app 提供**统一的"OpenAI 兼容 STT + TTS + LLM 后处理"endpoint** | OpenAI SDK / curl 即调 |
| 覆盖中文 + 英文 + 多语种三档场景 | 中文用 SenseVoice / Paraformer 系，英文用 Whisper turbo，多语种用 Whisper large-v3 |
| 多用户共享 + 用户感知隔离 | clusterScoped + Olares 多租户 sharedEntrance 标准模式 |
| 国内可达 | 模型源默认 ModelScope；Whisper 走 hf-mirror.com fallback |
| GPU / CPU 双轨 | NVIDIA CUDA 12+ 主路径，CPU fallback 给无 GPU 节点 |
| 与现有 Olares 应用复用 | LLM 后处理直接复用 `ollamav2` sharedEntrance，不再重复部署 |
| 升级 / 回滚干净 | Helm chart + 模型版本号化 + hostPath PVC 持久化 |

### 1.2 约束（事实已查证）

| 约束 | 来源 |
|---|---|
| speaches 已上 Olares Market（当前 1.0.12），sharedEntrance host `sharedentrances-speaches`，port 80→8000，OpenAI 兼容路径全开 | `speaches/OlaresManifest.yaml` |
| speaches GPU 注入注解 `applications.app.bytetrade.io/gpu-inject: "true"` 是 Olares 标准 GPU 调度方式 | `speaches/speachesserver/templates/speaches.yaml` |
| hostPath 模型存储默认在 `userspace.userData/Huggingface/<app>` | speaches 模板 |
| Olares clusterScoped 模式：admin 装一份，user 通过 `dependencies.application` 引用 | speaches Manifest |
| ollamav2 sharedEntrance host 已被 speaches 默认引用 | speaches 模板 |
| CapsWriter Server 端：WebSocket 6016，protobuf 协议（非 OpenAI 兼容） | DF-wu/CapsWriter-Offline-Container |
| sherpa-onnx 单仓内支持 SenseVoice + Paraformer + Whisper + Zipformer 多模型 | k2-fsa/sherpa-onnx README |
| OlaresManifest 当前 `v0.11`，应用需声明 `amd64 + arm64` 两架构 | Olares Manifest 规范 |

### 1.3 非目标

- 不重新发明轮子；能复用 speaches 就复用
- 不追求"完美架构"；先有可用版本，再迭代
- 不为 Apple Silicon / MLX 等仅 Mac 场景做集群优化（这些只在 方案五 客户端侧用）
- 不做"私有 Helm chart 仓"；走 Olares Market 官方上架渠道

## 二、三阶段路线

### 2.1 全景

```
                短期阶段 (0 工程)          中期阶段 (中型)               长期阶段 (可选)
                ─────────────────         ──────────────────           ──────────────────
ASR-EN          speaches/whisper-1   →   同 短期阶段                →   + Voxtral Mini
                (faster-whisper-small)   (升级到 large-v3-turbo)        (多模态 / 24B)

ASR-ZH          ❌ (用户体验差)        →   olares-funasr            →   + Qwen3-ASR
                                          (sherpa-onnx +              (高准模式)
                                          SenseVoice-Small)

ASR-多语种     speaches/whisper-1   →   + Whisper-large-v3       →   + Parakeet TDT v3
                (small 不准)              (sharedEntrance 不变)         (RNN-T 流式)

TTS             speaches/tts-1       →   同 短期阶段                →   + 自家 OpenVoice / GPT-SoVITS
                (Kokoro-82M)             (中文音色可选)

LLM 后处理      ollamav2 现有        →   同 短期阶段                →   同 短期阶段
                                          (方案五 客户端 BYOK 也保留)
```

### 2.2 短期阶段 ── 零工程

**目标**：今天就能开始让 方案五 客户端连进来用。

**做什么**：
1. **不改 speaches 任何代码**。
2. 写一份 **方案五 客户端集成规范**（Endpoint 命名、Auth 方式、模型 alias 约定），见 §三 §3.4。
3. 写一份 **Olares Market 上的"使用文档增量"**，告诉用户：
   - 装完 speaches 后如何在 Type4Me / Handy / Whispr / CapsWriter Client 等第三方桌面端把 OpenAI baseURL 改到 speaches sharedEntrance。
   - 配套截图。
4. 写一份 **LarePass 内嵌的入口提示**（这是给 LarePass team 的请求，不一定真做）：在 LarePass 安装 speaches 时，引导用户复制 sharedEntrance URL 到剪贴板，给桌面客户端用。

**不做什么**：
- 不写中文 ASR 模型集成（speaches 用 small 中文准确率不够，但 短期阶段 接受这个缺陷）。
- 不写流式 WS endpoint（speaches 已有，但客户端集成方式由 方案五 设计决定）。
- 不动 ollamav2、不动 LLM 路线。

**工作量**：0.5 人周（文档为主）。

**风险**：
- speaches 默认 `faster-whisper-small` 对中文极差 → 中文用户体验差，可能引发"speaches 不能用"的误解 → 缓解：文档里强调"中文用户先把 `SPEACHES_WHISPER_MODEL` 改成 `Systran/faster-whisper-large-v3`，并接受 ~3 GB 模型下载"。

### 2.3 中期阶段 ── 中文扩展

**目标**：在 Olares 集群里有一份"开箱即用、中文为主、OpenAI 兼容"的 ASR 后端。

**两个候选方案**：

#### 方案 A：fork speaches 加 sherpa-onnx 后端（推荐）

**思路**：speaches 原本只有 `faster_whisper` 一个执行器；我们 fork 后加一个 `sherpa_onnx` 执行器，让同一个容器同时支持 `whisper-1`（Whisper 系）+ `sensevoice-small`/`paraformer-large`（中文系）两套模型 alias，都走 `/v1/audio/transcriptions`。

**优点**：
- 方案五 客户端无需改协议；只需在 model 字段切换 alias。
- 同一个 sharedEntrance 服务两种模型，路由 / Auth / 监控复用 speaches 现成。
- 升级时 Olares Market 单包升级。

**缺点**：
- 需 fork + 长期维护 speaches 分支（叫 `speaches-ext` 或 `speaches-zh`）；上游升级要 rebase。
- sherpa-onnx 是 C++ 项目，Python 绑定通过 pip `sherpa-onnx` 即可，但 `model_aliases.json` 的扩展需要熟悉 speaches 内部 `executors/` 目录。

**工程量估计**：
| 步骤 | 时间 |
|---|---|
| 调研 speaches `src/speaches/executors/` 结构，画清楚抽象边界 | 2 天 |
| 加 `executors/sherpa_onnx/` 模块（SenseVoice + Paraformer 各一个 wrapper） | 3 天 |
| 改 `model_aliases.json` 支持中文 alias | 1 天 |
| 把模型预下载脚本扩展（initContainer 增加 ModelScope 拉取分支） | 1 天 |
| 容器镜像新增 ARG `WHISPER_LANG=zh\|en\|multi` 控制安装哪些模型 | 1 天 |
| OlaresManifest 加 `SPEACHES_ZH_MODEL` 环境变量、新增 `Systran/faster-whisper-large-v3` 推荐档 | 1 天 |
| Helm 单元测试 + Olares 集群测试 | 3 天 |
| 文档 + UI 截图 | 2 天 |
| **合计** | **约 2 人周** |

#### 方案 B：新建独立 olares-funasr 应用

**思路**：基于 CapsWriter Server 端 fork（DF-wu/CapsWriter-Offline-Container 是最严肃的），加一层 FastAPI sidecar 把 CapsWriter 的 protobuf WS 翻译成 OpenAI 兼容 REST，再封 OlaresManifest。

**优点**：
- 独立维护，不污染 speaches。
- CapsWriter 自带"角色 / 热词 / 规则 / 历史"丰富功能，可作为差异化卖点。
- 与 Qwen-ASR 集成更顺（CapsWriter v2.3 已经支持）。

**缺点**：
- 方案五 客户端要支持"双 endpoint"配置（speaches / olares-funasr 切换），用户体验更复杂。
- 翻译层（CapsWriter protobuf ↔ OpenAI REST）是一段必须维护的胶水代码（~300 行 Python）。
- Olares Market 又多一个应用要审核。

**工程量估计**：
| 步骤 | 时间 |
|---|---|
| fork DF-wu 的镜像，去掉 Windows 特有依赖（默认是有的） | 3 天 |
| 写 OpenAI 兼容 FastAPI sidecar（`/v1/audio/transcriptions` → 投到 CapsWriter WS） | 4 天 |
| 包成 sharedEntrance + entrance（UI 给用户查看历史 / 热词管理） | 3 天 |
| 写 Helm chart（参照 speaches） | 3 天 |
| OlaresManifest + 国际化（en-US/zh-CN） | 1 天 |
| 模型预下载（Paraformer + Qwen-ASR + CT-Transformer 标点） | 2 天 |
| 集群测试 + 上架准备 | 3 天 |
| **合计** | **约 4 人周** |

#### 方案选择

| 维度 | 方案 A | 方案 B |
|---|---|---|
| 工作量 | 2 周 | 4 周 |
| 升级负担 | 中（rebase speaches） | 低（独立维护） |
| 方案五 客户端复杂度 | 低（单 endpoint） | 中（双 endpoint） |
| 用户使用体验 | 高（无感知切换中英）| 中（要选用哪家） |
| Olares Market 包数 | 1 | 2 |
| 长期可维护性 | 中 | 高 |

**结论**：**中期阶段 推荐方案 A**。低工作量、单 endpoint、对客户端友好。方案 B 留作 长期阶段+ 的"高级用户可选"档（如果有人非要 CapsWriter 的角色 / 热词功能，再单独装）。

### 2.4 长期阶段 ── GPU 高端模型

**目标**：给重度用户 / 多语种用户 / 流式低延迟用户提供"集群里跑大模型"的能力。

**候选**：

| 模型 | 体积 | VRAM | 加它的理由 | 推荐发布形式 |
|---|---|---|---|---|
| **Voxtral Mini** | ~3 GB INT8 | 12 GB | 中英多语种 + 语音问答（无需先 ASR） | 独立 `olares-voxtral` 应用 |
| Parakeet TDT v3 | ~500 MB | 4 GB | 25 欧洲语种 + 真流式 + EOU | 加到方案 A 的执行器列表里 |
| Qwen3-ASR | ~8 GB | 8 GB | 中文高准 + 多模态延展 | 独立 `olares-qwen-asr` 应用 |

**取舍**：
- Voxtral Small / Whisper large-v3（完整 1.5B）属于"24 GB+ VRAM 才能舒适跑"的档，**Olares 默认假设是个人云，不强推**；放进文档作为"如果有 A100/H100 节点的用户可手动启用"。
- Parakeet 的 CC-BY-4.0 Attribution 必须在 OlaresManifest `license` 字段和应用首页明示。

**工程量**：每加一个 GPU 模型 ~1‑2 人周。

### 3.2 sharedEntrance 设计

| 项 | 值 | 说明 |
|---|---|---|
| Service host | `sharedentrances-speaches-ext` | 与现有 speaches 不冲突 |
| Service port | 80 | K8s service port，目标 8000 |
| URL（集群内） | `http://sharedentrances-speaches-ext.user-system-${user}/v1` | 内部应用直接访问 |
| URL（外网，通过 LarePass VPN） | `https://<entrance-domain>` + 自动 https | LarePass 已建 VPN 到家用集群 |
| Auth | `authLevel: internal` 内部 token；方案五 客户端通过 LarePass Service Provider 取 | 不接受 anonymous |
| OpenAI base path | `/v1`（speaches 默认） | 直接 OpenAI SDK 调 |

### 3.3 模型预下载与持久化

**问题**：speaches 中期阶段 fork 后需要下三类模型：
- Whisper 系（HuggingFace `Systran/faster-whisper-large-v3-turbo`，~1.6 GB）
- SenseVoice / Paraformer（ModelScope `iic/SenseVoiceSmall` 等，~228 MB / ~700 MB）
- TTS（HuggingFace `speaches-ai/Kokoro-82M-v1.0-ONNX`，~80 MB）

**统一策略**：
1. initContainer `download-models`（沿用 speaches 模板）增加 ModelScope 分支：
   ```sh
   # ModelScope 拉中文模型
   pip install modelscope
   python -c "from modelscope.hub.snapshot_download import snapshot_download; \
              snapshot_download('iic/SenseVoiceSmall', \
                                cache_dir='/home/ubuntu/.cache/modelscope')"
   ```
2. hostPath PVC 拆两个挂载点：
   - `userspace.userData/Huggingface/speaches-ext` → `/home/ubuntu/.cache/huggingface`
   - `userspace.userData/ModelScope/speaches-ext` → `/home/ubuntu/.cache/modelscope`
3. 模型源 fallback 策略（initContainer 启动脚本逻辑）：
   - 中文模型默认走 ModelScope；如果 ModelScope 不可达（特殊网络），降级走 hf-mirror.com 同名仓
   - Whisper 默认走 `HF_ENDPOINT=https://hf-mirror.com`；用户手动改可走原 HuggingFace

### 3.4 方案五 客户端集成契约

> 给 方案五（第三方桌面客户端）的最小集成契约，**这是 方案四 给出的"对外承诺"**，需与 方案五客户端设计配套。

| 项 | 约定 |
|---|---|
| **发现机制** | 方案五 客户端通过 LarePass Service Provider SDK（详见 方案五客户端设计）查询 `speaches-ext` 应用的 sharedEntrance URL；不要硬编码 host 名 |
| **Auth** | LarePass 颁发的内部 token（Bearer），客户端不需要直接接触；通过 SDK 自动注入 |
| **OpenAI 接口路径** | `POST /v1/audio/transcriptions`（STT）+ `POST /v1/audio/speech`（TTS）+ `GET /v1/models`（探测可用模型） |
| **模型 alias** | 客户端在 model 字段填 `whisper-1` / `sensevoice` / `paraformer` / `tts-1`；不要填具体 HF 仓名 |
| **streaming** | speaches 0.8.2 已支持 `?stream=true`；客户端实现以 Server-Sent Events 接 |
| **错误码** | 502 = 模型未加载（首次启动 30‑60s），客户端要做指数退避重试 5 次；429 = 集群繁忙 |
| **音频格式** | 客户端送 16 kHz 单声道 PCM WAV / FLAC / OGG / MP3；speaches 自动 resample |
| **多用户** | 每个 LarePass 用户调到的是 admin 的 clusterScoped 实例，不会互相串数据；隐私保证依赖 Olares 用户态隔离 |
| **TTS voice ID** | Kokoro 提供 `af_heart`（英文女）/ `zf_*`（中文女）/ `zm_*`（中文男）等 |
| **版本协商** | 客户端启动时 `GET /v1/models` 拿到 `data[].id` 列表，UI 给用户选可用模型；不要写死 |

## 四、集群侧关键资源 / 配额

### 4.1 资源配额建议（每用户 / 每实例）

| 模式 | RAM | CPU | GPU 显存 | 磁盘 |
|---|---|---|---|---|
| 短期阶段（默认 whisper-small）| 2.5–9 Gi | 0.6–9 | 4–16 Gi | 2–20 Gi |
| 中期阶段（whisper-turbo + SenseVoice）| 4–12 Gi | 0.6–9 | 4–16 Gi | 4–40 Gi |
| 长期阶段（+ Voxtral / Parakeet）| 8–24 Gi | 1–12 | 8–24 Gi | 8–60 Gi |

### 4.2 多用户并发

- Olares clusterScoped 模式下，**所有用户共享同一个 Pod 实例**。
- 并发上限受 GPU 显存决定：
  - Whisper large-v3-turbo（FP16）单请求 ~2 GB → 12 GB GPU 约 5 个并发
  - SenseVoice-Small（INT8）单请求 ~500 MB → 12 GB GPU 约 24 个并发
- 家用场景 1‑5 用户同时，足够。

### 4.3 监控与日志

- speaches 自带 uvicorn 日志（/var/log 集成 Olares 日志系统）；
- 建议 中期阶段 加入 Prometheus exporter（暴露 `/metrics` 计 STT 调用数 / 延迟 / 错误率）；
- 与 Olares Cluster Dashboard 已有 GPU 监控集成（NVIDIA DCGM exporter 已被 Olares 默认装上）。

### 4.4 备份与恢复

### 4.5 升级与回滚

## 五、与 LarePass / Headscale 的集成

### 5.1 用户访问路径

```
[Type4Me / Handy / CapsWriter Client on user laptop]
         ↓ OpenAI SDK
[https://speaches-ext.<user>.<topDomain>/v1]
         ↓ Headscale VPN（已建）+ Olares Ingress
[K8s ClusterIP service: speaches-ext.speachesextserver-shared:8000]
         ↓
[uvicorn + faster_whisper / sherpa_onnx]
         ↓ Apple GPU/CUDA/CPU
[模型推理]
```

### 5.2 三种网络场景

| 场景 | 网络 | 方案五 客户端 baseURL |
|---|---|---|
| 用户在家局域网 | 同一 WLAN | `https://speaches-ext.<user>.<topDomain>/v1`（走 Olares Ingress + mDNS / 公网 DNS） |
| 用户在外地，LarePass 已建 VPN | Headscale | 同上（LarePass tunneling 透明）|
| 用户在外地，LarePass 未建 VPN | 公网 | 同上（要求 Olares 集群有公网 IP / NAT 穿透）|

### 5.3 LarePass Service Provider 机制

> 这条是 方案五 客户端发现 sharedEntrance 的关键路径，与 方案四 是契约关系。

- LarePass 桌面客户端登录后，**用户的所有已装 Olares 应用**会以 "Service Provider" 形式注册到 LarePass 本地数据库；
- 第三方桌面 ASR 应用（方案五 路径）通过 LarePass 提供的 SDK / 本地 API（IPC over Unix socket / HTTP loopback）查询 `speaches-ext` 的 sharedEntrance URL；
- 取到 URL 后 + 注入的 token，即可调 OpenAI 兼容 endpoint。

> 详细 SDK 形式留给 方案五客户端设计；本节只确认 **方案四 在 sharedEntrance 注册时需要给出 LarePass 可识别的 metadata**（建议在 OlaresManifest 加 `lareTags: ["openai-compatible-asr", "openai-compatible-tts"]` 或类似 tag，让第三方应用过滤）。这一条**待 LarePass team 确认是否已有 tag 机制**。

## 八、章节小结

1. **短期阶段 几乎零工程**：现成 speaches + 一份 方案五 客户端集成文档 + 一份用户引导。0.5 人周。
2. **中期阶段 选方案 A**：fork speaches 加 sherpa-onnx 执行器，单 endpoint 同时服务 Whisper + 中文模型。约 2 人周。
3. **长期阶段 按需加 GPU 模型**：Voxtral / Parakeet / Qwen3-ASR 三选若干，独立或合并均可，每个 ~1‑2 人周。
4. **架构契约**：方案四 = OpenAI 兼容 STT + TTS；LLM 后处理是 方案五 责任，通过 ollamav2 sharedEntrance 或客户端 BYOK 解决。
5. **关键依赖**：LarePass Service Provider SDK（需与 LarePass team 对齐）；Olares 自带 GPU 调度注解、hostPath PVC、clusterScoped 多租户均可直接复用。
6. **国内可达性**：默认 ModelScope（中文）+ hf-mirror.com（Whisper），通过 `HF_ENDPOINT` 环境变量覆盖。
