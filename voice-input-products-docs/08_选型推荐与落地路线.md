# 选型推荐与落地路线

> 本文是面向决策层的"应该做什么 / 先做什么 / 投入多少 / 期望什么收益"的综合落地指南。**目的**：把全部调研物料的所有调研物料压缩成一张张可执行的选型表、阶段路线图与工作量矩阵，使最终汇报能直接照搬。
>
> **不做的事**：不给最终拍板（Olares 团队 / 业务方拍）；不写商业计划书；不做利润模型。

## 一、决策框架

### 1.1 三种"决定要做"的判断

| 判断 | 决策权重 |
|---|---|
| **战略意图**：Olares 想不想拥有"自家语音输入"这块技术拼图？ | 5 |

| **风险**：法律 / 平台政策 / 上游模型变化 | 3 |

### 3.2 短期阶段 — 2026 Q3：零工程上线 + 验证 方案四

**目标**：用最低投入验证 方案四 endpoint 的真实可用性，给用户看到"Olares 集群里能跑语音"这件事。

**交付物**：

| # | 项 | 形式 | 负责 |
|---|---|---|---|
| 1 | 方案一 兼容性指南（中英）| 应用商店内嵌文档页 + docx | 文档组 |
| 2 | 方案五（轻量版）：adapter daemon | macOS/Windows/Linux 二进制 + 7 个客户端配置指南 | 1 名后端开发 |
| 3 | 方案四 短期阶段：speaches Olares 应用文档增强 | OlaresManifest 文档区 / Olares Market 介绍页 | 文档组 |
| 4 | 用户引导：LarePass 装完 speaches 后弹窗"复制 endpoint URL" | LarePass PR | LarePass team |
| 5 | LarePass Service Provider SDK 设计文档 | 与 LarePass team 对齐 | 跨团队 |

**投入**：1‑2 人月。

**成功标准**：
- speaches Olares Market 月装机量 ≥ 1000；
- adapter daemon GitHub Star ≥ 200；
- 至少 3 个第三方 ASR 客户端在其文档中提及"可指向 Olares speaches"。

### 3.3 中期阶段 — 2026 Q4：中文扩展 + 客户端旗舰

**目标**：把 方案四 中文体验做好（speaches-ext），把 方案五 桌面客户端做出旗舰，把 方案三 Android 做出 MVP。

**交付物**：

| # | 项 | 形式 | 负责 |
|---|---|---|---|
| 1 | 方案四 中期阶段：speaches-ext | Olares Market 新应用 | 1‑2 名后端 |
| 2 | 方案五（完整版）（macOS + Windows）| Homebrew Cask + msi | 2 名桌面端 + 1 设计 |
| 3 | 方案三 RecognitionService APK | F-Droid + LarePass 二维码 | 1‑2 名 Android |
| 4 | LarePass Service Provider SDK 落地 | LarePass 版本号 +1 | LarePass team |
| 5 | 模型源国际化 + ModelScope/hf-mirror 自动切换 | speaches-ext 配置项 | 后端 |
| 6 | 端到端测试 + 国内主流 Mac/Win/Android 设备覆盖 | 测试报告 | QA |

**投入**：8‑12 人月（视并行度）。

**成功标准**：
- speaches-ext 月装机量 ≥ 5000；
- 方案五（完整版）客户端 MAU ≥ 2000；
- 方案三 APK F-Droid 下载量 ≥ 500/月；
- 中文 ASR 实测准确率 ≥ 92%（家用普通话场景）。

### 3.4 长期阶段 — 2027 Q1：GPU 高端模型 + 完整 IME + Linux

**目标**：覆盖高端用户、完整 Android IME、Linux 桌面客户端。

**交付物**：

| # | 项 | 形式 | 负责 |

| 3 | 方案二 完整 IME（视 方案三 反响）| F-Droid + LarePass 二维码 | Android |

## 九、章节小结

1. **默认推荐 = 「中道」组合 8‑10 人月**：覆盖 65% 用户面，3 个月可上线 短期阶段，6‑9 个月完成 中期阶段 主体。
2. **最低门槛 = 「冒险家」2 人月**：用 方案一 + 方案五（轻量版） + 方案四 短期阶段 验证市场反响。
3. **ROI 顶端 = 方案四 短期阶段 + 方案五（轻量版） + 方案一 指南**：单位人月覆盖用户面最高。
4. **关键依赖 = LarePass Service Provider SDK**：决定 方案二/方案三/方案五 的 ±30% 投入；立项前必须对齐。
5. **路径优先级 = 方案三 > 方案二**：Android 上 RecognitionService 用户感知阻力小、覆盖面同等、投入小。
6. **iOS 是无解约束**：仅能用 Apple 系统输入法 + 桌面端覆盖。
7. **Olares 内已有 `speaches` + `ollamav2` + `whisperwebuiv2`** —— 强建议 方案四 中期阶段 不要重复造轮，先与现有团队对齐重定位。

## 十、给最终报告的"一页纸结论"草稿

> 把以下文字直接放进最终报告的 Executive Summary：

**Olares 内"语音输入"能力可走五条候选方案（方案一 至 方案五）。综合用户覆盖、工程投入、ROI 三维评估，默认推荐"中道组合"——方案四短期+中期阶段（直接复用并扩展现有 speaches Olares 应用，加中文模型）+ 方案五自研 Tauri 桌面客户端（macOS+Windows，复用 Handy 等 OSS 基线）+ 方案三 Android RecognitionService APK——约 8‑10 人月可上线短期 + 中期阶段主体，预计覆盖 65% Olares 用户面。**

**关键依赖：LarePass Service Provider SDK（决定客户端发现 endpoint 的体验，立项前需与 LarePass team 对齐）；模型源 ModelScope（中文）+ hf-mirror.com（Whisper）双轨；ollamav2 复用为 LLM 后处理后端。**

**关键约束：iOS 第三方键盘无麦权限（Apple 政策硬约束），iOS 用户只能 方案一（Apple 系统）+ 方案五（桌面端覆盖）；国内 Android 分发不依赖 Google Play，走 F-Droid + LarePass 二维码 + Olares 自家市场。**

**ROI 最优三个动作：① 方案四 短期阶段 直接复用 speaches；② 方案五（轻量版） adapter daemon（1 人月覆盖桌面全 ASR 客户端用户）；③ 方案三 Android RecognitionService（3‑5 人月覆盖 Android Gboard 用户面）。**

**当前最大不确定项：LarePass Service Provider SDK 是否已有 / 何时落地。其次：speaches 与 whisperwebuiv2 重叠如何处置；Olares Mobile roadmap 是否影响 方案二/方案三 分发；Android Google Play 2026/2027 实名政策影响。**
