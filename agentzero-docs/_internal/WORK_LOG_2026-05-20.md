## 三、端到端 MCP 集成实测史（最关键的事实链）

按时间顺序记下每一步遇到的现象、错误结论、最终真相。**这一节是为了不重蹈覆辙**。

### 3.1 第 1 个坑：`authLevel: private` → OpenCode 公网 URL 401 redirect

**现象**：OpenCode 配 `https://239ce90b.demo0002.olares.com/.../sse` 时被 Olares 网关跳转到 `auth.demo0002.olares.com` 登录页（HTTP 2 400 + Location 头）。

**误判过程**：先怀疑 token、再怀疑路径、再怀疑 SSE vs streamable-HTTP；都不是。

**真相**：私有 entrance 默认要登录，跨 app 调用被 Olares OpenResty 直接拦了。改成 `authLevel: internal` 解决。

### 3.2 第 2 个坑：`/http` 还是 `/http/`（**反复犯，最严重的一次自我误导**）

**现象**：用 `type: "remote"` + URL 末尾 `/http`（无斜杠），第一次报 "Streamable HTTP error"。

**误判过程（共两次）**：
1. 第一次怪 trailing slash：因为 curl `-X POST` 不带 `-L` 直接打 `/http` 返回 HTTP 307 Temporary Redirect，于是断定 "OpenCode 客户端没跟 307 重定向 POST"，硬把文档写成 "trailing slash is required"
2. 用户测了 `/http/`（带斜杠）也一样报 "Streamable HTTP error"，**我才意识到**：当时的 "Streamable HTTP error" 根本不是 trailing slash 问题，而是 504 在 15 秒触发后被客户端误报成 transport 错误

**真相**：mcp-remote / OpenCode 的 streamable-HTTP 客户端**会自动跟 307 POST 重定向**（重发 body），URL 带不带尾斜杠都能通。"Streamable HTTP error" 这个文案是误导性的，实质是 upstream 504 被客户端 wrap。**修了 `apiTimeout: 0` 之后，无尾斜杠也直接通**。

教训：**`/` 这条线索我抓了两遍。两次都是错的**。下次遇到类似 "Streamable HTTP error" 直接先去看时间戳，是不是 ~15s 出来的 → 99% 是 upstream timeout，跟 transport 协议本身无关。

### 3.3 第 3 个坑：mcp-remote 代理也救不了 → 实际是上游 504

**现象**：试了 `type: "local"` + `npx mcp-remote` 代理也卡 / 失败。

**误判过程**：以为 OpenCode 内置 streamable-HTTP 客户端跟 agent-zero MCP server 的 session-id 处理有冲突，建议用 mcp-remote 当 stdio bridge。

**真相**：跟 session-id 也没关系。**仍然是 Olares envoy/openresty 默认 15 秒 upstream timeout**。修 `apiTimeout: 0` 后无需 mcp-remote。

### 3.4 最终可用配置（确认通过的）

```json
{
  "mcp": {
    "agent-zero": {
      "type": "remote",
      "url": "https://239ce90b.demo0002.olares.com/mcp/t-jvYKHFucz1lu1A_7/http",
      "enabled": true
    }
  }
}
```

- **不需要** mcp-remote 代理
- **不需要** 尾斜杠
- **不需要** 自定义 timeout 字段（但客户端默认 timeout 太短的话 -32001 仍会出现，见第四节）
- 前提：chart 已升到 1.0.4 (apiTimeout: 0 + authLevel: internal) + agent-zero 自己 Chat Model 配 OK

集群内 curl 公网 URL 实测：单次 `tools/call send_message` 27 秒拿到完整 9 KB JSON-RPC 响应。链路本身通。

## 四、压力实测的"40% 成功率"问题（未解，明天的实验题）

### 4.1 实测数据

OpenCode（带 OMO 插件）连续 5 次发同一条 prompt `使用agent-zero这个MCP，列出其所有可用的tool和功能。`（每次间隔到 agent-zero 日志稳定）：

| # | agent-zero pod 日志 | OpenCode+OMO 客户端 | 实际 |
|---|---|---|---|
| 1 | ✅ MCP Chat message completed | ✅ 拿到结果 | 通 |
| 2 | ✅ completed | ❌ -32001 RequestTimeout | **服务端干完了，客户端没拿到** |
| 3 | ❌ litellm 504 + retry 污染输出 | ❌ -32001 | 真失败 |
| 4 | ✅ completed | ✅ 拿到结果 | 通 |
| 5 | ✅ completed | ❌ **直接中止，无返回无报错** | **静默 abort** |

**端到端成功率 2/5 = 40%**。

### 4.2 三个独立但叠加的故障源

#### A. 外部 Ollama / Embedding 服务的 15 秒 504

第 3 次直接报：

```
httpx.HTTPStatusError: Server error '504 Gateway Timeout'
for url 'https://8f00b8b7.demo0002.olares.com/api/generate'
```

域名 `8f00b8b7` 不是 agentzero（`239ce90b`），是**另一个 Olares app**（agent-zero 配的 Chat Model 提供方，疑似 Ollama）。它那侧 `apiTimeout` 大概率没设 0，所以模型推理 > 15s 就被它**自己侧**的 Olares 网关砍。

#### B. agent-zero 自身的 stream 污染 bug

「请介绍下金庸」（直接在 agent-zero UI 里对话，**不经过 MCP/OpenCode/OMO**）的日志里同样出现：

```
Reasoning:                ← 第一份开始
Error: Memory consolidation timeout for area fragments
Reasoning:                ← 第二份叠上来
...
Response: 
{
    "thoughts": [
Response:                 ← 又一遍
{
    "thoughts": [
```

agent-zero 在 `_91_recall_wait.py` / `_50_recall_memories.py` 这条 memory 后台 task timeout cancel 后，**没清理旧 stream output 就开了新一轮 monologue**，两轮输出交错打印。如果这段交错的内容刚好是 MCP HTTP response 体，客户端就解析失败。

`Error: Memory consolidation timeout for area fragments` 这一条**几乎每次都出现**，说明 Embedding 服务（也是某个外部 app）也跑不进 agent-zero 内部的 `asyncio.wait_for` 窗口。

#### C. OMO 的并发 / paraphrase 行为

[oh-my-opencode / oh-my-openagent](https://github.com/code-yeongyu/oh-my-openagent) 的 README 自吹：

- "Discipline Agents — Sisyphus orchestrates Hephaestus, Oracle, Librarian, Explore. **A full AI dev team in parallel.**"
- "Team Mode — Lead agent + **up to 8 parallel members**"
- "Background Agents — **Fire 5+ specialists in parallel.** Context stays lean. Results when ready."
- "**aggressive parallel execution**"

确证 OMO 在改写 prompt：用户发 1 条中文，agent-zero pod 日志收到 **5 个不同英文 paraphrase** + 1 个中文（最后一次）。能解释 paraphrase 的只能是 OMO 的 IntentGate / Sisyphus 或 OpenCode 底层 LLM。

第 5 次"静默 abort 无报错"在直接 UI 对话里不存在，**只在 OMO 在场时出现**，跟 OMO 强相关。

### 4.3 "100% 反驳"的尝试与失败

用户明确要求："如果你真的能确认不是 OpenCode、OMO、AgentZero 的问题，我们就可以先不管了，但你一定得能做到 100% 确认。"

逐条反驳"它们无辜"的结论：

| 嫌疑 | 现有证据 | 100% 排除？ |
|---|---|---|
| **agent-zero retry/stream bug** | 直接 UI 对话也现场重现双倍输出 | ❌ **不能**，bug 在它代码里 |
| **OMO 并发 / paraphrase** | "静默 abort" 只在 OMO 在场出现；paraphrase 行为确证 | ❌ **不能**，缺裸 OpenCode 对照 |
| **OpenCode 内置 streamable-HTTP 客户端** | 单次 curl 27s 拿到完整 9 KB，但**未做连续 5 次 curl** | ❌ **不能**，缺对照 |

**结论：无法 100% 排除任何一个**。Chart 这一层（agentzero 自己）已修到尽，但整体使用稳定性受多个上游/客户端因素叠加影响。

```bash
URL="https://239ce90b.demo0002.olares.com/mcp/t-$MCP_TOKEN/http/"
for i in 1 2 3 4 5; do
  echo "=== 第 $i 次 ==="
  kubectl run mcp-rep$i --rm -i --restart=Never -n default --image=curlimages/curl:8.10.1 -- sh -c "

    curl -sS -X POST '$URL' -H 'Content-Type: application/json' \
```

**不影响功能**，与 market 上正式发布的 clawdbot / flaresolverr 同等地位。明天若有空可以尝试把 ingress readiness probe 路径从 `/` 改成 `/api/health`（不会被任何 auth 层 403）看能不能逃出锁定，但**优先级低**。

```bash
kubectl get application agentzero-demo0002-agentzero -o json | jq '.spec.options'
```

**Whisper 的 `spec.options` 也是空的**。说明平台**根本不把 `options.apiTimeout` 映射到 application CR 上**，它在 install 时被消费成路由/网关配置了。

**结论修正**：之前怀疑"apiTimeout 没生效"是错的线索，撤回。chart 的 `options.apiTimeout: 0` 写法跟其他 226 个 app 完全一致，**没毛病**。

| 探测 | 命令 | 结果 |


**1 条 MCP 消息 → agent-zero 内部 3 路并发打 qwen3:14b**（主对话 + memory _50_ + memory _91_）+ 0.x 路真 embedding，每路超时 proxy 又重试，把 14B（一次只能跑一个 token）打成队列死锁。

### B.2 重启 ollama 验证根因

```bash
kubectl delete pod -n ollamaqwen314bv2server-shared -l app=ollama
# 等 30 秒
probe6: POST /api/generate "Say hi" num_predict=5 → HTTP=200 time=4.003s ✓
```

**根因 100% 锁定**：不是 Olares 平台、不是 chart、不是 MCP 协议、不是 agent-zero 应用代码本身的 bug —— 是 **agent-zero 的内部并发模式把单实例 LLM 服务打爆**。

## C. 用户发现的关键配置错误

用户 5/20 一直说"我配的是 Qwen3:2.7B 当 embedding"。5/21 用户突然意识到这个**严重错误**：

> 之前 AgentZero 的 Embedding Model 一直是 qwen3:2.7B（**一个聊天模型**），不是真的 embedding 模型！

memory 插件每次都要做"伪 embedding"：拿一个 chat LLM 跑一段对话来"近似"向量。这意味着 14B / 2.7B 两个 chat 模型同时被压。改成 `qwen3-embedding:0.6b` 之后效果立竿见影。

> 教训（写文档时要醒目）：**Embedding 必须用真正的 embedding 模型**，不能拿 chat LLM 凑。

## D. 模型分配的迭代过程

四个手头模型：`qwen3:14b` / `qwen3.5:9b` / `qwen3:30b-a3b-instruct-2507-q4_K_M` / `qwen3-embedding:0.6b`。试了 3 种分配：

| 尝试 | OpenCode | A0 Chat | A0 Utility | A0 Embed | 结果 |
|---|---|---|---|---|---|
| #1 | 14B | 14B | 14B | 14B（伪 embed） | 雪崩，被 user 配错 |
| #2 | 14B | 30B-a3b | 9B | 0.6B 真 embed | A0 Chat 太慢（1m15s+），OpenCode 超时报 -32001 |
| **#3** | 14B | **9B** | **30B-a3b** | 0.6B 真 embed | **稳，单次 25s 完成** |

最终采用 #3：每个角色在独立 ollama pod，无队列共享；Chat 用 9B dense 保证速度；Utility 用 MoE（实际算力 3B）做简单 memory 任务。

assistant 犯过的错：在 #2 阶段否定了用户提出的"9B Chat + 30B Utility"，理由是"30B 当 Utility 浪费"。结果 #3 证明用户直觉是对的 —— 在客户端 60s 默认超时这个硬约束下，Chat 必须快，30B 当 Utility 不算浪费而是必要。

## E. OpenCode 集成的最终真相

### E.1 用户当场质疑救场

5/21 假定"OpenCode 是 bug"几次后，用户问："你怎么能确定是 OpenCode 的问题，而不是 AgentZero 的问题？"

assistant 承认从来没干净测过纯 curl 长 prompt。立刻做：

```
URL=".../mcp/t-$MCP_TOKEN/http/"
curl POST initialize → 200 + mcp-session-id
curl POST notifications/initialized → 0
curl POST tools/call send_message "列工具" → HTTP=200 size=5906 time=24.76s
```

**5906 字节完整 markdown，24.76 秒到位**。这一条 curl 把锅从"未知"定死到了 **OpenCode 客户端那一段**：

```
AgentZero 应用层 → MCP server → envoy → openresty → 公网 → [OpenCode 客户端] → UI
                                                              ↑ bug 在这
```

### E.2 OpenCode bug 的具体表现

之前观察过：
- agent-zero 日志显示 `MCP Chat message completed: <完整 markdown>`
- OpenCode 同时刻显示 -32001 RequestTimeout
- OpenCode 自动 retry 6 次（每次 OpenCode 都派 1 个新 MCP request 到 agent-zero）
- 6 个并发把 agent-zero 内部 LLM 队列打爆，雪崩

OpenCode bug **至少** 两点：
1. 默认 MCP 请求超时窗口在 60s 附近，而正常 agent-zero 响应可能 25-60s，刚踩边
2. 超时后立刻 retry，无 backoff，retry 还自动并发派多次

我们没办法改 OpenCode 源码，**只能用配置和提示词绕过**。

### E.3 最终可用的工作配置

```jsonc
// opencode.json
{
  "mcpServers": {
    "agent-zero": {
      "type": "remote",
      "url": "https://239ce90b.demo0002.olares.com/mcp/t-<MCP_TOKEN>/http",
      "enabled": true,
      "timeout": 300000  // ← 5 分钟，足够 agent-zero 慢响应
    }
  }
}
```

AgentZero 端：
- **memory 插件 OFF**（Settings → Plugins → 关闭 memory_*）
- Chat: qwen3.5:9b
- Utility: qwen3:30b-a3b
- Embedding: qwen3-embedding:0.6b

Prompt 模板（关键）：
```
请你调用 agent-zero MCP 服务器上的 agent-zero_send_message 工具，
把下面这段话原文转发给远程 Agent Zero 实例，然后把它返回给你的完整回复原样贴回来。
不要你自己回答，必须通过这个工具。
只能调用一次 agent-zero_send_message。如果一次没拿到完整结果，再回头问我，不要自己重复调。
转发内容: "<真正想问的话>"
```

最后那一句"只能调用一次"是**消除 OpenCode LLM 自作主张并行调用**的关键。

### E.4 稳定性实测

最终配置下连发 6 次"列工具"长 prompt，**5 次成功，1 次 504（第一次冷启动）**。agent-zero 日志显示：

```
$ kubectl logs ... | grep -E "received|completed" --since=10m
8 received, 8 completed (1:1 配对)
```

每次 completed 的内容首格式都不同（🛠️ / 🤖 / ## / **# 等）→ 证明是 LLM 独立调用拿到独立响应，不是 client retry 同一个请求。

## F. 几个被错走的路（写文档时要提醒读者别再踩）

1. **`mcp-remote` stdio 代理** —— 5/20 试过，短 prompt 通，长 prompt 仍然 -32001。assistant 今天又跳到这个建议被用户骂。**确认无效**。
2. **`type:"remote"` + `/http/` 末尾加斜杠 + `timeout: 300000`** —— 5/20 试过，长 prompt 仍 -32001。但今天 5/21 配上 memory off + parallel call off + 4 模型隔离之后，**这个组合反而是终配**。所以这条单独不行，叠加才行。
3. **顶层 `options.apiTimeout: 0` 没生效** —— 撤回，平台不写到 spec.options 是正常的。
4. **"OpenCode 30B-a3b 工具调用差"** —— 部分对，但本质问题是模型分配雪崩。换 14B 是因为不和 A0 抢，不是因为 30B-a3b 工具调用本身有大问题。
