## 二、Milestone 0（0.5 个月，0.6–0.8 人月）— `voice-model-puller` 镜像

> **关键性**：自家模型矩阵 ~74 个 app 共用同一个 API 容器（详 `技术设计文档.md` §7.1），新增 voice-* app 时**只**需要写 OlaresManifest + 改 ConfigMap 三个值。**不做这一件事**就会回到"每个模型应用各做一遍下载逻辑"的局面，跟"对用户完全统一 UX"的承诺矛盾。

### 2.0.1 工作内容

| 模块 | 内容 | 工作量 |
|---|---|---|
| 镜像核心逻辑 | Python + FastAPI + `huggingface_hub` SDK + aria2 + zstd 的下载/校验/解压链；门禁模型的 `waiting_for_hf_token` 状态机；引擎容器反代（按 `MODEL_CAPABILITY` 路由路径） | 0.4 人月 |
| OpenAI 兼容路径反代矩阵 | STT / STT-stream / TTS / TTS-clone / VAD / DIAR / TRANSLATE / ENHANCE / EMBED / ALIGN 各路径的请求/响应透传 + WS 透传 | 0.1 人月 |
| `/v1/models` / `/healthz` / `/readyz` / `/metrics` 标准端点 | 元数据返回 + 状态机暴露 | 0.05 人月 |
| CI + 上 GHCR + 多架构（amd64/arm64）build | 基础流水线 | 0.05 人月 |
| 文档 + cookbook | "新增一个 voice-* app 的 7 步指引"（对应 `技术设计文档.md` §7.4.3）| 0.05 人月 |

**小计**：约 **0.6 人月**，1 人 ≤ 0.5 个月可完成。

### 2.0.2 验收标准

1. 同一个镜像，喂三种 ConfigMap（`olares-cdn` / `hf-public` / `hf-gated`）能跑出三种行为；
2. 门禁模式下 `HF_TOKEN` 为空时 `/readyz` 持续返 503 并带 `license_url`；填上 token 后 30 s 内自动开始下载；
3. 反代上游引擎容器，TTS / STT / VAD 三类的 OpenAI 兼容请求全部走通（用 §7.4.2 的 `voice-engine-kokoro` / `voice-engine-faster-whisper` / `voice-engine-vad` 三个引擎做端到端验证）；
4. README 含"3 步装一个新 voice-* app"指引（含 `voice-tts-kokoro-82m-v2` 完整可复制粘贴 chart）。

### 2.0.3 与第一阶段的并行性

M0 与第一阶段 **可并行**（不同人）：M0 = 镜像 + 引擎规约；第一阶段 = 核心应用骨架 + provider 抽象。两件事到第二阶段才合流（M0 镜像作为第二阶段所有 voice-* app 的依赖件）。

## 三、第一阶段（1.5–2.5 个月，2–3.5 人月）

### 3.1 里程碑 1.1：核心应用骨架

**交付物**：一个新 Olares 应用 `voice-ai-hub`（暂名），含：

| 模块 | 内容 | 工作量 |
|---|---|---|
| API 网关 | OpenAI 兼容 4 端点（transcriptions / translations / speech / realtime）；扩展端点先做 5 个最常用（diarize / vad / detect-language / dictionaries / config）| 0.5 人月 |
| 配置中心 | SQLite + REST API + 简单加密；用户配置 schema 落实 | 0.3 人月 |
| 任务编排 | 同步路径 + 异步队列（RQ + Redis）+ WebSocket 直转发 | 0.4 人月 |
| Web UI MVP | 配置页 + 用例演示页（4 个：转录 / 翻译 / TTS / diarize）+ 任务历史 | 0.5 人月 |
| OlaresManifest + Helm chart | 单容器 + 单 sub-chart；dependencies 声明（ollamav2 / speaches / whisperwebuiv2 可选）| 0.2 人月 |

**小计**：约 1.9 人月

**推荐技术栈**：
- 后端：**FastAPI（Python）**（与 ASR 生态、ollamav2 接口语言一致；OpenAI 兼容方便）
- 配置 / 历史 DB：**SQLite**（足够；不必引 Postgres）
- 任务队列：**RQ + Redis**（轻量；Celery 太重）
- 前端：**SvelteKit** 或 **Vue 3**（与 Olares 已有应用风格匹配；体积小）

### 3.2 里程碑 1.2：接入已有本地 provider + voice-* / ollama-* 自动发现

**交付物**：核心应用能自动发现并使用已装的 `speaches` / `whisperwebuiv2` / `ollamav2`，无需用户手动填地址。

| 模块 | 内容 | 工作量 |
|---|---|---|
| 本地 provider 发现（现有 3 app）| `speaches` / `whisperwebuiv2` / `ollamav2` 的 OlaresManifest dependencies + 启动时探测 sharedEntrance | 0.2 人月 |
| **voice-* / ollama-* 自动发现机制**（详 `技术设计文档.md` §13.6）| `discover_voice_providers()` 扫 sharedEntrance + 读 `MODEL_NAME` / `MODEL_CAPABILITY` env，按统一规则注册 provider；门禁 app 跳过未填 token 的 | 0.3 人月 |
| Provider 适配器（现有 3 app）| 把 speaches / whisperwebuiv2 / ollamav2 的 API 包装成统一 provider interface | 0.2 人月 |
| 默认配置预填 | 第一次启动自动写入默认模型选择 | 0.1 人月 |

**小计**：约 0.8 人月

### 3.3 里程碑 1.3：接入三个海外 BYOK + 国内 Qwen 系列（已决策最优先）

**交付物**：用户能在 Web UI 里填 OpenAI / Deepgram / ElevenLabs 三家海外 key + **阿里 Qwen 系列**（Qwen3-ASR / 阿里云 NLS / 通义听悟 API + Qwen LLM API），立即可用。

> **2026-05 新进展提示**：OpenAI 已在 2026-05-07 推出 Realtime 三模型（`gpt-realtime-2` speech-to-speech / `gpt-realtime-whisper` 流式 ASR $0.017/min / `gpt-realtime-translate` 实时翻译 $0.034/min 70→13 语种），全部经 `/v1/realtime` 入口。第一阶段 BYOK 应一并纳入这三个 model 标识——这意味着第一阶段就能在 BYOK 路径上提供"流式听写 / 实时翻译 / voice agent"三大 SOTA 远程能力，自家 `voice-stt-live` 等只需提供"本地兜底 + 隐私优先"路径即可。

| 模块 | 内容 | 工作量 |
|---|---|---|
| 海外 Provider SDK 封装 | OpenAI / Deepgram / ElevenLabs SDK 引入 + 适配 | 0.3 人月 |
| **国内 Qwen 系列 SDK 封装**（已决策第一优先级）| Qwen3-ASR / 阿里云 NLS / 通义听悟 / Qwen LLM API；统一签名 + 协议转译 | 0.3 人月 |
| 凭证加密存储 | 用 Olares 集群密钥 + 字段级加密 | 0.2 人月 |
| 连通性测试 | `/v1/providers/test/{provider}` 端点 | 0.1 人月 |
| Web UI 凭证录入 | 配置页 provider 区块 | 0.1 人月 |

**小计**：约 1.0 人月

**其余国内 provider（火山豆包 → 讯飞 → 腾讯云 → 百度智能云）按合理顺序排在第二阶段**——它们 API 协议不一致、签名机制复杂，需要更长时间适配。

### 3.4 第一阶段完成后用户能做什么

- **打开 Web UI** → 一键启用本地已装的 speaches/whisperwebuiv2/ollamav2
- **填一个远程 key**（如 OpenAI）→ 用于 fallback
- **转录文件**：上传任意音频 → 出文稿 + 时间戳
- **翻译音频**：上传非英语音频 → 出英文文稿
- **TTS**：输入文本 → 出音频
- **流式 STT**：浏览器麦克风 → WebSocket 实时显示文字（如有 Deepgram key）
- **说话人分离**：上传多人音频 → 每段标 speaker

> **这就是 Auralwise 形态的最小可用版**。

### 4.5 第二阶段完成后用户能做什么（增量）

- **~54 个 voice-* model app 在 App Store 可装**——每个 app 用户体验和 `ollamabgem3567mv2` 一字不差（装→等→拿 BASE_URL+MODEL_NAME 走人）
- **中文场景** 真正可用（SenseVoice / Paraformer / Qwen3-ASR / 中文 LLM 摘要 + 国内 TTS）
- **会议记录**：开始一个会议 session → 浏览器实时录音 → 自动出纪要 + 行动项；**新增**：流式 Sortformer 实时显示当前说话人，+ MOSS-Transcribe-Diarize 端到端一步出转录 + 说话人 + 时间戳
- **播客生成**：输入主题大纲 → 自动生成多角色对话播客；**新增**：MOSS-TTSD 一步直出多角色音频（不需 LLM 改写脚本 → 多 voice 拼接两步走）
- **字幕生成**：上传视频 → 出多语种 SRT / VTT；**新增**：Qwen3-ASR-1.7B 替换 Whisper 作为中文 / 唱歌 / 多语默认
- **声音克隆 TTS**：录一段参考声音 → 用它读任意文本（声纹库由 hub 持有；TTS app 无状态）；**新增**：MOSS-TTS-Nano-100M（CPU 可用 + 克隆）/ Higgs Audio v2.5（强对话风格）/ IndexTTS 2.5（多语种）多档可选
- **听感型音频问答**（2026-04 新增能力域）：上传一段音频 + 问题 → 由 MOSS-Audio 直接产出含 prosody / 情绪 / 背景声线索的回答 / 摘要 / 推理
- **真正 S2S 对话**（2026-05 新增能力域）：录一段语音 → MOSS-Speech 直接出语音回答（不经文字中介）；**接近 OpenAI gpt-realtime-2 体验**
- **音乐理解 / 音效生成**（2026-05 新增能力域）：MOSS-Music 做音乐风格 / 段落分析；MOSS-SoundEffect 做文生音效（弱档候选）

8. 是否在第一阶段就上 Web UI，还是 headless 先行 → 影响约 0.5 人月（建议同步推，让用户感知到产品）

## 十、本章结论

1. **M0 + 第一 + 第二阶段 ≈ 14–20 人月、7–10 个月**就能把"Auralwise 形态的统一语音 AI 平台"在 Olares 上跑通，含 ~54 个 P0+P1 voice-* model app（含 1 个门禁 app）+ 中文场景 + 端到端用例（含听感型音频 QA / 摘要 + 真正 S2S 对话 + 多角色对话 TTS + 流式 diarization）。（2026-05 月度扫描后较 2026-04 第一轮上调约 4–6 人月，主因引擎 image 从 17 → 25 + P1 从 21 → 36 + 新增 2 能力域。）
2. **`voice-model-puller` 镜像（M0）是关键瓶颈件**——做不出来则后续 ~74 个 voice-* app 的"用户视角完全统一"承诺无法兑现。建议立项即派 1 人做，与第一阶段并行。
3. **桌面 / Android 客户端是长期路线**（第三阶段），不阻塞核心应用上线。
4. **现有 3 个 Olares 应用零修改复用**——第一阶段实际上没有"新建模型应用"的工作量。
5. **真正的工程重头是第二阶段**——~25 个引擎 image + ~54 个 P0/P1 voice-* app 是后续所有用例的物质基础；但靠 M0 把每 app 工作量压到 0.05–0.15 人月，总量可控。
