# 产品愿景与总体架构

> 这是统一语音 AI 平台课题的根文档。本文件先讲愿景与架构，下游各文档（独立模型应用清单、API 契约、落地路线、风险）都基于本文。

---

## 一、产品愿景（四条原则）

### 1.1 模型可配置、双形态供给

所有用到的模型（STT、TTS、VAD、说话人分离、翻译、LLM 后处理 等），都是**用户可配置**的；每个模型都有两种形态：

- **本地形态**：以"独立模型应用"形式安装到 Olares Market，与 `ollamav2` 同级（每个应用就是一个 OlaresManifest，提供 sharedEntrance 给本平台核心应用调用）
- **远程形态**：用户在配置里填供应商的 API key + URL，**BYOK** 调用远程服务

用户在配置中心里挑：
- 不同用例可挑不同模型（例如转录用本地 SenseVoice，TTS 用 ElevenLabs 远程）
- 同一用例可挑多模型并设 fallback（例如本地优先 → 失败回退云端）
- 全局默认 + 单次调用覆盖

### 1.2 核心 = API；界面是可选

核心应用主要提供**一套接口**，类似 Auralwise 的形态——任何客户端（Web UI、桌面 App、移动 IME、LarePass 内嵌、第三方应用、其它 Olares 应用）都通过这套 API 接入。

核心应用**自带一个轻量 Web UI**，作为：
- 配置中心（模型挑选、API key 录入）
- 用例演示 / 操控（用户可以直接在 Web UI 跑一个转录、TTS、播客生成）
- 任务历史 / 调试

界面是 UX 友好的"客户端默认实现"，但**不是核心**——任何用户都可以完全不用界面，只靠 API 接入。

### 1.3 质量优先级：英文 → 中文 → 实时性

- **英文优先**：所有用例的默认模型 / 默认配置，要保证英文质量到行业水准
- **中文不影响英文前提下越高越好**：中文支持是"加分项"，但不能为了优化中文质量牺牲英文（避免回到"国内大厂偏中文"的局面）
- **实时性越高越好**：能流式就流式；能 sub-second 就 sub-second；批量任务也要尽量短

具体到模型选择的指引（详见 `01_独立模型应用清单与配置层.md`）：
- 英文 + 实时：Deepgram Nova-3（远程）/ Parakeet TDT v3（本地）
- 中英双语 + 准确性：Whisper large-v3 + WhisperX（本地）/ AssemblyAI Universal-3 Pro（远程）
- 中文 + 实时：sherpa-onnx + **Paraformer streaming**（本地，SenseVoice 非原生流式可走 `streaming-sensevoice` fork）/ 阿里云 NLS 流式（远程）

### 1.4 核心应用独立存在；自家 ASR 应用体系独立规划；现有应用不被扩展

- **核心应用**是一个**全新**的 Olares 应用（暂名 `voice-ai-hub`，最终命名待定），与现有所有应用并存
- **本平台规划自家的 ASR / 语音 AI 模型应用矩阵**——按 **1 app = 1 个具体模型变体** 的颗粒度铺开 STT/STT-stream/TTS/VAD/diarization/translate/enhance/embed/align 八大能力域，约 40+ 个独立模型应用（详 `01_独立模型应用清单与配置层.md`）
- **不在 `whisperwebuiv2` 等现有应用上扩展任何新功能**——它们继续保留独立人设；本平台短期借力它们作为现成 provider，长期由"自家应用矩阵"成熟后作为默认路径
- 已有的 `whisperwebuiv2` / `speaches` / `ollamav2` 等**继续作为独立应用**存在（用户可以单独装、单独用），它们与核心应用的关系是**短期借力的现成 provider**——核心应用通过它们的 sharedEntrance 调用模型能力；但核心应用并**不替代**它们的独立用户体验，也**不向上推 PR 给它们加功能**
- 未来新建的"独立模型应用"也按此原则：每个都是可独立使用的应用 + 同时被核心应用调用

> **简言之**：核心应用是"语音 AI 总入口 + 总调度器"；**自家 ASR 应用矩阵**是"主力供应商"；现有应用是"短期借力 + 长期解耦"的兼容路径；三者解耦。

### 1.5 独立模型应用 UX 契约（与 `ollama*` 系列 1:1 对齐）

> **核心承诺**：从用户视角，**所有**自家独立模型应用（不管底层是 Whisper 还是 CosyVoice 还是 pyannote）都长成**完全相同的形状**，与已上架的 `ollamabgem3567mv2` / `ollamadeepseekr114bv2` 等 36 个 ollama 系列模型应用**用户体验完全一致**。

具体到四条硬约束：

1. **1 个 app = 1 个具体模型变体（含量化档位）**——不是"1 个 app + 一堆下拉菜单切模型"。`ollamaqwen3527bq4kmv2` 与 `ollamaqwen35a3budq4klv2` 这种"两个量化档各占一个 app"就是已建立的先例。
2. **App Store 安装条本身覆盖"镜像拉取 + 模型下载"**——pod readiness 阻塞到模型就绪为止。**不允许出现"装完打开还要再等几分钟首次下载"** 这种场景。
3. **装完用户能立刻读到 (BASE_URL, MODEL_NAME) 两个值**就能粘到任何其它应用里用。Service 命名规则、entrances 端口、env 暴露形态全部对齐 `ollama*` 范式（详 `技术设计文档.md` §七）。
4. **v2 拆分（`subCharts: [server (shared/clusterScoped), client]`）**——管理员装 server 一份，普通用户装 client 引用同一个 server，模型只下一次。

**唯一允许的偏离**：HuggingFace 门禁模型（如 `pyannote-3.1`）需要用户在 App 配置页粘一次 HF_TOKEN（OlaresManifest `envs` 标准机制）。**这是仅有的"用户视角"差异**，且仅出现在门禁模型上；其它一切（安装入口、安装动画、(BASE_URL, MODEL_NAME) 暴露形式）和非门禁模型一字不差。

为了让以上承诺技术上成立，需要做一个公司内部的 `beclab/voice-model-puller` 镜像（对照 `ollama*` 系列里的 `harveyff-olares-ollama` API 容器），由它统一处理：

- 从 Olares CDN（`cdn.olares.com/models/voice/...`）拉 tarball + md5 校验 + 解压
- 门禁模型走 HF + 用户填的 `HF_TOKEN`
- 主容器 readiness 阻塞到模型就绪
- 反代上游引擎容器到 `:8080` 暴露 OpenAI 兼容路径

这一个镜像服务全部 ~74 个 voice-* app（同 `harveyff-olares-ollama` 服务全部 36 个 ollama-* app 一样），是"完全统一 UX"的关键件。详见 `技术设计文档.md` §七.0 与 `03_落地路线与工作量.md` 里程碑 0。

## 三、核心应用的四大模块

### 3.1 API 网关层

- **OpenAI 兼容端点** + **扩展端点**两套
- OpenAI 兼容：`/v1/audio/transcriptions`、`/v1/audio/translations`、`/v1/audio/speech`、`/v1/realtime`（WebSocket，与 **OpenAI Realtime API 2026-05 三模型**对齐：`gpt-realtime-2` speech-to-speech / `gpt-realtime-whisper` 流式 ASR / `gpt-realtime-translate` 实时翻译 70→13 语种）
- 扩展端点：`/v1/audio/diarize`、`/v1/audio/detect-language`、`/v1/audio/vad`、`/v1/audio/align`、`/v1/meeting/sessions`、`/v1/podcast/generate`、`/v1/subtitles/generate`、`/v1/dictate/stream`、`/v1/voices`、`/v1/dictionaries` …（详 `02_用例覆盖与API契约.md`）
- 所有端点都支持 **每次调用覆盖配置**（在 request body 里指定 `model` / `provider` 参数）

### 3.2 配置中心

- 用户级配置：每个用户 `bfl.username` 独立配置树
- 配置 schema：分 `models`（按用例分类的模型选择）+ `providers`（远程 API key + URL）+ `preferences`（默认语种、质量档位等）
- 存储：核心应用内 SQLite + hostPath PVC
- 加密：远程 API key 用 Olares 集群密钥加密（参考 `ollamav2` 等的做法）

### 3.3 任务编排

任务类型按时长 / 模式分四种：
| 类型 | 例子 | 实现 |
|---|---|---|
| **同步短任务** | TTS 短文本、< 1 分钟音频转录 | HTTP 同步返回 |
| **同步流式** | 实时听写、实时翻译 | WebSocket / SSE |
| **异步长任务** | 1 h+ 音频转录、播客生成 | 任务队列（RQ + Redis）+ polling / Webhook |
| **流式 + 持久化** | 会议记录 | WebSocket 实时 + 完成后存档 |

### 3.4 多用户 / 历史 / 配额

- **多用户隔离**：所有任务、历史、配置按 `bfl.username` 隔离
- **历史**：默认保留任务记录 + 转录文稿 + TTS 输出（可在配置里关）
- **配额**：本地模型默认无限；远程 API 按 user-level token 限速（避免单用户用爆共享 API key）

## 四、设计原则

1. **API 优先**：界面是 API 的演示器；任何能在 UI 做的事都能通过 API 单独完成
2. **模型可换**：核心应用不绑死任何引擎；同一用例可热切换 provider
3. **自家 ASR 应用体系独立规划**：本平台的 ASR / 语音 AI 模型层主力是**自家应用矩阵**（按 1 app = 1 model 颗粒度铺开 ~74 个 voice-* model app，覆盖 STT 离线 / STT 流式 / TTS（含 dialogue 子能力）/ VAD / Diarize（含 streaming）/ Translate / Enhance / Embed / Align / Audio-LLM / **Audio-S2S** / **Sound-FX** 共 12 个能力域，详 `01_独立模型应用清单与配置层.md` §1.2），不依赖任何现成开源应用的扩展
4. **不在现有应用上扩展**：`whisperwebuiv2` / `speaches` / `ollamav2` 等保留独立人设；本平台短期借力它们作为现成 provider，但**不向它们提 PR / 加功能**；用户不强制必须装核心应用
5. **本地优先 / 远程兜底**：默认推本地模型应用；用户主动配远程后才走远程
6. **OpenAI 兼容是底线**：任何能用 OpenAI SDK 调的代码都能直接调本平台；扩展端点用清晰的命名空间隔离
7. **解耦不耦合**：模型应用之间互不依赖；核心应用通过 sharedEntrance 调用，不读对方的内部 DB / 文件
8. **本地化通过 sharedEntrance**：核心应用调本地模型应用时，走内部 sharedEntrance（不出集群）；BYOK 远程才走 `allowedOutboundPorts`

## 八、本课题在 Olares 全景中的位置

- **不替代** `whisperwebuiv2`（继续是"通用文件转录 GUI"）
