# 风险与开放问题

> 本文盘点统一语音 AI 平台课题在落地过程中的风险与待决策事项。按 6 类组织。

---

## 一、技术风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **统一 provider 适配层的复杂度** | 远程供应商 SDK 协议 / 鉴权 / 限流 / 错误码各异；统一适配工作量易爆 | 第一阶段只支持 3 家（OpenAI / Deepgram / ElevenLabs），后期按需增加；用 `litellm` 等成熟库做底座 |
| 2 | **流式 WebSocket 协议碎片** | OpenAI Realtime / Deepgram / AssemblyAI 各自 WS 协议不一样；统一对外难 | 对外只暴露"OpenAI Realtime 兼容"；对内做协议转译 |
| 3 | **本地 / 远程切换的状态丢失** | 长任务跑到一半切换 provider → 中间结果丢 | 任务级 provider 绑定（任务开始时锁定，不允许中途切）|
| 4 | **多用户 GPU 并发竞争** | 多人同时跑本地大模型转录 → GPU 排队严重 | 任务队列 + 优先级 + 配额；本地资源吃紧时自动 fallback 远程 |
| 5 | **远程 API key 泄漏** | 加密不彻底或 log 不慎打印 → 用户云账户被盗刷 | 用 Olares 集群密钥加密 + 字段级加密 + log 脱敏 + 定期扫描代码 |
| 6 | **本地模型应用版本不一致** | 用户装的 `speaches` 是旧版，核心应用调用新端点会 500 | 启动时探测版本 + 兼容性矩阵 + 配置 UI 提示用户升级 |
| 7 | **流式 STT 延迟在中文场景的明显回退** | Whisper 流式中文质量差 → 中文用户体验落差 | 中文流式默认推荐远程（火山豆包 / 阿里云 NLS）；本地 SenseVoice 流式标 "experimental" |
| 8 | **声音克隆 TTS 的语种 / 风格漂移** | XTTS v2 等本地克隆质量不及 ElevenLabs；用户期望被打破 | 文档明示能力边界；克隆类用例默认推荐远程 ElevenLabs |
| 9 | **音频文件上传 GB 级带宽峰值** | 用户上传 2GB 视频体验差 / 占满集群入口带宽 | 客户端先抽音轨 + chunk upload + 文件大小硬限 |
| 10 | **长任务 HTTP 超时** | Olares Nginx 3-5 min 超时，1 h 转录跑不完 | 强制走异步任务队列；HTTP 端点立即返 `task_id`，状态走 polling/SSE/Webhook |
| 11 | **核心应用单点** | 平台所有用例都经过它，宕机就全瘫 | 第一阶段单容器即可；第二阶段拆为 API gateway + worker 池 |
| 12 | **配置存储数据一致性** | 多写并发可能脏 | SQLite 已有事务足以；不用复杂 DB |

## 二、产品 / 定位风险

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 13 | **与 Auralwise / OpenAI Realtime 等的"差异化"不清晰** | 用户问"为啥不直接用 Auralwise" | 三个差异化点：(a) 自托管 / 数据不出家；(b) 本地模型应用与现有 Olares 生态共生；(c) 同时支持本地 + 远程双形态 |
| 14 | **与已上架的 `whisperwebuiv2` 边界不清** | 用户分不清"用核心应用还是直接用 whisperwebuiv2" | 文档明确：whisperwebuiv2 是"一次性文件转录 GUI 工具"；核心应用是"全用例 API 平台 + 多用例联动"；**本平台不在 whisperwebuiv2 上扩展任何新功能**，自家 `voice-stt-whisperx-*` 等矩阵成熟后两者并存共生，用户可挑 |
| 15 | **国内用户认知偏好"开盒即用"** | 让用户配 provider / 挑模型，国内用户不耐烦 | 默认配置开箱即用（本地 3 个应用 + 推荐远程一键加 key）；高级用户才进配置中心 |
| 16 | **可配置带来的"选择困难症"** | 26 用例 × 多 provider = 用户配置爆炸 | 提供"档位预设"（个人 / 中文优化 / 高质量 / 极速 等）；档位一键应用全部用例 |
| 17 | **核心应用与"独立模型应用"的拥有者关系** | 模型应用是 Olares 团队维护还是社区？维护节奏不一致影响用户体验 | OlaresManifest 中标 `submitter: Olares`；定期回归测试每个本地 provider |
| 18 | **声音克隆 / 多角色播客的合规风险**（已决策"做"，但风险仍在）| 用户用克隆克隆别人 / 生成假声明 | (a) 用户协议明示责任；(b) 声音克隆与 F-3 声纹注册端点耦合，要求用户上传"我的声音"先注册（默认不允许直接传任意片段，仅"已注册的 voice_id"可用于克隆，提高滥用门槛）；(c) AudioSeal 水印可选打开（默认开）；(d) Web UI 默认把克隆能力放在"高级模式"，不在新手引导首屏 |

## 九、本章结论

1. **风险总量 44 条**（2026-05 新增 #42 新模型纳入流程缺口 / #43 OpenMOSS 多家族 license 未明示 / #44 TEN-VAD 非竞争条款），按 6 类分布；与上一份"语音转录"课题（30+ 条）类似——大多是承袭过来。
2. **新增的关键风险**：统一 provider 适配层复杂度、流式协议碎片、配置选择困难症、与 Auralwise 差异化、本地模型应用版本协调。
3. **开放问题 10 项** 大多可分阶段决策，不必在立项点都定。
4. **两个原课题的关系**：从"两个独立产品立项"转为"统一平台下的两类用例"——原报告内容继续作为该用例的技术参考，不作废。
