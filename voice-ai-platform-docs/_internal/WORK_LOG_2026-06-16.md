## 一、音频模型改进计划 — 工程范围结论(已收敛)

**要实现"音频模型和场景",只需改两个仓:**

1. **`llm-init`**:serving 加音频引擎种类(现仅 `ollama/vllm/llamacpp/sglang` 文本引擎)、`MODEL_MODE` 放开(现仅 `chat|embedding` → 加 `stt/tts/vad/diar/...`)。
2. **`llm-gateway`**:仓内 mode/catalog 枚举放开 + 接上音频数据面(`/v1/audio/*` + 必要的透传/流式)。今天它一条音频路由都没有。

**其余一律不碰**(验收标准:谁要为"每加一种音频能力"去改这两个仓以外的代码,就是抽象漏了):
- 新音频模型 app = **产物/数据**(按 `ollamallmbasev3` 那样 `templateOnly` 克隆),不是改工程。
- `llm-register`(Dify 移植目录)= **已废弃**,半年没动,不是运行时依赖;mode 词表在 gateway 自己仓里。
- Market 的 `/llm-providers`、`olares-cli` = 通用平台件,与音频无关。

**llm-init 改动量估算**(已实地读代码核过):
- T0 仅可发现(只扩 MODEL_MODE + metadata,引擎仍在 app 自带容器):~150–350 行生产 + 同量测试,2–4 天。
- T1 让 llm-init serve 一个音频引擎族:~600–1300 行 + 同量测试,1–3 周。
- 关键抽象:`internal/adapter` 的 `Adapter` 接口(proxy 型是反向代理);加引擎要扫 ~6 处 switch(`config_enums.go`/`engine_args.go`/`config_load_engine.go`/`controlplane/endpoints.go`/`config_validate.go`/`obs/log.go`)。
- 流式(`stt_stream`/`audio_s2s`)是另一笔账:数据面 `mount.go` 现在纯 HTTP ServeMux,无 WebSocket。
- 本仓测试纪律极严,测试代码≈生产代码 1:1。
- **第一步最划算:T0**——真正大头其实在 gateway 音频数据面,不在 llm-init。

## 二、LLM Gateway 市场功能排障(今天的主战场)

### 现象
界面"上游供应商 / 从 Market 安装"打不开,先报 `market_upstream_unreachable (503) … context deadline exceeded`。

### 排障链路与结论
1. **配置**:`llmgatewayv3` configmap 里 `market.mock=false`、`base_url=http://appstore-svc.os-framework:81`(指真实市场)。
2. **连通性测试**(在 gateway 后端 pod 内用 `kubectl debug` + curlimages/curl):DNS 正常解析到 `10.233.22.165`,但 `Trying …:81` → **Connection timed out after 5003ms**。→ 网络层被隔离。
3. **网络策略定位**:
   - 用户命名空间 `llmgatewayv3-shared` 的 4 条 NetworkPolicy **全是 Ingress-only**,`Not affecting egress` → gateway 出站根本没被限制。
   - 拦截在目的地:`os-framework` 的 `os-system-np`(PodSelector 为空=管所有 pod,含 appstore=`market-deployment`,label `app=appstore`)入站**只放行** `ns-type=system|user-internal|protected` + kube-system/kubesphere-system + os-framework 自己。普通用户共享命名空间不在内 → SYN 被丢 → 超时。
4. **官方临时解法**(来自用户给的文档 `~/Downloads/Market 返回 LLMGatewaySupported 应用列表.md`):
   > 新权限还没上线;gateway 访问 lldap/nats/appstore 需给命名空间打标签 `bytetrade.io/ns-type=system`,再重启 Pod。
5. **已执行并见效**:
   ```bash
   kubectl label ns llmgatewayv3-shared bytetrade.io/ns-type=system --overwrite
   kubectl rollout restart deployment -n llmgatewayv3-shared
   ```
   → 报错从"超时(503)"变为 **`market_catalog_failed: 404 page not found`**,且 UI 出现"从 MARKET 安装"按钮。**网络这关已通。**

### 当前卡点(明天的起点):接口契约不一致 → 404
实地读 gateway 后端代码确认:
- `backend/internal/olares/market_client.go` 写死 `GET /app-store/api/v2/applications?category=AI`(注释明写 "proxies **olaresmock**")。
- 整个后端**没有 `llm-gateway-supported` 字样**——连仓库 HEAD 都没对接真实市场新接口。

而真实市场(文档)实际提供的是:
```
POST http://appstore-svc.os-framework:81/app-store/api/v2/apps/llm-gateway-supported
header: X-Bfl-User: <olaresID>
```
返回的是声明了 `LLMGatewaySupported` 的应用列表(= `ollamallmbasev3 / vllmllmbasev3 / sglangllmbasev3 / llamacppllmbasev3 / ollamav3` 这几个 llm base,就是 UI 里可"选/装/克隆"的"模型")。

**结论:gateway 后端(v2.0.3)还停留在 olaresmock 契约(`GET /applications`),真实市场已换成 `POST /apps/llm-gateway-supported`,两边没接上。** 这不是配置/标签能修的,是后端代码改动 + 出新镜像。

## 三、关键事实备查

- gateway 是 v3 应用 `llmgatewayv3`,装在用户共享命名空间 `llmgatewayv3-shared`;镜像钉死 `beclab/llm-gateway-backend:v2.0.3` + `-frontend:v2.0.3`。
- gateway 的 helm 包(`deploy/helm/llm-gateway/README.md`)本意是**装进 `os-framework`**(系统命名空间,与市场同处),所以才默认能连市场;打成用户 app 装进用户命名空间才撞上隔离。
- 镜像发布:`llm-init`/`llm-gateway` 的 CI 只在 push-to-main / `v*` tag 时推 `docker.io/beclab/*`;测试分支 push 不发布(隔离安全)。
- 真实市场返回契约样例已存于用户文档 `~/Downloads/Market 返回 LLMGatewaySupported 应用列表.md`。
- 安装契约的 6 个接口(olaresmock 实现的那套):`GET /applications`、`POST .../{name}/{install,upgrade,uninstall}`、`GET /tasks/{id}`、`GET /llm-providers`;安装状态机:`available→pending→downloading→installing→initializing→running`(到 running 才有 `shared_entrances_url`)。
