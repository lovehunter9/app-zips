> 承接 `WORK_LOG_2026-05-26.md`（统一语音 AI 平台综合调研）。今天是对一篇**新的需求文档**做分析，

## 〇、输入：用户给的「音频模型改进计划」原文要点
- **背景**：音频任务需多模型组合（如转录 = VAD + ASR + Translate + Diarize），每类又有多个可选模型；
  要求**模型托管与应用调用分开**。
- **基本思路**：
  1. 通过 **LLM-Init** 下载模型，各模型用自己官方仓库的方式提供接口；LLM-Init 对不同类型模型提供
     **统一接口**，并保证不同类型模型间**输入输出可组合**。
  2. 通过 **LLM-Gateway** 聚合。
  3. **olares-cli 调用为一等公民**，UI 层主要看状态。
- **时间表（挂 Olares 核心版本号，按业务场景驱动）**：
  - 1.12.7：Plaud 会议转录 → `stt`(离线) + `vad` + `diar`
  - 1.12.8：Typeless 语音输入 → `stt_stream`
  - 1.12.8：YouTube/播客视频转录 → `translate` + `tts` + `tts_clone`
  - 1.12.10：数字人场景
  - 之后：同品类铺更多模型；再之后：支持公有云同类模型
- **模型能力（15 个，= 接口契约的"类型表"）**：
  `stt / stt_stream / tts / tts_clone / tts_dialogue / vad / diar / diar_stream / translate / enhance / embed / align / audio_llm / audio_s2s / sound_fx`

## 一、我的核心判断
这篇是对 `voice-ai-platform-docs` 那套规划的**再抽象/收敛**，换成更工程化、更贴 Olares 底座的视角。
一句话：把音频能力做成**三层解耦**——**托管(LLM-Init) / 聚合(LLM-Gateway) / 调用(olares-cli 为主)**，
核心诉求是让"多个异构模型串成一条流水线(VAD→ASR→Diarize→Translate)"变得**可配置、可替换、可组合**。

## 二、三层架构 ↔ 现有资产映射
| 文档说法 | 实质职责 | 对应现有 |
|---|---|---|
| LLM-Init | 按各模型官方方式跑起来，但对外按"能力类型"统一接口、保证 I/O 可拼接 | ≈ `voice-model-puller` + ~25 engine image + ~74 `voice-*` app |
| LLM-Gateway | 聚合托管模型成一套对外接口、做路由/选型 | ≈ `voice-ai-hub` 的 API 网关角色（也可能想复用 Bifrost）|
| olares-cli（一等公民）| 主消费入口；UI 仅看状态 | **新强调**（旧规划是"API + Web 配置中心"，这里 UI 降级、CLI 升级）|

## 三、相对旧规划(README)的三点实质变化（待确认是否有意）
1. 把"核心应用 voice-ai-hub"进一步拆成 **Init / Gateway 两层**，托管 vs 聚合职责更清。
2. 交付节奏**挂 Olares 核心版本(1.12.x)** 而非"app 上架里程碑" → 读起来像**平台级**工作（olares-cli、
   LLM-Init 当平台原语），量级远大于"上架一个 app"。
3. **CLI 优先、UI 退居其次** → 产品形态从"带 Web 配置中心的 hub"转向"CLI/API 为主"。

## 四、真正的难点（linchpin）
"LLM-Init 提供统一接口 + 保证类型间 I/O 可组合" 是命门也是最难：
- 需为每个**能力类型**定义**规范化 I/O 契约**(canonical schema)，让 VAD→ASR→Diarize→Translate 能拼；
- 又要"用各模型官方跑法" → 每个模型一层 **adapter** 翻译成统一契约。**adapter + 契约设计 = 工作量与风险的真正所在**，
  puller/engine-image 只是载体。
- 那 15 个能力词就是这套契约的"类型表"，和 README 的 12 能力域完全对得上（只是把 clone/diar_stream 拆出来）。

# 2026-06-16 代码级深挖：把 §五 的疑问落到实证

> 数据来源：`beclab/llm-gateway`、`beclab/llm-init`、`beclab/llm-register`、`beclab/apps`（gh api 实读）。

## 8.1 三个组件的"代码真相"
- **llm-init**：模型下载 / 文本 LLM serving 的 sidecar。两模式：serving（text LLM，吐 `/v1/*`）+ download-only（其它类型只下载到共享 HF cache，不serve）。**它不提供 vad/diar 等"能力统一接口"**——只管把模型放到位。
- **llm-gateway**：Olares 原生、框架级 OpenAI 兼容网关 + Quasar 管理 UI。
  - `ModelMode` 枚举（`internal/providers/model.go:377+`）只有 10 种：
    `chat / completion / embedding / rerank / moderation / **tts** / **stt** / image_generation / **audio_speech** / responses`。
    → 音频相关只有 **stt / tts / audio_speech(≈realtime s2s)** 三个；**vad/diar/align/enhance/translate/clone/dialogue/stream/audio_llm/sound_fx 这 ~11 个能力在 schema 里根本不存在**。
  - **数据面只挂了** `/v1/chat/completions`、`/v1/embeddings`、`/v1/models`（`router.go`）。`stt/tts` 被测试标注 "Dify naming, not GA" → **连 stt/tts 现在都还没实装**。
  - 管理面很全：provider/model CRUD、market-catalog passthrough、market-install/upgrade/uninstall、default-models、spend/audit/quota。
  - 明确**不做运行时编排/链式调用**（ARCHITECTURE ADR-5 / §2.6）。
- **llm-register**：**就是 Dify**（`pyproject` 里 `name = "dify-api"`，整套 Dify 依赖 + `controllers/console|openai` + `core/model_runtime`）。即 Go 版 gateway 的"上游 catalog / model_runtime 来源"。它的能力词表（llm/embedding/rerank/speech2text/tts/moderation）正是 gateway 那 10 种 mode 的出处——**同样没有 vad/diar 等**。
- **olares-cli**：纯系统运维（install/node/gpu/backups…），**无任何模型调用 / 流水线命令**。

## 8.2 "1 模型 = 1 app"的确切契约（老板那句话的落地形态）
对比两个真实 app：
- **新范式（gateway 可发现）= OAC `apiVersion: v2`**：以 `ollamaqwen314bv2` 为样板：
  - `sharedEntrances:`（`host: sharedentrances-api`, `port: 0`, `invisible: true`, `authLevel: internal`）= **注册进集群/网关的发现钩子**；
  - 伞 chart + 双子 chart：`...server`(`shared: true`，集群级、admin 装一次) + `...client`(per-user 引用)；
  - `options.appScope.clusterScoped + appRef`、`dependencies` 把 client 锁到 server → **共享 app 机制**；
  - 对外是 **OpenAI 兼容端点**（ollama 的 `/v1/...`）。
- **旧范式（现存音频 app）= 独立 Gradio webUI**：以 `cosyvoice` 为样板：
  - `olaresManifest.version: 0.10.0`（非 v2）、**只有普通 `entrances`**（gradio 8080→7860）、跑 `webui.py`；
  - 用**老的 `beclab/downloader-init:v0.1.0` Job** 下模型（不是 llm-init）；
  - **没有 sharedEntrances、没有 OpenAI API、不进 gateway**。

**结论**：现存音频 app（cosyvoice/fishspeechv2/whisper*/speaches…）全是"给人点的独立 webUI"，要进网关被组合，需要**按 v2/sharedEntrances 范式重做成 OpenAI 形状的服务端点**。`apps` 仓 308 个 app 里 **v3 范式只有 `acestepv3` 一个** → **音频侧的网关化几乎是绿地**。

## 8.3 §五 五个疑问的实证答案
1. **LLM-Gateway 是谁？** → 已存在的 `beclab/llm-gateway`（Go + Quasar），不是 Bifrost、不是 voice-ai-hub。它**只吃 OpenAI 形状**，且现仅 GA chat+embeddings。
2. **编排归谁？** → gateway **明确不做**（ADR-5）。olares-cli 现也不做。→ **编排目前无主**，正好对上老板"每个模型做成 app 自己组合"=**调用方/CLI 侧编排**。
3. **LLM-Init 是不是 voice-model-puller 改名？** → 是同类职责的**已存在平台原语**，旧规划里要新造的 `voice-model-puller` 被它取代/吸收。
4. **olares-cli 能调 app 业务端点吗？** → **不能**，纯运维。要 CLI 一等公民就得给它加"音频调用/流水线"命令面（重）。
5. **平台级还是 app 级？** → 真相是**混合**：模型托管走 **app 级**（每模型一个 v2 app）；统一接口/编排/CLI 一等公民是 **平台级**（gateway schema 扩展 + cli 命令面），后者重。

## 8.4 三个能力的"归属"已清晰
- **stt / tts / audio_speech**：gateway schema 已有槽位（虽未 GA）→ 可走"扩展 gateway 数据面"路线。
- **其余 ~11 能力（vad/diar/align/enhance/translate/clone/dialogue/*_stream/audio_llm/sound_fx）**：gateway 无槽位、Dify 无词表 → 只能落在 **app 自有端点 + 调用方编排**，短期不指望 gateway 统一。

## 8.5 推荐的第一步（见对话）
切入点 = **1.12.7 Plaud 会议转录场景**里**做出第一个 v2 范式的音频模型 app（离线 STT，如 whisper/parakeet）**：
把现有 `whisperservicev2` 这类从"webui/旧 downloader"重做成 `apiVersion: v2` + `sharedEntrances` + OpenAI `/v1/audio/transcriptions` 形状，
作为"1 模型 = 1 app + gateway 可发现"的**样板桩**。它同时验证：契约形状、共享 app 机制、(可选)llm-init download-only 接入。vad/diar 第二步再以同范式各做一个 app。

# 2026-06-16（二）订正：平台已用 **v3**，且音频链多数已落地（读 `~/aboveos/terminus-apps`）

> 用户明确：不再做 v2，只做 **v3**。重点参考 `speachesv3`。上面 §8.5 的"做 v2 STT 桩"作废——**那根桩其实已存在**。

## 9.1 v3 应用范式（以 `speachesv3` 为黄金样板，逐项）
- 头部：`olaresManifest.version: '0.12.0'` + **`apiVersion: 'v3'`**。
- **单一扁平 chart**（v3 把 v2 的 `xxxserver`/`xxx` 子 chart 拍平成一个 chart）；用 **`workloadReplicas`** 平铺声明每个 Deployment（键 == Deployment metadata.name == values `workloads.<name>`）。
- **`sharedEntrances`**（`host: sharedentrances-<x>`, `port: 0`, `invisible: true`, `authLevel: internal`）+ 一个**同名 Service `sharedentrances-<x>`**（80→引擎端口）= **集群级/网关发现钩子**。
- **`options`**：`shared: true` + `onlyAdmin: true` + `allowMultipleInstall: true` + `appScope.clusterScoped: true` + `appRef:[旧app]` + `conflicts:[旧app]` → 标准"admin 装一次、全集群引用"的共享 app。
- **`accelerator:` 多模式块**（`nvidia` / `nvidia-gb10`(Spark 统一内存，GPU 从 requiredMemory 切) / `cpu`），每模式各自 req/lim/GPUMemory。这是 v3 资源校验单位（Σ 所有容器 requests/limits，initContainers 不计）。
- **模型存储 = 跨 app 共享 App Common**：`appCommon/huggingface` 挂到固定 `/cache/hf/hub`，标准 HF `models--owner--repo/snapshots/<sha>/` 布局，全 HF 系 app 去重共享。
- **下载 = `llm-init` download-only**（独立 Deployment，不是 initContainer）：`ENGINE_KIND=""`(nullengine)、`MODEL_SOURCE="hf://A,hf://B"`(逗号多源，首个 ROLE=main)、镜像 `beclab/llm-init:v1.2.x`、暴露 `/livez`(进程)`/readyz`(模型齐)。
- **就绪 gating 在 nginx 入口层**：引擎立刻起(不等模型)→ pod Ready → Olares 发布 entrance；nginx 用 `auth_request → download-svc/readyz` 决定：模型没齐就反代 llm-init 的**下载看板**(注入轮询脚本，齐了自动 reload 进 app)，齐了才反代引擎。
- **HF 镜像/token**：v3 禁止模板里直接引用 `OLARES_USER_*`；`envs` 里声明 app-local 名 + `valueFrom.envName: OLARES_USER_HUGGINGFACE_SERVICE/TOKEN`，模板用 `.Values.olaresEnv.HF_*`。
- 引擎镜像用上游原版，启动时跑 **runtime hotfix**（speachesv3 用内联 python 打一堆补丁：whisper-1 别名、中文 TTS misaki、CJK emoji 等）。

## 9.2 关键订正：Plaud 链 + 多数能力**已经有 v3 app 了**

## 9.3 真正没解决的 = 计划的硬核（不是打包，是"统一接口 + 可组合"）
- **接口不统一**：speachesv3=OpenAI 形状；whisperservicev3=bespoke `/service/*`；mtranserver=自有。计划要的"LLM-Init 对不同类型统一接口 + 保证 I/O 可组合" **目前未达成**——每个 app 各说各话。
- **组合方式不统一**：whisperX 把 transcribe+vad+diar+align+combine **打包进一个 app 内部串**；而老板说"每个模型做成一个 app 再组合"。**这是真实冲突**：bundle(whisperX 式) vs atomic(一能力一 app、外部编排)。这条决策没拍 → 是第一步真正该定的东西。
- **编排无主**：跨 app 串 VAD→ASR→Diar→Translate 仍没有标准载体（gateway 明确不做；olares-cli 不做）。

## 9.4 重定位的"第一步候选"（v3 语境，待用户拍方向）

# 2026-06-16（三）硬约束："尽量不打镜像、用公开/已有资源"——决定一切

> 用户工作原则：能用 Olares 已有 + 公开资源就别自建镜像；必须自建的，要充分证据细谈。

## 10.1 这条原则本就是 v3 房规（实证）
现有 v3 app 镜像来源全是**公开上游镜像**（顶多 mirror 进 beclab 命名空间）：
- `mtranserverv3` → `docker.io/xxnuo/mtranserver:4.0.33`（**裸用公开镜像，未 retag**）
- `openedaispeechv3` → `beclab/aboveos-matatonic-openedai-speech`（= 公开 `matatonic/openedai-speech` mirror）
- `fishspeechv3` → `beclab/harveyff-fishaudio-fish-speech`（= 公开 fish-speech mirror）
- `whisperservicev3` → `beclab/pavelzbornik-whisperx-fastapi`（= 公开 whisperX-FastAPI mirror）
- 基础设施：`beclab/aboveos-bitnami-openresty`、`beclab/aboveos-busybox`（公开 mirror）
→ **v3 的价值 = 封装公开镜像，不写模型服务器。** 用户原则与现状一致。
另：**`localai` 已在 beclab/apps 市场**。

## 10.2 结构性真相（"从哪下手"的真因）
**已做成 v3 的能力 = 恰好都有"公开服务器镜像"；还缺的能力 = 恰好只有"库、无干净公开服务器"。缺口不是没人做，是"不打镜像就做不了"。**
"bundle vs atomic"也非哲学选择——**被公开镜像的供给决定**（whisperX 是 bundle 因为那个公开镜像就是 bundle）。

## 10.4 结论 & 推荐
- **VAD 当首桩不合适**：无干净公开镜像（仅 LocalAI 全家桶）、且验不到 llm-init（违背选它的初衷）。
- **桶 C（vad/diar/align/enhance/embed）= 真正难啃的，恰恰因为它们没公开服务器**；要原子化只能"接受薄 wrapper 镜像"或"用 LocalAI/bundle"。→ **这是要给老板拍的核心裁决**（不打镜像 ⇒ 这几个能力做不出原子 app）。
- **最佳首桩 = 流式 STT（WhisperLive 公开镜像）**：不打镜像 ✓、HF 系验得到 llm-init ✓、真缺口 ✓、OpenAI 兼容 + WS ✓、对 Typeless(1.12.8) 直接命中、对 Plaud 也有用。
- **对 Plaud 1.12.7 的诚实判断**：缺的正是 vad+diar（桶 C）→ "完全不打镜像 + 原子化"做不全；要么 LocalAI(vad)+某 diar 全家桶（乱），要么接受薄 wrapper/whisperX bundle。**此点需老板定。**
