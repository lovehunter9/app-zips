## 二、定位长音频对齐塌陷的真正病根（不是玄学）
- 现象：整段转写 >~5 分钟音频，文字记录从某一时刻起「几十段全挤在同一秒」，词时间退化成 0.2s 均匀兜底值。
- 用户关键澄清（务必记牢）：**STT（Qwen3-ASR）不返回任何时间戳**，只给文本；**ALIGN 是唯一时间来源**；
  DIAR 只给说话人。所以严禁用「按字数平均切」去分窗——那是一切错误的根源。
- 查 Qwen 官方口径：`Qwen3-ForcedAligner-0.6B` 只在 ~270s 内可靠，超过后索引饱和、LIS 单调化把后面所有词
  压到一个时间戳（「同一秒」签名）。官方做法＝迭代重对齐，检测饱和点并在此切窗。
- **实现 `alignLong`（饱和切窗）**：每窗喂 >一窗的文本（over-provision），`reliableAlignEnd` 检测塌陷平台、
  只保留可靠前缀，从最后一个可靠词的 END 时间 + 剩余文本续对下一窗。移除旧的 `splitTextN`（按字数比例切）。

## 三、抓出 alignLong 的致命字符偏移 bug（本日核心修复）
- 盘上 23:24 用新代码重转的记录仍从 `645.86` 起整条尾巴塌平 → 说明后半段 unit 没能映射回 `fullText`。
- 用**该记录真实文本**逐趟复现（探针打印 `a/cOff/part/units/k/nextA/nextC`），抓到元凶：
  ```
  pass4 a=634.9 cOff=11746 partLen=6609 units=1160 k=340 keptEnd=746.98  nextC=18355 ← 字符偏移跳到文本末尾!
  → 循环因 cOff 到头而终止，音频 747→1012s(4分钟)从未对齐 → 尾部被 buildCharToTime 全钉在 645.86
  ```
- 根因：饱和窗口的 `part` 是重复短词极多的尾巴（So/It/the…），我却对**全部 unit（含塌陷的垃圾尾）**跑
  `mapUnitsToRef`，`indexOf` 在重复词上一路越级匹配 race 到文本末尾，`nextC` 跳飞。初版探针「没事」只因当时
  用旧文本（本身就是对齐器产出的），匹配太顺；真实新 STT 文本 tokenization 一变就露馅。
- **修复两条**（`server.js`）：
  1. 只映射**可靠前缀** `u.slice(0, k+1)`，绝不碰塌陷垃圾尾（先算 `k` 再映射）。
  2. 新增 `mapUnitsBounded`：token 只允许在游标前方 `slack=48` 字符内匹配，短词不得跨越式跳；无近匹配则游标最小前进。
- 同音频复现对比：pass4 `nextC` 18355→13712；覆盖时长 746s→1005.9s（≈全长1012）；非单调 0；最大塌陷 run 巨大→9。
