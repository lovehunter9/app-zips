## 二、定位长音频对齐塌陷的真正病根（不是玄学）
- 现象：整段转写 >~5 分钟音频，文字记录从某一时刻起「几十段全挤在同一秒」，词时间退化成 0.2s 均匀兜底值。
- 用户关键澄清（务必记牢）：**STT（Qwen3-ASR）不返回任何时间戳**，只给文本；**ALIGN 是唯一时间来源**；
  DIAR 只给说话人。所以严禁用「按字数平均切」去分窗——那是一切错误的根源。
- 查 Qwen 官方口径：`Qwen3-ForcedAligner-0.6B` 只在 ~270s 内可靠，超过后索引饱和、LIS 单调化把后面所有词
  压到一个时间戳（「同一秒」签名）。官方做法＝迭代重对齐，检测饱和点并在此切窗。
- **实现 `alignLong`（饱和切窗）**：每窗喂 >一窗的文本（over-provision），`reliableAlignEnd` 检测塌陷平台、
  只保留可靠前缀，从最后一个可靠词的 END 时间 + 剩余文本续对下一窗。移除旧的 `splitTextN`（按字数比例切）。

## 三、抓出 alignLong 的致命字符偏移 bug（本日核心修复）
- 盘上 23:24 用新代码重转的记录仍从 `645.86` 起整条尾巴塌平 → 说明后半段 unit 没能映射回 `fullText`。
- 用**该记录真实文本**逐趟复现（探针打印 `a/cOff/part/units/k/nextA/nextC`），抓到元凶：
  ```
  pass4 a=634.9 cOff=11746 partLen=6609 units=1160 k=340 keptEnd=746.98  nextC=18355 ← 字符偏移跳到文本末尾!
  → 循环因 cOff 到头而终止，音频 747→1012s(4分钟)从未对齐 → 尾部被 buildCharToTime 全钉在 645.86
  ```
- 根因：饱和窗口的 `part` 是重复短词极多的尾巴（So/It/the…），我却对**全部 unit（含塌陷的垃圾尾）**跑
  `mapUnitsToRef`，`indexOf` 在重复词上一路越级匹配 race 到文本末尾，`nextC` 跳飞。初版探针「没事」只因当时
  用旧文本（本身就是对齐器产出的），匹配太顺；真实新 STT 文本 tokenization 一变就露馅。
- **修复两条**（`server.js`）：
  1. 只映射**可靠前缀** `u.slice(0, k+1)`，绝不碰塌陷垃圾尾（先算 `k` 再映射）。
  2. 新增 `mapUnitsBounded`：token 只允许在游标前方 `slack=48` 字符内匹配，短词不得跨越式跳；无近匹配则游标最小前进。
- 同音频复现对比：pass4 `nextC` 18355→13712；覆盖时长 746s→1005.9s（≈全长1012）；非单调 0；最大塌陷 run 巨大→9。

## 八、残留问题（下周一强化）：逐词高亮「突进→卡住」(burst-then-gap)
用户实测（1.0.8，8090 重转 Vault，记录 `60921671`，203 段、时间已单调）反馈：某些句子字幕高亮会
**飞快向下滑一串词、然后停在某个词上等好久**，直到音频真到那个词才继续。示例（截图取证）：

- 13:44 「So maybe we're doing dynamic credentialing for our message queues, but this kind **of** goes on.」
  逐词：`So@824.58 … but@827.22 this@827.7 kind@827.78 of@827.94` → **`goes@831.38`**（`of`→`goes` 凭空空 3.44s）。
  高亮 824.58→827.94 一口气冲到 `of`，随后卡住到 831.4。
- 14:35 「**And this way**, you're constantly moving…」逐词：`And@875.517 this@875.745 way@875.86` →
  **`you're@878.9`**（`way`→`you're` 空 3.04s）。三词挤在 0.34s，随即停住。

### 数据扫描（全片 3261 词）
写脚本统计「相邻词间隔 ≥2s」的位置，共 **16 处**，每处都伴随「前 5 词被压在很短时间内」的 burst 特征：
```
42.08(2.24s, 前5词1.44s) 45.92 49.60 56.72(前5词0.59s!) 262.96 412.46 419.14
508.74(2.88s) 518.82 634.90 722.68 757.86(前5词0.88s) 765.70 780.82
827.94(3.44s, 前5词1.32s ←用户案例) 875.86(3.04s, 前5词0.60s ←用户案例)
```

### 成因判断（两类，需分别处理）
1. **对齐器自身的局部微塌陷**（主因，用户两例都属此类，且都在 pass5 窗口**内部**、非接缝）：
   Qwen ForcedAligner 在停顿/换气处会把前面一串词的时间**前挤成 burst**、再留一个大空档，本质是
   全局塌陷的「轻症局部版」。我们目前**原样保留对齐器逐词时间**（`finalizeWords` 只做钳位+严格单调，
   不识别 burst、不平滑大间隔），前端卡拉OK高亮如实渲染，就表现为「突进→卡住」。
2. **窗口接缝处的边界词**（次因）：`alignLong` 每窗接续时，下一窗首词起始＝上一窗最后可靠词的 END(`a`)，
   若真话在此处有停顿，边界词会拿到 `a` 而与后词间形成间隔（如 `634.90s` 恰为 pass3→pass4 接缝）。
   `reliableAlignEnd` 只裁**窗尾**塌陷平台，不管**窗内**微塌陷。

### 下周一强化方向（择一/组合，先不动）
- **去 burst（de-burst）**：检测「N 个词被压在异常小的 dt 内（如 >4~5 词/秒）且紧跟 ≥2s 间隔」的段，
  把这串词**在 [burstStart, 下一词起始] 区间内重新均摊**（用那段空档时间把突进的词铺开），使高亮匀速推进。
- **区分真停顿**：大间隔可能是真静默（此时高亮该停）。用 VAD/能量或已提取的 16k WAV 在该区间做一次
  静默检测——**仅当该处并非真静默**时才判定为对齐 burst 并平滑，避免把合理停顿也抹平。
- **窗内塌陷检测**：把 `reliableAlignEnd` 的平台检测从「只裁窗尾」扩展为「窗内多平台」识别，对内部平台做局部重摊。
- **接缝重叠**：`alignLong` 相邻窗加少量 overlap（如 5~10s），用重叠区校正边界词时间，消除接缝间隔。
- 复现脚本已就绪（`/tmp` 探针思路：flatten 逐词 start → 找 ≥2s 间隔 + 前窗 burst 密度），可固化到 docs 便于回归。

## 九、测试机复现「算法不稳定」（下周一细查，今日仅记录，未查未修）
1.0.8 部署到测试机后，用户重转同一条 Vault，逐词高亮仍出问题，且**比本地更严重**（用户原话「图2情况更严重」）。截图取证：
- 图1：视频在 **16:10**（字幕「maybe network connectivity is an issue / 也许网络连接是一个问题」，已开补翻译显示译文），
  但文字面板里 **16:03 一带堆了多段**（"So you don't have a single PEM…" / "We can audit against…" /
  "Either statically or dynamically…" / "And then, in a broader deployment…" / "For example, this might be console…" 全标 16:03）。
- 图2（更严重）：视频同在 **16:10**，但文字面板/自动滚动却停在 **6–12 分钟**区（6:02、6:14、11:39、12:07…），
  即当前词定位/自动滚动**跳飞到十分钟以前**。

### 关键对照：同代码不同结果 ⇒ 不稳定（这是本条核心）
- **本地 1.0.8 跑同一条音频**（记录 `60921671`，23:34 重转）扫描结论：**203 段、段起始非单调 0 处、无任何「同一秒 ≥3 段」堆叠、
  尾部一路单调到 1005s** —— 完全干净。
- **测试机 1.0.8 同镜像同音频**：却出现 16:03 堆叠 + 高亮跳到 6–12 分钟。
- 结论：**同一份代码/镜像，换一次运行就从「干净」退化到「严重塌陷+定位跳飞」**，符合用户判断「算法不稳定」。

### 初步怀疑（待周一证实，勿当结论）
1. **STT 转写文本 run-to-run 不一致** 是最大嫌疑：`alignLong` 用「字符偏移 `cOff` + 按 `cps` 估算每窗 `want`」来切窗，
   对文本长度/内容高度敏感。文本稍有出入 → 窗口边界、over-provision 量、饱和点全变 → 可能重新触发 `cOff` 漂移
   / 窗内塌陷 / 边界词错位。今晚想用「STT×2、ALIGN×2 比对」证实，但探针请求字段没对齐真实服务（STT/ALIGN 都返回 0，
   是探针 bug 不是服务问题），**未完成**，周一重做（真实参数见 `server.js` `gwAudioOp`/`sttParams`：
   STT `response_format=json`、align 传 `text`+`model`+`file`，auth 用 Bearer key + cookie + x-bfl-user；
   注意 `config.json` 里 `language:"zh"` 而音频是英文——是否语言参数影响 STT/align 也要一并查）。
2. 也不能排除 **ALIGN 自身非确定性**（同音同文两次输出微差）叠加放大。
3. 「16:03 堆叠 + 跳 6–12 分钟」的组合，形态上像 **cOff 漂移的老病复发**（后半段某窗喂空/错位 → 一批段拿不到正确时间
   → buildCharToTime 把它们钉到邻近某时刻，同时另一批早段被后段时间污染），只是本地这次没触发、测试机触发了。

### 周一必做（按顺序）
1. **取证**：把测试机那条记录的 JSON 拉下来（`data/library/<id>.json`），本地扫描：段起始单调性、`floor(start)` 同秒堆叠、
   尾部覆盖、逐词 ≥2s 间隔 + burst——和本地干净版逐项对比，锁定退化发生的时间段与对应 `alignLong` 窗口。
2. **复现不稳定**：修好 determinism 探针，STT×3 比对文本差异；对差异文本各跑 alignLong，看窗口边界/塌陷是否随文本漂移。
3. 若证实是文本敏感：让 alignLong **少依赖 `cOff` 字符记账**——考虑用「本窗实际消费的 unit 数」推进、或窗间加 overlap 用时间校正边界，
   降低对 STT 文本逐字一致的依赖（与「八」的强化方向合并处理）。
