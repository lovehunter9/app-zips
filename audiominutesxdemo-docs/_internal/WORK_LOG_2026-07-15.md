## 一、1.0.16（里程碑，已冻结）

三件事，全部叠加在 1.0.14 主路径之上，不动已稳的 committed 对齐逻辑。

1. **修复重叠语音段导致字幕高亮失效**（前端 `App.tsx`）— commit `5d67688`
   - 病根：diar 重叠说话人轮次会让「拍平的全局词起点数组」`wordStarts` **非单调**，前端 `lastAtOrBefore`
     的二分查找失效 → 部分文字不高亮、「跳前跳回」。
   - 修法：新增 `sortedIndex()`，对词起点做**时间排序副本** + `order` 反查表；`syncToTime` 在排序数组上
     二分、再用 `order` 映回 `flat` 原始下标取 `gi`。重叠语音下高亮恢复正确。
   - 「跳前跳回」是单光标 UI 遇重叠语音的**预期产物**，字↔音本身对得上；分段转写+对齐质量到此**可接受**。
2. **A 档可视化「可疑对齐区间」**（`server.js` `detectSuspects`）— 同 `5d67688`
   - 从最终词级时间按**语速异常**检出：基准 `R0=总可见字/总段时长`（加权均值）；`cram`(<2s 且 >3×R0)=挤压/
     飞掠，`slow`(≥2s 且 <0.4×R0)=停滞/漂移。相邻同类合并。TXT/HTML 详细记录各加一表。
   - 优点：从 segments 现算，**老记录不重转即可见**。局限：整体平移式漂移（局部语速正常）测不出。
3. **开发者模式开关**（`App.tsx`，`localStorage` 持久化）— commit `7fbcdca`
   - 设置里加「开发者模式」勾选框，默认**关**；关时隐藏「详细记录」按钮，只有开发者能进对齐诊断。
4. **冻结里程碑**：chart 指向 1.0.16 镜像 — commit `8cdbd2b`。**1.0.14 与 1.0.16 是里程碑；1.0.15 是耻辱柱。**

## 四、1.0.20（今天最终）— 两遍法根治「前移重试丢时间戳」— commit `caf0eb4`

**核心洞察**：应当「直接找准前/后**真实可靠词**，拿中间部分去重对齐；再塌才均匀铺」——不该出现巨大 GAP。
这本质就是**两遍法**：第一遍找出「因前移重试丢了时间戳的区域」，第二遍用重叠窗搞定这些区域。

设计（`audiominutesxdemo-app/server.js` `alignLong`）：
1. **第一遍 = 主循环照常跑（就是 1.0.14）**，只多做一件事：某窗**前移重试成功**（`attempt>0`）时，把被跨过、
   没拿到真实对齐的字符区间 `[cOff,c0)` 连同**两端真实时间锚**记进 `shed[]`：
   - **左锚 A** = 窗起 = 上一可靠词的 end；
   - **右锚 B** = 首个「时间真正前进过窗起 a」的 committed 词的 start（跳过堆在窗头的塌头）。
2. **第二遍**（主循环后）：对每个 `shed` 区取重叠窗 `[A,B]` **重对齐一次**拿真值；若又塌（覆盖 <50% 窗时长）
   → 在 `[A,B]` 内按字长**均匀铺**兜底。两端钉真锚 → **不漏 GAP、不堆接缝**。重对齐调用次数 = 前移区个数
   （**有界**，最多 4 路并发）。
3. **彻底删除**：候选池 / `SEAM_TOL` / 候选救回 / `realignGuessedSpans` / cram·spike·巨无霸·还债块整套
   事后启发式。`resolveCoverage` 精简为「排序 + 补洞线性插值 + 报警」。
4. **详细记录同步精简**：去候选表与逐字 cram/giant 标注，新增「前移修复区」两遍法视图。
5. 净 **−200 行**（158+/358−）。

但宿主机 `curl` 连 Docker Hub 正常（auth.docker.io=200、registry-1.docker.io/v2/=401 是正常「要 token」）。

## 五、【明日大事·超级大】llm-init 收编音频模型接口，剔除 NGINX，评估官方引擎内置

> 用户原话：之前做音频相关模型时**强令不改 llm-init**，模型需要的新接口都由 **NGINX 代理**；现在要**改变这个
> 结构**——llm-init 要**代理这个接口**、**把 NGINX 剔除**；并且要**分析现在 llm-init 的代码变化，看各模型的
> 官方引擎是不是也适合放进 llm-init 里**。「超级大的事，却要飞快地做完。」

### 5.1 现状架构（已核对代码，2026-07-15）

**音频链路（`audiolabxv3` / `audiolabwv3`）—— 三体拼装 + NGINX 合流：**
- `llm-init`（`beclab/llm-init:v1.2.4`）跑**下载专用模式**（`ENGINE_KIND=""`）：纯 HF 下载器 + 控制面
  + dashboard + `/api/model-spec` + `/readyz`，端口 :8090，**没有 /v1 数据面**。**刻意保持 llm-init 不改。**
- **官方音频引擎**（`engine.yaml`，按 mode 黑箱选 image：stt=faster-whisper、diar=pyannote_fastapi、
  vad=whisper 复用+wrapper）自己提供 OpenAI 音频面 `/v1/*` 于 :8000（`audio-engine` / `sharedentrances-api` svc）。
- **NGINX/openresty 合流层**（`audiolabxv3/templates/ingress.yaml`，`audiolabxv3ingress` Deployment，
  image `beclab/aboveos-bitnami-openresty:1.25.3-2`，:8080）把两者合并到**一个公网入口**：
  - `/v1/` → `audio-engine:8000`（推理数据面）
  - `= /v1/models` → **合成静态 JSON**（因离线镜像的 /v1/models 会 401/500）
  - `/` → `download-svc`(llm-init) :8090（控制面/dashboard/进度）
  - 这层就是「模型新接口由 NGINX 代理」的那层。

**对照：llama.cpp 链路（`llamacppllmbasev3`）—— llm-init 自带代理、无 NGINX：**
- `llm-init` 跑**代理模式**（`ENGINE_KIND=llamacpp`）：下载 GGUF + 在 :8090 提供 OpenAI `/v1/*` 代理，
  **反代引擎 `http://llamacpp:8081`**（llm-init v1.1.0+ 按 ENGINE_KIND 推导上游 URL）。**没有独立 NGINX**，
  llm-init 自己就是单一入口 + 代理。`sharedentrances-api` 直接指向 llm-init:8090。

→ **结论**：llama.cpp 早已是「llm-init 一体化代理」的形态；音频侧因当初「不许改 llm-init」而多了 NGINX 一层。
明天要做的就是**把音频侧对齐到 llama.cpp 形态**：给 llm-init 增加音频的 ENGINE_KIND（反代 audio-engine 的
`/v1/audio/*`），删掉 openresty ingress。
