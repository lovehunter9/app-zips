# 语音转录产品综合课题 · 立项与样本初稿

> **本文定位**：把"语音转录类应用与服务"这一独立调研课题的边界、与已完成"语音输入法"课题的关系、研究方法、第一轮样本框架先落地。后续每一类样本展开成专题文档，最后汇总成 `README.md` 提供"一页纸结论"。

## 一、课题边界

### 1.1 与"语音输入法"课题的关系

| 维度 | **语音输入法**（已交付，见 `voice-input-products-docs/`）| **语音转录**（本课题）|
|---|---|---|
| 触发方式 | 按住热键说话 → 实时打字注入当前输入框 | 上传 / 拉取 / 录制音频文件 → 出文字稿 |
| 时长 | 一句话级（秒级） | 分钟级到小时级 |
| 关键输出 | 注入到光标位 | 完整稿件 + 时间戳 + 说话人 + 章节 + 摘要 + 字幕 |
| 典型场景 | 写作 / 写代码 / 聊天回复 | 会议纪要 / 播客 / 采访 / 视频字幕 / 庭审 / 病历 |
| 核心硬约束 | 低延迟（< 500 ms），单进程，文本注入 | 高吞吐 / 长任务、任务队列、对象存储、SRT/VTT 字幕 |
| Olares 现成锚点 | `speaches`（OpenAI 兼容 STT/TTS endpoint） | **`whisperwebuiv2`**（Gradio WebUI + 说话人分离 + 翻译） |

**两条课题的共享底座**：底层 ASR 模型清单（Whisper 家族 / faster-whisper / WhisperKit / SenseVoice / Paraformer / Parakeet / Voxtral / Cohere / Apple Speech / Deepgram Nova / 火山豆包 等）与服务端框架（faster-whisper-server / WhisperLive / WhisperLiveKit / Speaches）在两个课题里高度重叠。本课题在涉及模型层时**会引用语音输入法课题的对比表**，避免重复编纂，重点放在"转录场景特有的差异"上。

**两条课题的独立部分**：
- 样本集本身（端到端的"语音转录"产品几乎完全是另一批：MacWhisper / Buzz / WhisperX / Whishper / Otter / Rev / Fireflies / Read.ai / 讯飞听见 / 通义听悟 …）
- "转录特有"技术维度（说话人分离 diarization、word-level 时间戳、章节切分、摘要生成、字幕导出格式、批量任务、长音频处理、BGM 分离、热词词典、自定义术语）
- 移植 Olares 的难度评估视角（长任务调度、对象存储、带宽峰值、GPU 内存峰值、与 `whisperwebuiv2` 的关系）

### 1.2 本课题**包含**

- ✅ 端到端商业产品（桌面 App、Web SaaS）
- ✅ 端到端开源项目（CLI 工具、自托管 WebUI）
- ✅ 会议机器人 / 实时转录（自动加入 Zoom/Teams/Meet 拉转录）
- ✅ 视频字幕 / 创作者工具（CapCut / Premiere / DaVinci / Submagic / Veed）
- ✅ AI 笔记本 / 长音频整理（NotebookLM / AudioPen / Voicenotes / Cleft）
- ✅ 国内大厂转录（讯飞听见 / 通义听悟 / 飞书妙记 / 腾讯会议 AI / 网易见外 / 录音宝）
- ✅ 行业垂直（医疗 / 法律 / 媒体 / 教育 / 客服 / 政府）

### 1.3 本课题**不包含**

- ❌ 实时按键输入式语音输入法（已在另一课题完成）
- ❌ 纯 TTS（文本转语音）产品（不在"转录"语义范围）
- ❌ 语音克隆 / 配音 / Voice changer 类产品
- ❌ 语音助手 / 语音对话机器人（Siri / Alexa / Voicebot）
- ❌ 通话录音监控 / 客服质检的"录音分析中后台"——只在涉及"转录引擎"时引用

### 1.4 设计层而非工程层

本课题与"语音输入法"课题保持一致：**只做到设计层评估**，不写 Helm chart、不写代码骨架，但会给出 OlaresManifest 的关键字段集与"如果立项第一周该想清楚什么"。

## 二、研究方法

### 2.1 三级置信度（沿用上一课题约定）

- `[高]` 有官方文档 / 源码 / 实际抓包 / 官方定价页 / 上架 manifest 证据
- `[中]` 多方独立第三方评测 + 一致逻辑推断
- `[推测]` 仅有间接线索（如官方未披露模型，但社区抓包到 endpoint）

### 2.2 评估维度（语音转录场景）

每个样本从以下 12 个维度刻画：

1. **形态**：桌面 App / Web SaaS / 会议机器人 / CLI / 自托管 WebUI / 视频编辑插件 / 行业 SDK / API 服务
2. **平台覆盖**：macOS / Windows / Linux / iOS / Android / Web / Self-host
3. **输入源**：本地文件 / URL / YouTube / Zoom-Teams-Meet 直接拉 / 麦克风录音 / 实时流
4. **输出格式**：纯文本 / SRT / VTT / TTML / JSON 带时间戳 / Markdown / DOCX / PDF
5. **ASR 引擎**：自研闭源 / Whisper / faster-whisper / WhisperX / Deepgram / AssemblyAI / Speechmatics / 阿里达摩 / 火山 / 讯飞
6. **说话人分离**：无 / 简单阈值 / pyannote / 3D-Speaker / WeSpeaker / 自家闭源
7. **时间戳精度**：句级 / 词级 / 音素级
8. **后处理 AI 能力**：标点恢复 / 数字格式化 / 章节切分 / AI 摘要 / 关键点提取 / Action Items / Q&A / 翻译
9. **多语种**：仅英文 / 中英双语 / 100+ 语种 / 方言
10. **长任务策略**：阻塞 / 异步任务队列 + 邮件通知 / 流式增量
11. **隐私 / 数据所有权**：纯本地 / 用户控制 / SaaS 多租户 / BYOK
12. **许可证 / 商业模式**：开源协议 / 免费试用 + 订阅 / 按分钟计费 / 企业合同

### 2.3 Olares 移植难度评估维度

每个候选移植项目从以下 8 个维度评估：

1. **是否有 headless server 模式**（可以脱离 GUI 跑后端）
2. **容器化成熟度**（官方/社区 Docker image 状态）
3. **GPU 依赖**（必须 GPU / GPU 可选 / 纯 CPU 可跑）
4. **持久化需求**（仅模型缓存 / + 上传文件 + 转录结果数据库）
5. **对象存储需求**（音视频文件能否存在 hostPath PVC，还是需要 S3）
6. **长任务调度模式**（同步阻塞 / Celery / RQ / 自研 worker / 任务队列）
7. **OpenAI 兼容性**（是否暴露 `/v1/audio/transcriptions`）
8. **与 Olares 现有应用复用度**（与 `whisperwebuiv2`、`speaches`、`ollamav2`、对象存储应用的关系）

## 五、初始假设（先放着，后续验证）

> 这些是基于上一份课题经验做的"假设"，本课题第一轮调研后逐一验证。

1. **`whisperwebuiv2` 已经事实上占据 Olares 上"语音转录 GUI"的位置**——任何"再做一个 Whisper WebUI"的新应用都很难有差异化。`[待验证]`
2. **`speaches` 已经事实上占据 Olares 上"OpenAI 兼容 STT endpoint"的位置**——任何"再做一个 OpenAI 兼容转录 API"的新应用都难以差异化；本课题的"新增价值"应在 `whisperwebuiv2` 之外的方向（如长任务队列、对象存储集成、说话人分离专家模式、AI 摘要、字幕编辑器、会议机器人）。`[待验证]`
3. **国内场景的转录需求与海外差异显著**——讯飞听见 / 通义听悟在中文 + 方言 + 中英混合 + 行业术语上比 Whisper 优；国内用户对私有化 / 自部署有强需求。`[待验证]`
4. **会议机器人这一形态在 Olares 上的可行性较低**——它需要拉 Zoom/Teams/Meet 的 webhook 或者用 headless browser 加入会议；这是网络穿透 + 商业账户的双重门槛。`[待验证]`
5. **真正适合 Olares 的方向是"个人级长音频整理"**——即 AudioPen / Voicenotes / NotebookLM 类，因为它们和"个人云"的定位高度契合。`[待验证]`
