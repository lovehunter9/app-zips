
### 2.4 `options.apiTimeout: 0`（解决用户抱怨 2）

`OlaresManifest.yaml`：

```yaml
options:
  apiTimeout: 0    # ← 新增
  dependencies:
  - name: olares
    type: system
    version: '>=1.12.3-0'
```

依据：搜了 terminus-apps 下约 100+ 长任务 app（claudecode、tensorzero、litellm、ragflow、n8n、ollama×N、vllm×N、openwebui、acestep、…）几乎都设了 `apiTimeout: 0`。

实测：设之前 `large.ics` 上传 15s 就 504；设之后 5 分钟才 504（见第三节解锅过程）。**该字段映射到 Envoy `RouteAction.Timeout`**（已在 `Olares/framework/app-service/pkg/sandbox/sidecar/envoy.go` 验证），不是消除全部超时。

### 2.5 数据持久化（hostPath + initContainer + fsGroup）

之前的 chart 没做持久化（emptyDir），pod 重启数据丢。补成与近期其他应用（opennotebook / opencode / tensorzero）一致的模式：

```yaml
volumes:
  - name: radicale-data
    hostPath:
      type: DirectoryOrCreate
      # 注意 1.12.3+ 用 .Values.userspace.appData，老版本拼接子目录
      ...
initContainers:
  - name: fix-permissions
    image: docker.io/beclab/aboveos-busybox:1.37.0
    command: [sh, -c]
    args:
      - mkdir -p /data/collections; chown -R 2999:2999 /data; chmod -R 770 /data
    securityContext:
      runAsUser: 0
securityContext:
  fsGroup: 2999
env:
  - name: TAKE_FILE_OWNERSHIP
    value: "false"   # 因为 init 已经修过，runtime 不要再 chown 整个目录
```

UID 2999 是 `tomsquest/docker-radicale` 镜像里 radicale 进程的固定 UID。
`TAKE_FILE_OWNERSHIP=false` 是该镜像的官方"已用 initContainer 修过权限，runtime 别再动"的开关。

`permission.appData: true` 也补上了（manifest 声明应用要访问 userspace.appData）。

### 2.6 i18n upgradeDescription

`i18n/en-US/OlaresManifest.yaml` + `i18n/zh-CN/OlaresManifest.yaml`：累积式（保留 v1.0.6 的旧条目，新增 v1.0.8 段），格式跟用户偏好的 `v1.0.6` / `v1.0.8` 风格一致（不是 `Chart 1.0.6`）。

## 三、用户实测过程 + 5 分钟 504 解锅链（最关键的事实链）

按时间顺序，记录每一步的现象、错误推断、最终真相。

### 3.1 第一轮（仅升级 + 资源 + 持久化，**未加 apiTimeout: 0**）

| 文件 | 大小 | 现象 |
|---|---|---|
| small.ics（5,000 events，1.9 MB） | 504 在 15s | 但**刷几下能成功**（Radicale 后台继续写盘） |
| large.ics（50,000 events，19 MB） | 全程 504 | **页面无法刷新出来**，必须重启 pod 才能恢复 |
| 顶栏 `list` / `info` 接口 | 始终 404 | 共享模块未启用，正常 |

用户决定加 `apiTimeout: 0`（"加了如果无效就不再提"）。

### 3.2 第二轮（加 `apiTimeout: 0`）

实测：

- small：1.2 分钟成功，无 504 ✓
- large：5.1 分钟 504 ✗

15s 的硬上限消失了，但出现了新的"约 5 分钟"的硬上限。用户问："是 radicale 自己搞的？"

### 3.3 第一次错怪：以为是 `l4-bfl-proxy` 的 `xds-route-timeout`

`Olares/framework/l4-bfl-proxy/cmd/main.go` 里看到默认 `xds-route-timeout: 5m`，瞬间下结论"是这个"。

**错的**：l4-bfl-proxy 是平台入口反代，配置 sandbox 层的 xDS 推送超时，跟单条请求的处理时长无关。用户给了 radicale 容器内日志 + envoy sidecar 日志：

```
radicale.log:
  [INFO] PUT response status for '/wrx/radicale-bench-large/'
         in 595 seconds: 201 Created           ← 595s，Radicale 自己干完了
  
envoy-sidecar.log:
  ...PUT body received completely (t=42s)...
  ...
  upstream_reset_after_response_started{stream_idle_timeout}
                                       (exactly t=300+42=342s)
```

Envoy sidecar 日志写得清清楚楚：**`stream_idle_timeout` 在请求体接收完之后的 300s 触发**。Radicale 自己继续干（直到 595s 完成），但 Envoy 已经把连接关了。

### 3.4 真相：`stream_idle_timeout` 是 Envoy HCM 的默认 300s

定位代码：`Olares/framework/app-service/pkg/sandbox/sidecar/envoy.go`

- `apiTimeout` → 映射到 `RouteAction.Timeout`（已正确接管）
- **`stream_idle_timeout` 在 HCM 里压根没赋值，落到 Envoy 默认 300s（5 分钟）**

也就是说，OlaresManifest **不暴露**这个字段，chart 这一层**无解**。要么 olares 在 manifest 加一个新字段（比如 `streamIdleTimeout`），要么直接调高/取消 HCM 默认。

### 3.5 这一段教训

- **看到 `5 分钟`/`300s` 不要先猜 envoy 还是 nginx 还是 ingress，先去翻请求两侧的日志**。这次用户主动给了两份日志才把方向掰回来。
- 一个数值（300s）可能命中多个组件的默认值，证据链要打通"开始计时点"才算定锅。这次靠 `body received → 300s 后断开` 这个 delta 才定到 `stream_idle_timeout` 而不是 `request_timeout`。

## 四、性能优化尝试（**实测无效，全部回退**）

用户决定先不追 5 分钟那条线（"暂且按下"），改尝试**加快 Radicale 自身处理速度**，目标是让大文件能在 300s 内跑完。

### 4.1 方案 A 的内容

ConfigMap 注入 Radicale `[storage]` 段：

```ini
[storage]
type = multifilesystem_nolock              # 用 in-process threading lock 替换跨进程 file lock
use_mtime_and_size_for_item_cache = True   # 用 mtime+size 当 cache key（替代 SHA256）
use_cache_subfolder_for_item = True
use_cache_subfolder_for_history = True
use_cache_subfolder_for_sync_token = True
```

资源：CPU `request 0.5 / limit 2`、Memory `request 1Gi / limit 4Gi`。

**风险评估**（当时给用户的回答）：

- `multifilesystem_nolock` 强制 `replicas: 1`（chart 默认也是 1，但要在注释里写死提醒）
- ConfigMap mount 到 `/config/config` 可能撞上镜像内置默认配置，要确认 `RADICALE_CONFIG=/config/config` 还是 `/etc/radicale/config`
- 缓存子目录会改 `/data/collections/<user>/<col>/.Radicale.cache/` 结构，**第一次启动要全量重建缓存**，可能反而更慢

### 4.2 实测结果

用户清空数据重测：

| 文件 | 优化前 | 优化后 |
|---|---|---|
| small（5,000） | 67.3 s | **67.3 s**（基本无变化） |
| medium（20,000） | ~260 s 之前测过 | **259.9 s**（基本无变化） |

`kubectl logs` 确认 ConfigMap 生效（`storage type is 'radicale.storage.multifilesystem_nolock'` 等 4 行都在）。**优化生效了，但对耗时影响 < 1%**。

### 4.3 为什么无效（事后定性分析）

Radicale 的 `multifilesystem` 对每个 event 都做：

```
1. 把 .ics 文本写到 /data/collections/<user>/<col>/<uid>.ics
2. fsync(2) 这个文件
3. 更新 cache（item / history / sync-token 三份）
4. 给 cache 也 fsync
```

`multifilesystem_nolock` 只把"跨进程文件锁"换成"进程内 threading 锁"。但**单线程 Python + 每 event 多次 fsync** 才是瓶颈。锁竞争从来不是问题（单 replica 单进程 + WSGI 每请求自己跑），所以换锁没用。

cache 优化把 SHA256 换成 mtime+size，理论上能省 CPU 但**省的是 cache 写入这一步，bottleneck 不在 cache 而在每条 event 的 fsync**。

结论：**Radicale 的 `multifilesystem` 后端在批量导入场景下天然就是 ~11-13 ms/event**。要再快只能换后端（SQLite / Postgres，但不是简单 plug-in，需要上游开发或大改 chart）。

### 4.4 回退

用户决定撤销整套性能优化、保留 apiTimeout: 0、保留资源原始建议值。

- 删 ConfigMap + volumeMounts + volumes 里的 config-mount
- 资源回到 `cpu 250m/1000m, memory 512Mi/2Gi`
- 删 multifilesystem_nolock 的 `replicas: 1` 警告注释
- 重新打 `radicale-1.0.8.tgz`（5.7 KB，干净状态）
