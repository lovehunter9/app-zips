## 一、LLM 校正终局评估

### 1.1 英文 + LLM 校正实测数据（今日新增第 4 组）

| 维度 | 数据 |
|---|---|
| 音频 | 福尔摩斯：波希米亚丑闻（~64 分钟有声书）|
| 耗时 | **41 分钟 5 秒**（vs 无 LLM 4m47s，慢 **8.6×**）|
| 速度比 | 1.56× 实时（无 LLM 是 13.4× 实时）|

### 1.2 致命缺陷：LLM 元评论泄漏

输出中至少 **30+ 处** LLM 的判断性备注被吐进字幕：

```
In her eyes, she eclipses and predominates the whole of her sex. (No corrections needed.)
He threw over a sheet of fake, pink-tinted notepaper. (No correction needed.)
The Count shrugged his broad shoulders. (Corrected as it was grammatically correct and no errors were found.)
Egeria. It is in a German-speaking country in Bohemia. (This sentence seems to be incomplete or incorrectly structured. Egeria is a genus of flowering plants, not a country.)
```

最后一条最离谱——LLM 还自作主张去**百科核查**原文语义。

**根因**：`_clean_llm_output` 函数只清理了围栏 / `Corrected:` 前缀 / 外层引号，**没清理结尾的括号注释**。

### 1.3 四组数据综合矩阵

| 维度 | 中文 -LLM | 中文 +LLM | 英文 -LLM | 英文 +LLM |
|---|---|---|---|---|
| 耗时倍数 | 1× 基线 | **11×** | 1× 基线 | **8.6×** |
| 难错误（专名）| 仍错 | 仍错 | 仍错 | **仍错** |
| 新增问题 | -- | 5+ 事实幻觉 + 自循环 | -- | **30+ 处元评论泄漏** |
| 净效果 | 基线 | **明显负面** | 基线 | **混合，元评论泄漏不可接受** |

### 1.4 决策：删除 LLM 校正（不只是默认关闭）

理由：
1. **3 个独立失败模式**：中文事实幻觉、英文元评论泄漏、两种语言都修不好难错误（专名等）
2. **任何 ROI 不存在**：修对的 < 改坏的，时间成本 8-11×
3. **保留即风险**：UI 上一个可勾选项 = 任何用户都可能踩坑
4. **维护成本黑洞**：每修一个边缘问题，新的边缘问题还会冒出来；Qwen2.5-3B 这个尺寸根本看不懂 Whisper 错在哪

## 三、后处理用户可控化（Plan A：两个独立勾选）

### 3.1 设计抉择

用户提出关键观察：**既然后处理影响用户的输出形态，就应该是可知的可选项**。

讨论了 A/B/C 三方案，最终选 A —— **两个独立勾选**，理由：

| | Text Cleaning | Segment Merging |
|---|---|---|
| 影响范围 | 单段内**文字** | 跨段**结构** |
| 副作用半径 | 极小（标点 + 短语去重）| 较大（段数变少、时间戳跨度变长）|
| 用户想关的场景 | 几乎没有 | 偶尔有（词级对齐、研究调试）|

合并成一个勾会让用户为了"想看 Whisper 原始切分"被迫连标点修复也关掉，不划算。

### 3.2 代码实现（镜像旧 LLM 设计但精简）

**全局开关**（紧贴 `_TEMP_STEPS` 之前）：
```python
_text_cleaning_enabled = True
_segment_merging_enabled = True
```

**API 入参**（`/v1/audio/transcriptions`）：
```python
text_cleaning: bool = Form(True),
segment_merging: bool = Form(True),
```

**kwargs 注入**（紧贴 `_lock` 之前）：
```python
kwargs["_text_cleaning"] = bool(text_cleaning)
kwargs["_segment_merging"] = bool(segment_merging)
```

**Engine patch**（`_patch_whisper_engine`）：
- pop `_text_cleaning` / `_segment_merging` 两个 kwarg
- override-or-global 二选一逻辑：`override if not None else global`
- 条件性套用 pipeline：`pipeline = segments_gen`，按开关决定是否包 `_text_clean_segments` 和 `_merge_short_segments`
- `_skip_pipeline=True` 仍然短路（内部语言检测）

**Gradio UI patch**（复活并改造原 `_patch_gradio_ui`）：
- 注入两个 Checkbox：`Text Cleaning` + `Segment Merging`
- 各自的 `change` 回调改全局并 log

### 3.3 行为矩阵

| 场景 | API 入参 | WebUI 全局 | 实际生效 |
|---|---|---|---|
| API 调用未传 toggle | 默认 True | 任意 | 两个都开 |
| API 显式 `text_cleaning=false` | False | True | 文本清洗**关**，段合并**开** |
| WebUI 关掉 Segment Merging | （UI 不走 API 参数） | `_segment_merging_enabled=False` | 段合并**关**，文本清洗**开** |
| 内部语言检测（`_skip_pipeline=True`）| — | — | 两个都跳过 |

## 四、yaml 持久化（关键迭代）

### 4.1 问题暴露

用户截图 `default_parameters.yaml`，质问：**这两个参数没有写进 yaml 对吧？那用户打勾、去掉勾就记录不下来了。**

确实如此——勾选只是改内存全局变量，Pod 重启后丢失。这是明显的产品缺陷。

### 4.2 新增机制

新增两个函数（紧贴 `_patch_webui_config` 之后）：

| 函数 | 时机 | 职责 |
|---|---|---|
| `_load_post_processing_state()` | 启动时（main 中 `_patch_webui_config` 之后）| 从 yaml `_post_processing` 节读 → 写回两个全局 flag |
| `_persist_post_processing_state()` | 每次复选框 `change` 回调末尾 | 把两个全局 flag 写回 yaml `_post_processing` 节 |

**新启动顺序**：
```
_patch_webui_config()         # _PATCH_VERSION 版本化迁移
_load_post_processing_state() # 恢复用户上次勾选（或首次安装时写默认）
_patch_whisper_engine()       # 引擎 monkey-patch
_patch_gradio_ui()            # UI 复选框初始值 = 已恢复的状态
```

### 4.3 yaml schema（新顶级节）

```yaml
_post_processing:
  text_cleaning: true
  segment_merging: true
```

并列于 `whisper:` / `vad:` / `_patch_version:`，独立 schema 节避免污染 Whisper-WebUI 上游 schema。

### 4.4 首次安装路径（再迭代一次）

用户又问：**初始安装时这两个参数不写入 yaml 吗？就像咱们 PATCH 的其它参数一样。**

合理诉求。改造 `_load_post_processing_state`：

```
读 default_parameters.yaml
  │
  ├─ 文件读不出 → warn + 用代码默认（不写）
  │
  ├─ _post_processing 节缺失 → 首次安装路径
  │   └─ 把代码默认值写入 yaml + log "seeded defaults"
  │
  └─ _post_processing 节存在 → 正常加载路径
      └─ 逐键 isinstance(bool) 校验，赋值给全局 flag
```

### 4.5 与 PATCH 6 参数的设计对称性

| | PATCH 6 个参数 | `_post_processing` 2 个开关 |
|---|---|---|
| 首次安装是否写 yaml | ✅ | ✅（今日加上）|
| 用户能否在 yaml 里看到键名 | ✅ | ✅ |
| 版本升级是否强制覆盖 | ✅（`_PATCH_VERSION` 触发）| ❌（用户偏好优先）|
| 用户在 WebUI 改的会保留 | 日常重启保留，版本升级被覆盖 | 永远保留 |

差异是**有意的**：PATCH 是"我们的推荐配置，新版需要推送"，`_post_processing` 是"纯用户偏好，永远不动"。

## 六、用户预感的"微妙问题"——明日重点验证项

用户明确说"感觉有点微妙的问题"。我自查识别出**几个需要重点测试的疑点**：

### 6.1 持久化层

1. **首次安装的 seeding 时序**：`_load_post_processing_state` 在 `_patch_webui_config` 之后运行，这一刻 yaml 应该已经存在（被 init container 拷贝 + `_patch_webui_config` 可能已经写入 `_patch_version`）。但要验证：**真的有 `save_yaml` 的写权限吗？** init container 是 root 跑的，主容器 securityContext.runAsUser=0，应该没问题。
2. **toggle 时的 save_yaml 失败**：如果 yaml 文件被另一个 patch 进程同时读写，可能出现 lock 竞争。当前实现是 best-effort，失败仅 warn。需观察日志是否真有 `Failed to persist post-processing state` warning。
3. **`load_yaml` / `save_yaml` 是否保留注释**：Whisper-WebUI 的 `files_manager` 用什么 YAML 库？如果是 PyYAML，那注释和顺序都会丢；如果是 ruamel.yaml，则保留。**未验证**——明日跑一次后 cat 一下 yaml 看看其它参数顺序有没有被打乱。

### 6.2 Gradio Checkbox 注入位置

`_patch_gradio_ui` 改写 `WhisperParams.to_gradio_inputs`，在 `only_advanced=True` 时**先创建两个 Checkbox**再调原方法。两个问题：

1. **Checkbox 是否真的会被渲染**：Gradio 的组件需要在 `gr.Blocks()` 上下文里创建才会被收入界面。`to_gradio_inputs` 是否在 Blocks 上下文中被调用？**理论上是的**（这是 Whisper-WebUI 的常规调用路径），但**未实测**。
2. **`change` 回调的 `_persist_post_processing_state` 闭包能否正确触发**：Gradio 在重启后会序列化 / 反序列化 fn 引用。我们的 `_toggle_text` 是 `_patched_to_gradio` 内部的局部函数，可能存在闭包绑定问题。明日实测时如果发现勾选了但 yaml 没变，这是首要怀疑点。
3. **复选框是否在每个 Tab（File / Youtube / Mic）都注入了**：`to_gradio_inputs` 在三个 Tab 各调用一次，我们的注入会跑三次 —— 这意味着会创建 6 个 Checkbox（每个 Tab 一对）。**它们的状态是同步的吗？** 现在的实现共用同一个全局 flag，三个 Tab 上勾任意一个都会影响同一个变量，但**三个 Tab 的 Checkbox UI 显示状态不会自动同步**。这可能就是用户预感的"微妙问题"之一。**待验证 + 待解决**。

### 6.3 API per-request 与全局持久化的语义

教程承诺："API 显式传入这两个参数不会修改持久化状态"。代码层：API 通过 `kwargs["_text_cleaning"] = bool(...)`，这只影响 `_patched_transcribe` 内部的 override 变量，不会调 `_persist_post_processing_state`。**应该是对的**，但建议明日实测：API 传 `text_cleaning=false` 后，去 yaml 看 `_post_processing.text_cleaning` 是不是仍然是 `true`。

### 6.4 资源退回后的实测压力

把 deployment 内存从 22Gi 退回 18Gi、manifest limitedMemory 从 24Gi 退回 20Gi。理论上完全够（无 LLM 后），但**未实测**长音频转写是否还会触及内存峰值。如果碰到 OOM 杀进程，需要重新审视退回的幅度。
