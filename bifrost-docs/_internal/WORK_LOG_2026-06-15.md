## 三'、Terminal 自启修正：`--shell` 只是窗口名，真正机制是 `$ENV`
实测：装上 cli `0.0.1-test3` 后，`--shell=bifrost-shell` **只改了终端 tab 名**，进去仍是
bash/sh 提示符，并没执行 bifrost。结论：**beclab/terminal 的 `--shell` 仅作窗口标题**，
进入执行的是容器的交互式默认 shell。

参考 opencode 的做法发现真正机制：opencode 容器设了环境变量 **`ENV: /home/opencode/.profile`**
——POSIX `sh` 交互式启动会自动 source `$ENV` 指向的文件，opencode 就在那个 profile 里启动 TUI。

照搬到 bifrost（**纯 chart 改动，cli 镜像不动、不用再转换**）：
- `configmap.yaml`：`bifrost-config` 新增 `cli-profile` 脚本：
  ```sh
  export PATH="/usr/local/bin:$PATH"
  case "$-" in *i*) ;; *) return 2>/dev/null ;; esac     # 仅交互式
  if [ -z "${BIFROST_CLI_STARTED:-}" ]; then             # 防子 shell 复跑
    export BIFROST_CLI_STARTED=1
    bifrost          # 进入即启动 CLI
    exec bash        # 退出后落 bash（随用户）
  fi
  ```
- `bifrost.yaml` cli 容器：加 `env: ENV=/etc/bifrost/cli-profile`，并把 `bifrost-config`
  以 `subPath: cli-profile` 只读挂到 `/etc/bifrost/cli-profile`。
- `terminal.yaml`：`--shell` 改成 `bifrost-cli`（按用户要求，纯窗口名）。
- 镜像里那个 `bifrost-shell` wrapper（test3 已烤）现在不再使用，留着无害，不重建。

> 注意点：此机制依赖 terminal 进去执行的是**交互式 `sh`(ash)**。

### 三''、实测：terminal 执行的是 **bash**，改用 `~/.bashrc`（最终方案）
诊断 `echo "started=[$BIFROST_CLI_STARTED] shell=[$0] ENV=[$ENV] BASH_VERSION=[$BASH_VERSION]"`：
```
started=[] shell=[bash] ENV=[/etc/bifrost/cli-profile] BASH_VERSION=[5.3.9(1)-release]
```
- `shell=[bash]`（无前导 `-` → **非 login 交互式 bash**）；`$ENV` 已设但 **bash 不读 `$ENV`** → profile 没被 source、`started=[]`。
- 手动 `bifrost` 能正常进 CLI（logo + "Base URL http://localhost:8080"），证明 CLI 本体没问题。

修法（仍纯 chart、镜像不动）：把同一段 `cli-profile` 脚本**挂成 cli 容器的 `~/.bashrc`**：
- `bifrost.yaml` cli 容器新增 volumeMount：`bifrost-config` subPath `cli-profile` → `/app/data/.cli-home/.bashrc`（只读）。
  （`HOME=/app/data/.cli-home`，非 login 交互式 bash 会 source `~/.bashrc`。）
- 因为入口本就是 bash，脚本里**去掉 `exec bash`**：`.bashrc` 跑 `bifrost`，退出后自然停在这个 bash。
- 保留 `$ENV=/etc/bifrost/cli-profile` 挂载作 sh 退路（无害；guard 防双启）。
- 用 hostPath 卷内嵌套挂 configmap 文件（`/app/data` 是卷，`.bashrc` 再叠挂）——免改卷、免 seed、不怕陈旧（每次部署重渲染）。

### 三'''、CLI 首屏 "Base URL" 引导 → seed 配置免填
现象：自启进 bifrost CLI 后停在首次引导页问 "Base URL"，底部 `error: base URL is required`
（那行 `http://localhost:8080` 是灰色占位，不是实填值）。

查证（docs.getbifrost.ai）：bifrost CLI 配置在 **`~/.bifrost/config.json`**：
```json
{ "base_url": "http://localhost:8080", "default_harness": "...", "default_model": "..." }
```
首次创建、TUI 改设置会**写回**此文件 → 不能只读挂载。

网关端口：`bifrost/values.yaml` `port: 8080`，ingress `proxy_pass http://bifrost:8080`，
探针打 8080 → 网关在 pod 内**听 8080**（`containerPort: 8000` 那行是写错的装饰值，无影响）。
cli 的 `BIFROST_BASE_URL=http://localhost:8080` 本就对。

修法（纯 chart、镜像不动）：`fix-permissions` init 里 **seed-once** 写
`~/.bifrost/config.json = {"base_url":"http://localhost:{{ .Values.port|default 8080 }}"}`
（文件不存在才写，chown 1000）。这样首屏跳过 Base URL，用户后续在 TUI 改 harness/model 仍能写回。
- 对**已装**的用户：升级到新包时 `.bifrost/config.json` 还不存在 → 会被 seed；本次会话也可手填一次 `http://localhost:8080`。

### 五、TUI 启动尺寸竞态二修（chart-only，无需重建镜像）
现象：有的窗口正常，有的会先闪一下小分辨率再变大，且变大后底部残留一行坏的。
根因：前端 resize(SIGWINCH) 常比 shell 启动晚几百 ms；PTY 先停在默认/小尺寸且本身"稳定"，
旧逻辑"连续两次相同就启动"过早 break → bifrost 先按小尺寸画、resize 到了再重画 → 底部残留。
修复（configmap `cli-profile` 轮询逻辑）：先等下限 `_floor=8`(≥0.8s 让 resize 落地)，
再要求尺寸非零且稳定 `_need=3`(~0.3s)，硬上限 `_max=45`(4.5s)。代价是每个窗口固定 ~0.8–1s 后才出 TUI，
但渲染一次到位、不再闪/不再残留。chart 仍锁 1.0.8，已重打 tgz。

备注：第二张截图状态栏暴露真正的 bifrost CLI 二进制版本 = **v0.10.5**（npm bootstrapper 是 1.0.1，两码事）。

### 五'、尺寸竞态三修：只第一个窗口坏（chart-only）
反馈：后开的窗口都正常，只有"装完自动弹出的第一个"底部那行还坏；且要求别动到后开的。
分析：后开窗口 tmux 直接给真实大尺寸 → `stty size` 一上来就是宽的；只有第一个窗口从默认 `80x24`
起步、resize 晚到，`_floor=0.8s` 仍不够。
改法（不再用盲等下限，改按尺寸本身判断）：轮询直到 **列数 > 80**（已从 80 默认值长成真实宽度）
且稳定 3 次(~0.3s)才 `clear`+启动；硬上限 6s 兜底。效果：已宽的后开窗口 ~0.3s 直接进、比之前更快、
绝不被拖慢/破坏；第一个窗口精确等到变宽再画。已 `sh -n` + bash/sh 实测阈值逻辑（80→等、>80→进）。chart 仍 1.0.8。

### 七、尺寸竞态四修：新开 tab 仍偶发（拉长稳定窗口，chart-only）
反馈：第一个窗口好了，但新开 tab 仍偶发两种坏态——①保持在小；②闪小后变大但底部坏行。
本质（两态对立）：底部坏行=启动后又 resize、bifrost 重画 bug；保持在小=启动时小且之后无 resize。
唯一同时满足="尺寸已定、不再 resize 后"才启动。新 tab 创建时 tmux+网页终端头几百 ms 会做一两轮 resize，
上版"宽且稳定 0.3s"在 resize 中途就启动了。
改法：仍要求列数>80，但把稳定窗口从 0.3s 拉到 **~1s（_need=10）**，把建 tab 的 resize 轮次完整等过去；
cap 提到 10s（_max=100）。代价每 tab ~1s+，用户明确接受"可以慢一点"；第一个窗口只多等 ~0.7s、不破坏。
已 sh -n + helm 渲染/打包通过，chart 仍 1.0.8。

### 十、彻底回退 SQLite → Postgres + 放开 config.json 可写
背景：用户实测——当前(postgres 版)**保留数据重装，配置仍在**。说明"keep-data 会清中间件 Postgres"
这个当初切 SQLite 的前提**根本没验证扎实**（源于一次移除类型不明的 provider 丢失报告）。复盘：
- keep-data：appData 与中间件 Postgres **都保住** → Postgres 能留住（用户实测）；
- 彻底删除数据：appData 也被删 → SQLite 的 config.db 同样没了。
→ **SQLite 毫无额外收益**，反而带来孤儿 config.db 混乱。早先"保留数据还丢"的真凶应是 config.json
content-hash 覆盖，已由"providers 留空"解决，与 SQLite 无关。

改动（用户决策：回 Postgres + 放开文件可写）：
1. configmap：`config_store` sqlite → **postgres**（与 logs_store 同库 bifrostdb；providers 仍留空）。
2. config.json 不再只读挂载：init 容器从 `/etc/bifrost-default`（bifrost-config ConfigMap）**一次性 cp** 到
   `/app/data/config.json`（不存在才写），此后该文件在 appData 上**用户可改**、可持久。网关去掉只读 subPath 挂载。
3. 代价（用户已接受）：seed-once → 以后 chart 改 store 接线不会自动覆盖用户文件（需手删 /app/data/config.json 重拉）。
镜像无需重打；chart 仍 1.0.8，已重打 tgz。

迁移注意：从旧只读挂载版升级后，若 `/app/data/config.json` 残留旧文件（可能含 sqlite），init 不覆盖 →
需 `rm /app/data/config.json` 后重启 pod 让其重新播种 postgres 版；旧的 26MB 孤儿 config.db 可删（postgres 模式不读它）。

### 十一、最终定论：config + logs 都用 SQLite（推翻 §十）
§十里"keep-data 保住 Postgres"的说法又被实测推翻：用户删数据装→配置→**不删数据重装**，
**provider 没了，调用日志也没了**。证实：**uninstall+reinstall（含 keep-data）会清中间件 Postgres**，
只有 appData(/app/data) 活下来。结论锁死：

- `config_store` → **sqlite**，path `/app/data/config.db`
- `logs_store`  → **sqlite**，path `/app/data/logs.db`（官方确认 logs_store 支持 sqlite）
- `vector_store` 仍 Redis（仅语义缓存，丢了无所谓）
- config.json 仍 seed-once 到 appData、用户可改（§十的可写机制保留）
- 官方文档佐证：getbifrost.ai storage 页明确两 store 均支持 sqlite/postgres，sqlite 用 `config.path`。

附带：BIFROST_PG_PASSWORD 现已无人引用（仅因 postgres 中间件仍在 provision 而保留）；
postgres 中间件目前实际闲置，将来可考虑彻底摘掉以省资源（本次未动，避免扩大改动面）。

测试预期：删数据装=干净播种 sqlite；UI 配置写入 config.db；不删数据重装→appData 存活→
config.db+logs.db 都在→provider 与日志都应持久。chart 仍 1.0.8，已重打 tgz，镜像不变。
