## 六、晚间续：OverlayFS + chart 搬进镜像 + 用户包"零网络重装"攻坚

### 6.0 ⭐ 用户的硬指标（原话，一字不改）
> **「我他妈的不关心我这台测试机需不需要重装，我关心的是用户的机器在任何新装、重装、重启、升级下都不会再经过网络重装？！」**

判定标准：**用户机器，在「新装 / 重装 / 重启 / 升级」任意场景下，绝不再经过网络重装用户包。** 自己测试机的一次性过渡重装不算数。**这是后续所有改动的最高优先级验收标准。**

### 6.1 OverlayFS 取代 `cp -a` 快照（chart 1.0.44，commit `9057d3a`）
旧方案首启/升级要 `cp -a` 几百 MB rootfs 到 `.pkg-root`（IOPS 瓶颈，慢）。改为 **OverlayFS**：
- 镜像 rootfs（`/usr /bin /sbin /lib /lib64`）作只读 **lower（零拷贝）**；用户装包的增量落在 appData 上的小 **upper**。
- 新增 `init-overlay`（privileged，trusted `beclab/` 镜像，OPA 放行）挂载 overlay，`Bidirectional` 传播给其它容器。
- 首启/升级不再大拷贝、重启瞬间完成。

### 6.2 把 chart 里的脚本/静态资源搬进镜像（commit `a962ede`，chart 1365→~380 行）
- 新建 `opencode-docker/olares-bake/{lib,assets}`，把 init-setup / init-overlay / init-packages / pkg-manager / start-opencode 脚本、以及它们内联的静态内容（web-preview & system-admin SKILL.md、OMO 默认配置、python 配置写入器）全部移出 chart、烤进镜像 `/opt/olares-bake/`。
- `pkg-install` 放进 rootfs `/usr/local/bin`（随 overlay lower）。
- chart 只 `exec /opt/olares-bake/lib/<x>.sh` 并用 env 传少量动态值（域名、OMO 开关/版本）。
- 逐字比对确保行为等价。

### 6.3 期间排查的几个问题（结论）
- **bash 进不去 / 默认 shell**：根因①旧 pkg-manager 每次启动无条件 `apk del bash && apk add bash`，overlay 下 `apk del` 留 whiteout，离线时 add 失败→bash 消失；根因②多处硬编码 `/usr/bin/bash`（Alpine 实为 `/bin/bash`）。已改为**仅当 bash 真不可运行才自愈** + 全部用 PATH 解析。默认 shell 尊重 opencode 原生逻辑（有 bash 就优先 bash），终端 shell 选项可用即可。
- **右上角 Terminal 按钮消失**：opencode 上游 bug（v1.15.6+ 新版 V2 titlebar + `VITE_OPENCODE_CHANNEL` 在独立 web 构建下元素丢失），**前端编译期问题，chart 改不动**。
- **Web UI 页脚版本显示 1.15.x ≠ 1.16.0**：opencode 的 **web 前端版本与 CLI/server 二进制版本独立**；`opencode --version` 实测 1.16.0，属正常。
- **opencode.json / oh-my-openagent.json 持久化**：用户改动在 appData，重启/升级均保留。
- **OMO 当前版本怎么看**：见 `~/.cache/opencode/packages/oh-my-openagent@<ver>/` 目录名 / 配置里钉的 spec。

### 6.4 ⭐ 本次核心：用户包"零网络重装"（待打 `1.16.0-test3`，尚未提交）
**现象**：用户只多装了 1 个包（ffmpeg），升级却把 ffmpeg 的 **94 个依赖**联网全盘重装，卡死初始化。
**根因**：overlay 是否重置（→重装用户包）原本绑定 `BAKE_MANIFEST` 指纹（= opencode+OMO+cli+skills 版本）。**任何**版本一变（甚至 `@olares/cli@latest` 解析到新版）→指纹变→重置 upper→`apk add` 联网重拉。等于**几乎每次升级都重装**。

**三处修复（镜像侧，chart 模板无需动 = 6.2 搬进镜像的红利）**：
1. **`BASE_HASH` 解耦 + 改为「意图哈希」**（`Dockerfile`）：overlay 重置只由 `BASE_HASH` 决定，而 `BASE_HASH` 现在 = `sha256(alpine版本 + glibc版本 + BASE_PKGS列表 + arch)`，**不再哈希实时 apk DB**。
   - opencode/OMO/cli 怎么升都不变 → upper 保留 → 用户包**零重装、零网络**。
   - 之所以用「意图」而非「实时 DB」：避免重打镜像时上游 Alpine 打补丁导致 DB 漂移→误触发重装（即"无意义重装"）。
2. **钉死 Alpine**：`FROM alpine` → `FROM alpine:3.23`；`BASE_PKGS` 提为唯一来源 `ARG`。
3. **持久化 apk 缓存**（`pkg-manager.sh` / `init-packages.sh`）：appData 上 `/home/opencode/.apk-cache`，`ln -sfn .../.apk-cache /etc/apk/cache` 让 apk 自动用缓存；所有 `apk add` 去掉 `--no-cache`。同版本 `.apk` 命中本地盘、不再联网。
4. **删除 `chown -R /usr/local`**（`init-packages.sh`）：它会把整个 `/usr/local`（含 opencode 二进制）copy-up 进 upper，一旦保留 upper 旧 opencode 会盖住新镜像的→升级失效。去掉后 opencode/vite/cli 永远走 lower，升级自动生效。
- `init-packages` 标记格式 `.installed-<apphash>` → `.base-<basehash>`；skills 戳改用 `APP_HASH`（版本变才刷新，与 overlay 重置脱钩）。
- CI 默认 tag → `1.16.0-test3`；chart 主镜像 → `docker.io/beclab/lovehunter9-anomalyco-opencode:1.16.0-test3`（helm template 已验证；`sh -n` 三脚本通过）。

**当前各场景结论**：
| 场景 | 是否网络重装用户包 |
|---|---|
| 全新安装 | 否（无用户包） |
| 重启 | 否（upper 保留） |
| 升级 opencode/OMO/cli | **否**（BASE_HASH 不变）← 本次核心收益 |
| 我们主动改 BASE_PKGS / 升 Alpine / 升 glibc | 仍会（BASE_HASH 变→重置 upper），同版本可命中缓存离线、Alpine 大版本跳变则需联网 |

### 6.5 ⚠️ 距「硬指标」还差的一块（周三重点）
6.0 要求**任何场景**都不联网重装。目前唯一残留：**我们主动动基础层**（改 `BASE_PKGS`/升 `alpine`/升 `glibc`）时 upper 会重置并联网重装用户包。
- 现实里这只在我们主动决定时发生（用户日常升 opencode 不会触发），但严格按用户原话「任何升级」仍是缺口。
- **周三待定的关闭方案**（择一/组合）：
  a. 策略层：约定永不在普通发版里改基础层；需改时单独走、并预热缓存。
  b. 让 base-change 的 restore 强制走 `.apk-cache` 离线（同版本可行；Alpine 大版本跳变时需提前把新版 `.apk` 预热进缓存或预 bake）。
  c. 评估"重订基(rebase) upper 而非重置"的可行性与 apk DB 漂移风险。
- 还有过渡问题：从旧测试镜像升 test3 会**最后重装一次**（标记格式变 + 旧 upper 脏含旧 opencode）。用户明确：**测试机不在乎**，干净装即可，prod 不存在旧机制。
