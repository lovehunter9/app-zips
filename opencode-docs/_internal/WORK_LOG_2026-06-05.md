## 三、关键修正：OMO 缓存活在 appData hostPath，必须 seed

回顾运行时 overlay 契约：`/home/opencode` 被 **appData hostPath 整体覆盖**在镜像之上。而 OMO 缓存路径 `~/.cache/opencode/...` = `/home/opencode/.cache/...`，正好在被覆盖区。

→ **结论：烤进镜像 `/home/opencode/.cache` 无效**。改为与 `.pkg-root` 同款机制：
1. 镜像把 OMO 缓存烤到中立 staging `/opt/olares-bake/opencode-cache/packages/<spec>/`（不被 hostPath 覆盖）；
2. init 首启 `cp -a` seed 进 `/home/opencode/.cache/opencode/packages/<spec>`（带 marker，只一次）；
3. `opencode.json` plugin 项**钉精确版本** `oh-my-openagent@4.7.5`，与目录名逐字符一致 → 命中、零联网；
4. 用户改 `OPENCODE_OMO_VERSION` → spec 变 → seed 不命中 → opencode 自己联网拉一次（与今天回退语义一致）。

写进设计文档 §6.1（修正）+ §9A（chart 改动）。

## 五、重要发现：官方 Dockerfile 不能直接继承

官方 `packages/opencode/Dockerfile` 只有 18 行，且 `COPY dist/opencode-linux-x64-baseline-musl/bin/opencode`——拷的是它 **CI 自产的构建产物**，我们没有那个 `dist/`。

→ 所以我们是**重写**一份自包含 Dockerfile（二进制从 GitHub release 自取），而不是 `FROM` 它再叠层。已在 Dockerfile 注释和文档 §7 讲清。

## 七、插曲：olares-cli skill 描述超 1024（不是 OpenCode 的锅）

用户转来一条社区报告（RonnyPfannschmidt）：「olares-cli 的 skill 在 opencode/zed 里全坏了，因为 description 超长」。排查结论：

- 实测 `beclab/Olares` 仓 `cli/skills/` 下 6 个 skill，**5 个 description 超 1024**：settings 1296 / dashboard 1275 / cluster 1251 / files 1084 / market 1027；只有 olares-shared(982) 未超。
- 1024 限制三源一致：OpenCode 文档 https://opencode.ai/docs/skills （"Follow length rules"节）、Zed https://zed.dev/docs/ai/skills （Frontmatter 表 + 50KB 预算）、通用规范 openagentskills.dev。
- **但实测 OpenCode 1.16.0 并不强制 1024**：造 2040 字符描述的 skill，`opencode debug skill` 照常全量加载、不报错、不截断、不丢弃。文档写了规则、代码（V2 loader）没校验。真正硬性拒载/丢弃的是 **Zed / Codex**。
- 结论：**根因在 olares-cli（描述写太长），修复也在 olares-cli**，与我们打包的 OpenCode 应用无关，更不在镜像优化范围。已给用户可转给 olares-cli 团队的证据。
